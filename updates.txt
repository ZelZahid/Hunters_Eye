Hunter's Eye - Update Log
=========================

Versioning: starts at 0.001, incrementing by 0.001 for each significant update,
working toward 1.000 ("Hunter's Eye complete" - see the long-term vision in
CLAUDE.md, which is a long way off on purpose). Each version below has a
matching git tag (v0.001, v0.002, ...) pointing at the exact commit for that
state. To get back to a known-working point after something breaks, check out
that tag rather than guessing from commit history - that's what these are for.

------------------------------------------------------------------------------
Version 0.001 - 2026-08-27
------------------------------------------------------------------------------
First tagged checkpoint. Took the project from a rough Diablo II prototype to
a working, documented, cross-platform-minded detection engine:

- Docs & project setup: added CLAUDE.md (architecture + long-term product
  vision), requirements.txt, a portfolio-ready README, and a source-available
  license (PolyForm Strict) suited to a future commercial product.
- Cleanup: merged two main.py files into one, renamed version1/ -> legacy/,
  organized assets into folders, added .gitignore.
- Fixed an OpenCV 5 compatibility break (cv.groupRectangles was removed from
  OpenCV's Python bindings; replaced with NMS-based match merging) and a
  backwards result-limiting slice bug.
- Added OCR-based item-name detection (text_detection.py + assets/items.txt)
  so new items can be watched for by adding a line of text, not a new
  reference image - built to scale to hundreds of item names at no extra
  per-frame cost.
- Performance pass: profiled every stage of the pipeline, cut matchTemplate
  cost via a tuned capture scale, and moved OCR onto its own thread so it can
  no longer stall the fast detection loop. Took real-gameplay FPS from ~11 to
  ~40+.
- Replaced the debug window with a real transparent, click-through overlay
  (overlay.py) drawn directly over the game, fixing two subtle Win32 bugs
  along the way (the window rendering solid black, and clicks not passing
  through to the game) - both verified with actual on-screen testing, not
  just code review.
- Confirmed end-to-end on real gameplay: the overlay correctly boxes
  "Full Rejuvenation Potion" text over the live game, with the character
  still fully controllable through the overlay.

Version 0.002 - 2026-08-27
------------------------------------------------------------------------------
Focused entirely on making OCR item tracking usable during real, active
gameplay instead of only while standing still - a mix of visual fit and a
multi-round performance investigation, each step verified against the real
game rather than assumed:

- assets/items.txt renamed to assets/targets.txt (matches the code's own
  target_items/load_target_items naming); added FLAWLESS RUBY as a second
  watched item.
- Label boxes now padded to match the game's semi-transparent background
  panel instead of hugging just the OCR'd text glyphs.
- Fixed OCR item-tracking during movement, in three rounds once each fix
  proved insufficient on real gameplay:
  1. Widened the local re-localization search window and shortened the OCR
     refresh interval.
  2. Found the interval was now BELOW a single OCR call's own cost, making
     the throttle a no-op (confirmed via a loop-rate diagnostic); fixed the
     interval, and made tracking refresh its own reference patch every
     frame instead of comparing against an increasingly stale one.
  3. Found - via real gameplay logging - that OCR's returned position is
     already stale by the OCR call's own duration (~150-300ms at the time),
     not just "since the last loop tick"; fixed by immediately re-localizing
     against a fresh frame right after every OCR call instead of waiting for
     the next loop iteration.
- Cut real OCR latency significantly: measured actual OCR cost against real
  gameplay (~0.9s/call - far higher than earlier synthetic-benchmark
  assumptions of ~150-300ms), then cropped OCR to the gameplay viewport
  (excluding HUD margins where item labels never render anyway), cutting it
  to ~0.42s/call - over 2x - for free. This let the OCR refresh interval
  drop further, roughly halving worst-case discovery latency for brand-new
  items on top of the per-call speedup. An MSER-based smarter-sounding
  alternative was tried and measured first, then rejected when its own
  overhead turned out to eat most of its benefit - see Error_history.txt.
- Result: item discovery and tracking now hold up well during continuous
  movement and direction changes, not just while standing still - confirmed
  via real gameplay testing, not just code review.
- Found and fixed one more discovery-latency bug after user-reported real
  gameplay felt like a ~3-second delay: the OCR refresh interval was timed
  from when the previous call FINISHED, not when it started, silently
  stacking the call's own ~0.5s duration onto the intended 0.7s interval
  (~1.2s real gap instead of 0.7s). Confirmed via a live scan-to-scan-gap
  diagnostic before and after the fix. Real-gameplay hotkey behavior (Alt
  held continuously, not pressed on-demand) and a "does combat complexity
  spike OCR cost" hypothesis were both checked and ruled out as explanations
  - see Error_history.txt for both. User-confirmed after the fix: perceived
  delay dropped from "like 3 seconds" to "more like 0.5 seconds."

Version 0.003 - 2026-08-27
------------------------------------------------------------------------------
Pushed OCR speed further after user still wanted more than v0.002 delivered.
Considered and measured two alternative approaches before picking one:

- Considered switching text detection from OCR to template-matching known
  target strings (like the image-matching path already does for icons).
  Measured first: at OCR's native resolution, a single matchTemplate call
  costs ~21ms, so 20 templates/frame (~424ms) already matches OCR's old
  cost, and 80 templates/frame (~40 items with color-rarity variants) costs
  ~1.7s - over 3x slower than OCR. Rejected: OCR's cost is constant
  regardless of vocabulary size, template matching's grows linearly - the
  wrong trade for a system meant to scale to dozens/hundreds of items.
- Added tesserocr as the primary OCR backend (text_detection.py), talking to
  the Tesseract engine in-process instead of pytesseract's subprocess-per-
  call model, with automatic fallback to pytesseract if unavailable. No
  official Windows wheel exists (source build failed, needs a full C++
  toolchain - see Error_history.txt); used a well-established prebuilt-wheel
  project instead, no compiler needed. Measured ~3.5-4.5x faster against
  real gameplay (~0.1-0.26s vs ~0.42-0.6s per OCR call).
- Retuned OCR_INTERVAL_SECONDS down to 0.4 (from 0.7) now that a call costs
  far less, cutting worst-case new-item discovery latency further to ~0.6s.
- Verified live against real gameplay: zero lost-track events across a full
  test with substantial on-screen movement, FPS unaffected (~41).
- Changed the console FPS line to print once every 5 seconds (average over
  just that window) instead of every single frame, which was flooding the
  console at ~40 lines/second.

Version 0.004 - 2026-08-28
------------------------------------------------------------------------------
Added auto-collect: the first concrete use of the "action" seam described in
CLAUDE.md (move mouse / press key / click), which had only existed as a
future-plans note until now. Most of this version is a multi-round accuracy
investigation once real gameplay testing showed the first version wasn't
good enough - see Error_history.txt #16-#18 for the full root-cause detail
behind each round below.

- assets/targets.txt: a trailing "*" on an item name now marks it "to
  collect" - auto-collect moves the mouse to it and clicks until it's picked
  up or 5 seconds pass with it still on the ground, at which point it backs
  off and hands mouse control back rather than clicking forever.
- actions.py (new): a generic, game-agnostic click_until_gone() - knows
  nothing about item names or OCR, just clicks wherever a caller's position
  callback reports until that callback returns None or a timeout elapses.
  main.py's new run_auto_collect() thread is the D2R-specific glue that feeds
  it OCR-tracked positions.
- Hotkeys changed: quit moved from 'q' to 'End', and a new 'F4' snoozes
  auto-collect for 10 seconds (then re-arms itself automatically - not a
  plain on/off toggle, so it can't be accidentally left disabled). Both are
  global hotkeys via the `keyboard` package, same as before; 'q' was
  replaced because it's an ordinary letter pressed constantly during real
  gameplay.
- Fixed a false-positive bug in the fuzzy OCR matcher: short target names
  (2-3 letter Diablo II rune names like "Lo", "Um", "Ko") could match
  unrelated on-screen noise under the same fixed 0.75 similarity cutoff that
  works fine for long names - because difflib's ratio math makes short
  strings far more sensitive to a single shared letter. Now the required
  cutoff scales with target name length (effectively exact-match at length
  <= 3). This matters more than it otherwise would now that a match can
  trigger a real mouse click, not just a wrong overlay box.
- Fixed unstable detection boxes for short names: matching was done against
  Tesseract's whole recognized line, but Tesseract doesn't consistently
  decide whether e.g. a rune's name and the word "Rune" next to/below it
  belong on the same line between OCR passes - so the box (and therefore
  where auto-collect clicked) changed size depending on what else got swept
  onto the line that pass. Matching now tries every contiguous word-run
  within a line and boxes only the words that actually matched.
- Auto-collect click accuracy, fixed in stages after each proved
  insufficient on real gameplay (character moving during detection kept
  making clicks land where the item used to be, then clicks landing
  correctly but not registering, then registering but "rushed"):
  1. Replaced separate moveTo()+click() calls with one click(x, y) call,
     removing a ~0.1s gap (pyautogui's own default PAUSE) between the
     cursor arriving and the click actually firing.
  2. Slowed the actual click-retry cadence from every 0.15s to every 0.8s
     (while still polling every 0.1s for fast success detection) - D2R
     treats a click on an item as "walk over and pick it up on arrival," so
     clicking much faster than that walk takes kept re-issuing the move
     command and retargeting the character before it ever arrived.
  3. Replaced pyautogui.click() with manual mouseDown()/sleep/mouseUp():
     click() sends the press and release combined into one Windows
     mouse_event() call with zero time held, which some games' per-frame
     input polling can miss entirely even with the cursor in the right
     spot.
  4. Split the move and the press apart with their own settle delay too
     (not just press-then-release) - mouseDown(x, y) moved the cursor and
     pressed in the same call, risking the game resolving the click against
     where the cursor was a frame earlier.
- Reduced unnecessary overlay redraws (overlay.py's draw_rectangles() now
  skips repainting when the rectangles haven't changed since last frame) -
  an attempted fix for a reported mouse-cursor flicker; plausible root cause
  identified (this always-on-top layered window was being repainted every
  frame regardless of whether anything visible changed) but not separately
  re-confirmed by the user after the fact.
- Gated the OCR loop-rate/scan-gap/call-time diagnostic prints added in
  v0.002-0.003 behind a new OCR_DEBUG_TIMING flag (default off) - useful for
  re-tuning OCR_INTERVAL_SECONDS later, but too noisy to leave on by default
  once auto-collect added its own console output.
- User-confirmed after all of the above: click accuracy issue resolved.

Version 0.005 - 2026-08-28
------------------------------------------------------------------------------
Added per-item detection box colors, with a design discussion up front about
which targets.txt convention would be least error-prone before writing any
code:

- assets/targets.txt: an optional trailing "[colorname]" tag (e.g.
  "[purple]", "[darkorange]") sets an item's box color; omitted or
  misspelled falls back to the same green used before this feature existed,
  with a load-time warning on a misspelling rather than a silent wrong
  color or a crash. Considered and rejected a single-letter code (the
  user's original "[o]"/"[p]" idea) and a category-indirection scheme
  (define a color once, tag many items with a category name) in favor of
  this simpler per-item tag once the user clarified they wanted color set
  per item, not shared across a category.
- text_detection.py: new NAMED_COLORS palette (green, red, blue, yellow,
  cyan, purple, orange, darkorange, pink, gold, white) and DEFAULT_BOX_COLOR
  (green, unchanged). Deliberately excludes magenta/fuchsia - overlay.py's
  click-through mechanism depends on one exact color being invisible, and a
  box in that exact color would silently vanish.
- Colored FULL REJUVENATION POTION purple and all 15 runes dark orange in
  targets.txt, per the user's request.
- Threaded color end-to-end through the whole detection pipeline
  (find_text_matches -> shared_text_tracks -> detect_objects's rectangle
  merge -> detection_queue -> both run_overlay and the run_debug_window
  fallback) as an (r, g, b) tuple, converted to hex for Tk and reversed to
  BGR for OpenCV at each renderer's own call site - verified with a
  simulation script threading fake tracks through every stage before
  relying on live testing.
- Image-template matches (the icon-matching path, unrelated to targets.txt)
  keep using DEFAULT_BOX_COLOR - the color tag only applies to OCR matches.
- Found and fixed a documentation gap while touching CLAUDE.md for this:
  the auto-collect thread and actions.py added in v0.004 were never
  actually documented in the Architecture section (only referenced in
  passing from other sections) - added proper subsections for both.

Version 0.006 - 2026-08-28
------------------------------------------------------------------------------
Game-state reading: the engine can now answer "how full is that?" as well as
"where is that?". This is the groundwork for a decision layer (drink a potion,
retreat, run a scripted route) - the first thing any of that needs is to know
the character's current health and mana, and nothing in the project could read
a number off the screen before this.

- New game_state.py: a third detector alongside template matching and OCR, but
  a different shape of answer - it returns a single 0.0-1.0 fill fraction for a
  HUD meter rather than a bounding box. Deliberately generic: a "meter" is a
  screen region, a color, and a fill direction, which describes a health orb, a
  mana bar, a stamina strip or a robot's battery gauge equally well. No Diablo
  II knowledge in the module at all.
- New assets/meters.json (written by the calibrator on first run): where the
  meters actually
  are and what color they are, as fractions of the screen. Same philosophy as
  targets.txt - adding or moving a meter needs no code change. Stored as
  fractions specifically so one config stays correct at any capture scale,
  which is what keeps this from becoming another shared-resolution-constant
  trap (see Error_history #6).
- New calibrate_meters.py: drag a box around each orb once, and it writes the
  config. Then it runs a live preview showing the exact pixels being counted,
  the detected liquid surface drawn as a line, and the resulting percentage
  updating in real time. The preview exists because a mistuned color range
  fails by returning a plausible-but-wrong number rather than by raising an
  error, so it has to be checked by eye before anything acts on it. It also
  reports the measured hue/saturation of the pixels you selected and warns if
  they don't match the expected preset.
- main.py reads the meters off the frame detect_objects() already captured,
  rather than in a thread of its own. Measured 0.15ms/frame for two orbs -
  about 0.7% of the frame budget at 45 FPS - whereas a dedicated thread would
  have had to spend ~17-20ms on its own mss capture to do a ~0.3ms measurement.
  Readings are published to shared_game_state behind a lock and exposed via
  current_game_state(), following the same never-block-on-a-slow-producer
  pattern the OCR thread already uses.
- Readings are median-smoothed over 5 frames. Median rather than average
  because the failure mode is one frame being wildly wrong (a tooltip drawn
  over the orb on hover, a spell effect flashing across the HUD), and a median
  discards such a sample outright while an average absorbs part of it.
- A failed read reports None, not 0.0, and the two are kept distinct all the
  way through - a consumer must never mistake "couldn't read the orb" for
  "you have no health left". Missing config degrades to "no game-state
  awareness" with a warning rather than preventing startup.
- Verified with a 10-case synthetic test before any live testing, which caught
  two real bugs in the process - see Error_history #19 and #20. Both were in
  the fill measurement itself, and both were the kind that look correct under
  casual testing and fail at exactly the moment the number matters.

No new dependencies - this uses OpenCV, numpy and mss, all already required.

Version 0.007 - 2026-08-28
------------------------------------------------------------------------------
OCR that actually reads the game, item matching that can tell similar names
apart, and HUD meters that survive windowed mode. Mostly a correctness release:
several things that appeared to work were working by luck, and the ones that
were plainly broken turned out to share root causes with them.

OCR INPUT PREPARATION - the largest single win in the project so far.
- Frames are now binarized before reaching Tesseract (text_detection._preprocess).
  Tesseract expects a scanned page: dark text, light background, no texture. A
  game frame is the opposite. Measured on a real frame containing FIVE plainly
  legible rune labels, Tesseract read ZERO of them and returned 57 junk
  fragments scraped off the terrain; binarizing read four of the five.
- It is also much FASTER, which is not the usual direction for an accuracy fix:
  Tesseract's cost scales with how much candidate text it believes it can see,
  and thresholding deletes the texture generating the false candidates.
  Measured: 362ms -> 51ms per OCR call, 83 words -> 7; a full
  find_text_matches() call went 374ms -> 67ms.
- Three modes with PREPROCESS_AUTO choosing per frame from its own brightness,
  so the detector still works on a document or a light-themed window. Verified
  on a white page, a light-grey page, a dark terminal and a black game screen.

ITEM MATCHING - telling similar names apart.
- Names are matched word by word, not as one string. "RAL RUNE" scored exactly
  0.75 against "JAH RUNE", "LEM RUNE" and "GUL RUNE" because the shared " RUNE"
  is 5 of 8 characters, so an unlisted rune was being picked up and clicked on.
- Short words are compared by character POSITION rather than by difflib, which
  counts how many characters match but not where. "KE" scored 0.5 against both
  "KO" (a real misread) and "EL" (unrelated); positionally that is 0.5 and 0.0.
- targets.txt gained a leading "-" ("look-alike") marker: matched, then
  discarded. Fuzzy matching always returns the CLOSEST LISTED name, so an
  incomplete vocabulary misattributes rather than reporting nothing. All 16 low
  runes and the small Rejuvenation Potion are listed this way.
- Candidate spans are ranked longest-match-first, ratio only breaking ties.
  Ratio-first suppressed every clean read of "Full Rejuvenation Potion",
  because its own tail matched the look-alike entry equally well - a bug that
  got WORSE as OCR quality improved.
- Ties between different targets report nothing rather than guessing.
- diagnose_ocr.py: shows what Tesseract actually read and why each line did or
  did not match. Written because three fixes were attempted before anyone
  looked at the OCR output itself.

HUD METERS - windowed mode, multiple resolutions, status colours.
- window_region.py: meter regions can anchor to a window's client area instead
  of the screen. A detection box is screen-absolute and does not care where the
  game is; a meter region is a statement about a window's layout and is
  meaningless without it. Meters calibrated fullscreen read 0% once the game
  was windowed at 1280x800.
- One calibration profile per window shape, selected automatically by size then
  aspect ratio. Calibrating at a new size adds a profile; the same size
  replaces. A shape with no profile reads nothing and says NOT CALIBRATED,
  rather than reusing a profile that does not fit.
- A meter can now be several colours. Diablo II turns the health globe green
  while poisoned, which made it read 0% at every real fill level - "you are
  dead" at 90% health, during the one situation where the number matters most.
- calibrate_meters.py: shrinks the hand-drawn box to the meter's own colour
  (43% of a real hand-drawn box was animated scenery, which made the reading
  track torchlight rather than health), captures the same region main.py does,
  and opens its windows topmost so they are not hidden behind the game.

OVERLAY.
- Game-state debug panel on the overlay, toggled with 'F5', drawn as an
  independent layer so it never disturbs the detection boxes. Follows the
  anchored window. Preserves the None/0.0 distinction visually: a failed read
  shows "no read" with no bar, an empty meter shows 0% with a bar at zero.
- Panel plate is ~50% transparent (measured 47%), and TRANSPARENT_COLOR moved
  from magenta to near-black. The key colour is what antialiasing smears around
  every glyph, and magenta produced a visible red glow around each word;
  measured tint went from +36.8 to +0.5. The constraint on box colours inverts:
  magenta is now usable, near-blacks are not.

No new dependencies. window_region.py uses pywin32, already required on Windows
and already optional, and degrades to "no anchor" everywhere else.

Fourteen entries added to Error_history.txt (#21-#34) covering the above.

Version 0.008 - 2026-08-29
------------------------------------------------------------------------------
Pure performance release. Average FPS had drifted down to ~34; this took it to
~51 idle and ~43 with three items being tracked, measured A/B against v0.007 on
the same machine with the same harness. Nothing was traded away to get there -
every change below is either bit-identical output or was measured to be equally
or MORE accurate than what it replaced. No behaviour, no tuning constants, and
no detector logic changed.

The theme: almost all of it was work the pipeline was doing and then throwing
away. Very little was the actual detection.

TEMPLATE MATCHING NOW RUNS ON ONE CHANNEL, NOT THREE (17.5ms -> 3.2ms/frame).
- The three-channel matching was already colour-blind and nobody had checked.
  TM_CCOEFF_NORMED subtracts the mean and normalises across the whole patch, so
  measured against the real needle, a FULLY DESATURATED copy and copies
  hue-rotated by 30/60/90/120 degrees all still scored 1.000 in colour. The two
  extra channels were buying no discrimination at all for 14ms a frame.
- False-positive headroom on real screen content is unchanged (best non-match
  0.365 grey vs 0.353 colour, both far below the 0.60 threshold), and an
  end-to-end test boxes all three planted needles at the exact expected pixel
  while firing zero boxes on a needle-free frame.

TRACK RELOCALIZATION LIKEWISE (27-33ms -> 5.7ms PER TRACKED ITEM).
- Same reasoning, but this was the bigger absolute cost: at OCR_CAPTURE_SCALE
  1.0 the search window is ~700x530 native pixels, so three items on the ground
  cost the OCR thread ~100ms every loop iteration - it saturated a core exactly
  when something was worth tracking.
- Accuracy went UP, not down. Over 20 perturbed relocalizations (drift, dimming,
  added noise) grey found the correct position 20/20 against colour's 18/20 and
  scored equal or higher confidence on every single one.

THE OCR THREAD NO LONGER CAPTURES FRAMES IT WILL NOT LOOK AT.
- It ran a full-resolution capture every loop iteration unconditionally, ~45
  times a second. With no tracks to relocalize and no scan due - the normal
  case, since most of the time nothing is on the ground - that frame was
  discarded untouched. An idle thread was burning a whole CPU core and roughly
  400MB/s of memory bandwidth against the two threads that actually set the FPS.
  It now checks first and sleeps instead.
- Also: cv.resize at fx=1.0 is NOT a no-op, it is a full-resolution copy, and it
  was running on every one of those captures. ~3.7ms each, for an identical
  array.

CAPTURE STOPPED COPYING 8MB PER FRAME, TWICE.
- np.frombuffer over mss's own buffer instead of np.array(img), which goes
  through the array interface and duplicates the whole 1920x1080x4 grab. Both
  capture sites. Verified byte-identical on the same capture; ~4ms/frame.
- Downscale now happens BEFORE the alpha channel is stripped rather than after.
  Bit-for-bit identical output (verified: max difference 0 over a full frame) -
  INTER_LINEAR mixes channels independently and alpha is discarded either way -
  but the colour conversion then runs over 576x324 pixels instead of 1920x1080.
- Dropped a per-frame .copy() of the detection frame that nothing needed.

MEASURED AND REJECTED, so it does not get re-tried:
- Grabbing small sub-regions around each track instead of the whole screen, for
  relocalization. One 700x530 grab is 6.3ms against 17.3ms for the full screen,
  but THREE of them cost 22ms - more than the full-screen grab they would
  replace. Per-call overhead dominates; it would only pay off at one track.
- Capping OpenCV's thread count to leave more CPU for the game. matchTemplate
  barely parallelises here at all (3.12ms at 16 threads vs 3.26ms at 1), so
  there is nothing to reclaim.

OVERLAY REPAINT RATE, decoupled from detection FPS - a follow-up to the above.
- Making detection faster silently made the overlay repaint more often, because it
  redraws once per detection frame. Measured, box repaints went 34/s -> 51/s purely
  as a side effect. This is a fullscreen always-on-top LAYERED window, so every
  repaint makes the compositor redo the whole screen and the cost lands on the game,
  not on us - it shows up as cursor flicker and as the game feeling less crisp.
- overlay.py now caps the two layers independently: BOX_REDRAW_HZ 30, PANEL_REDRAW_HZ
  10. Purely display rates - nothing reads the screen to make a decision (auto-collect
  reads shared_text_tracks directly), so detection, tracking and actions are untouched.
- Measured, worst case (boxes moving AND health ticking) against a ~51Hz caller:
  repaint work 73.3 -> 34.3 ms/s, box repaints 47.6 -> 24.6/s, panel 32.0 -> 10.0/s.
- The one trade, stated plainly: a rate cap can only land on caller_rate/N, so a 30Hz
  cap against a 51Hz caller takes every second call - boxes update ~25/s, slightly
  less often than the ~34/s before. Still fluid; it buys back over half the
  compositor work.
- Verified a skipped repaint cannot strand a stale box: the pending content is
  deliberately NOT recorded as drawn, so the next call still sees a difference. Tested
  explicitly - after movement stops the box lands on its true final position.

FLICKER, ROUND TWO - after testing confirmed the click delay was gone and the
flicker was much improved but not fully.
- The panel's black text outline is off. It drew every label NINE times and was
  the single most expensive thing the overlay did. It existed to fight MAGENTA
  fringing, and TRANSPARENT_COLOR became near-black in v0.007 - so it had been
  painting black next to black ever since. Re-measured over both a dark and a
  bright backdrop: 8 offsets vs 4 vs none gave glyph contrast 183.7/183.6/183.4
  and 181.3/181.0/180.4, identical lit-pixel counts. Panel repaint 1.66ms ->
  0.605ms. The two settings are coupled: if the key colour ever goes back to
  something saturated, the outline has to come back with it.
- Boxes are no longer repainted for jitter (BOX_MOVE_DEADBAND_PX, 4px). At
  CAPTURE_SCALE 0.3 coordinates are scaled back up 3.33x, so ONE pixel of
  matchTemplate jitter on a completely stationary item becomes a 3-4px jump on
  screen and forced a fullscreen repaint every single frame, forever. Measured,
  a stationary-but-jittering item went from ~25 repaints/s to 0.3/s - the
  common case of standing still with an item on the ground is now free.
- Cumulative worst case since v0.007: repaint work 73.3 -> 31.5 ms/s. Stationary
  item with jitter: ~25 repaints/s -> 0.3/s, 2.5 ms/s.
- Verified the deadband cannot strand a box: compared against the last DRAWN
  position, so a box creeping 2px/frame stays within 4px of truth instead of
  falling behind. Appearing, disappearing and recolouring are never suppressed.
  Known trade: a box settles up to 4px from its true position when movement
  stops rather than snapping exactly. Display-only - auto-collect clicks
  coordinates from shared_text_tracks, never the drawn box.

ALSO MEASURED AND REJECTED:
- Updating canvas items in place with coords() instead of delete-and-recreate,
  on the theory that clear-then-redraw is what flickers. It is not faster:
  0.381ms vs 0.391ms for three boxes. Not worth the extra state.

WHAT WAS MEASURED AND FOUND *NOT* TO BE A PROBLEM:
- The overlay does not delay clicks. Measured end-to-end (click issued -> the handler
  of a window underneath actually running, real clicks, overlay repainting concurrently

Version 0.009 - 2026-08-30
------------------------------------------------------------------------------
Frame source seam + DXGI capture. SAME frame rate for 36% LESS CPU, and the
pipeline's own ceiling raised from ~58 to ~177 FPS in case it is ever wanted.

WHAT THE PROBLEM ACTUALLY WAS:
v0.008 took detection off the critical path (3.2ms/frame, ~312 FPS on its own),
which left screen CAPTURE as 83% of the frame budget and the sole thing setting
the frame rate. Measured on dev hardware (i9-11900K / RTX 5070, 1920x1080):
  sct.grab full screen                  13.6 ms
    of which GDI BitBlt alone           12.7 ms   <- the actual wall
  resize(0.3) + cvtColor                 0.3 ms
  -> capture thread total               16.0 ms = a hard ~58-62 FPS ceiling
It is NOT vsync: this display runs at 239Hz, so the ~16.8ms figure recorded
earlier was never a refresh artifact. And it is not fixable by tuning, because
it is one GDI blit: CAPTURE_SCALE does not touch it (the grab happens at full
resolution regardless - the resize is 0.3ms), and doing the downscale GDI-side
with StretchBlt measured 12.3ms, i.e. all of the cost is the blit and none of
it is the readback.

WHAT CHANGED:
- New frame_source.py - the "frame source" seam from CLAUDE.md, made concrete
  for the first time. A frame source is handed a screen region and hands back
  BGRA pixels; it knows nothing about what looks at them. cv.VideoCapture for a
  camera is the next backend to slot in here.
- DXGI Desktop Duplication backend (bettercam). The GPU already holds the
  composited desktop, so this reads it back instead of asking GDI to re-blit it.
- mss stays as the portable backend, chosen automatically when bettercam is
  absent, when the platform is not Windows, AND as a runtime fallback if DXGI
  fails mid-session (DXGI_ERROR_ACCESS_LOST on a resolution change, UAC prompt,
  driver reset or fullscreen transition). All three paths tested explicitly.
- main.py's capture loop is now PACED to TARGET_FPS (60) rather than running
  flat out, which is the actual point of the change - see below.

MEASURED, end to end on the real pipeline (capture + detect threads):
  mss, unpaced (v0.008)          55-59 FPS   0.78-0.84 cores   15.3 CPU-ms/frame
  DXGI, paced to 60               59.7 FPS   0.42-0.50 cores    7.0 CPU-ms/frame
  DXGI, unpaced                    177 FPS   3.56 cores        20.1 CPU-ms/frame
Full pipeline with overlay, OCR and auto-collect all live: 56.3 FPS.
mss fallback path re-measured after the change: 52.4 FPS / 0.79 cores - i.e.
unchanged from v0.008, so nothing regressed for a machine without bettercam.

WHY PACED, AND WHY 60:
Capture used to BE the throttle - mss could only produce ~58 frames a second, so
the loop never had to decide how fast to run. DXGI can produce ~177, and taking
all of them costs 3.56 cores instead of 0.42, which is the exact opposite of
what this project wants (design priority #2: never noticeably slow down whatever
it is watching). Note that unpaced full-screen DXGI is also the WORST row in the
table for CPU-per-frame - chasing FPS with no cap makes the thing that actually
matters worse. Higher FPS was never the goal; the same work for less CPU is.
60 specifically, because nothing downstream can use more: the overlay caps its
own repaints at BOX_REDRAW_HZ (30), auto-collect clicks coordinates out of
shared_text_tracks rather than from this path at all, and game_state's readings
are median-smoothed over 5 frames (83ms at 60 FPS).
Pacing also made frame delivery visibly STEADIER, not just cheaper: p95 frame
gap 18.4ms vs 21.9ms and worst case 21.1ms vs 32.5ms, because the loop is no
longer racing an unpredictable blit.

QUALITY: nothing traded. Same capture region, same resolution, same detector,
same thresholds, same coordinates. The only behavioural difference is that DXGI
returns a frame only when the desktop CHANGED, so a static screen re-serves the
previous frame instead of re-capturing an identical one - which is what mss was
already effectively doing, just at full price.

MEASURED AND REJECTED, so it does not get re-tried:
- bettercam's video_mode / get_latest_frame(): waits on an Event with NO
  timeout, so a dead capture thread hangs the caller forever with no way to time
  it out - the one failure mode design priority #1 rules out. It also
  np.array()-copies every frame out of a ring buffer, the same per-frame 8MB
  copy v0.008 removed. The polled grab() used instead measured CHEAPER anyway
  (3.4 vs 5.6 CPU-ms/frame at a matched 90 FPS), so nothing was traded for it.
- GDI StretchBlt to downscale on the GDI side (12.3ms with COLORONCOLOR, 17.0ms
  with HALFTONE, vs mss's 16.0ms). The nearest-neighbour mode is barely faster
  than the thing it replaces and throws away pixels the matcher needs; the
  quality mode is slower outright.
- Giving detect_text() its own DXGI source. It cannot have one - see
  Error_history.txt #39. It keeps its own mss capture.

NOT DONE, deliberately (both are real and both are quality decisions, not waste):
- Capturing only the game window instead of the whole screen. Measured 1280x800
  at 3.4 CPU-ms/frame against 7.0 for full screen - the single biggest remaining
  win. Held back because it changes the coordinate space every consumer assumes
  (CAPTURE_RECT, SCALE_TO_NATIVE, window_region.to_frame_fractions), which is a
  change worth making on its own rather than buried in this one.
- OCR_INTERVAL_SECONDS. Measured a single find_text_matches() call at 567ms
  against a text-heavy desktop while the interval sits at 0.4s - i.e. below the
  call's own cost, which CLAUDE.md documents as the condition under which the
  throttle stops throttling and starves relocalization. That thread measured
  ~0.9 cores on its own, MORE than the entire fast path. Not changed here
  because the right value depends on the real in-game call cost (~0.1-0.26s when
  last measured in-game), which needs OCR_DEBUG_TIMING during actual gameplay.

One new dependency: bettercam (Windows-only, optional, marked
sys_platform == "win32" in requirements.txt). One new file: frame_source.py.

Version 0.010 - 2026-08-30
------------------------------------------------------------------------------
Closed the loop the whole project has been building toward: read a number off
the screen, decide, press a key. Two features, and the second one only exists
safely because the first went in ahead of it.

FOREGROUND GUARD. Nothing previously checked that the game was still the window
on screen. Alt-tab away and the HUD meters measured whatever was now in front
of it - typically 0%, i.e. "you are about to die" - while auto-collect went on
clicking at screen coordinates that now belonged to a browser.

- window_region.find_window() now returns an OPAQUE HANDLE alongside the rect,
  so is_foreground() can be a raw GetForegroundWindow() comparison. Measured
  0.3us/call against 0.151ms for the EnumWindows sweep that finds the window in
  the first place - about 500x - which is the entire reason it takes a handle
  and not a title. At 60 FPS the check costs 0.018 ms/s.
- Wired into three places: meters report None (never 0.0), auto-collect stops,
  and the panel says GAME STATE / NOT FOCUSED / readings suspended / actions
  paused. The panel matters more than the console here for the same reason the
  RECALIBRATE banner does - the person who needs to know why nothing is
  happening is looking at the game, not at a terminal that already scrolled.
- Auto-collect is gated MID-ATTEMPT too, via click_until_gone's existing
  is_paused callback. An attempt clicks repeatedly for up to 5s, so alt-tabbing
  one click into it would otherwise let the rest land somewhere else entirely.
- None is a THIRD answer and is not False. No pywin32, no "_anchor" in
  meters.json, or the window not currently found all return None, and
  actions_allowed() is "anchor_focused() is not False". A setup that cannot
  perform the check is never disabled by it - otherwise macOS would have every
  reading and every action switched off permanently.
- Resolved a question that had been open in todolist.md: this is a hard stop,
  not an indicator. Focus is a conservative proxy for visibility and will say
  no in cases that would in fact have worked. A false no costs a paused pickup;
  a false yes costs a potion drunk against a browser's pixels.
- The anchor's handle is refreshed on every lookup even when the rect is
  unchanged: a game closed and relaunched at the same size and position is a
  DIFFERENT window with an IDENTICAL rect, and keeping the old handle would
  leave the check comparing against a window that no longer exists - i.e.
  permanently False, i.e. the guard stuck on with no way to clear it.

POTION DRINKING. The first thing in the project that acts on a measured NUMBER
rather than a found position, and the first consumer of game_state.py at all.

- actions.press_key() is the generic half; main.py's POTION_RULES /
  _potion_due() / run_potion_drinking() is the Diablo II glue. Belt as
  configured: 1 health, 2 and 3 rejuvenation (emergency tier), 4 mana.
- Rules are evaluated in order, first match wins, and each keeps its OWN
  cooldown. That is what lets the emergency tier fire immediately after an
  ordinary heal - taking a big hit one second after drinking is exactly when a
  rejuvenation is needed, and one shared cooldown would swallow it.
- POTION_MIN_GAP_SECONDS is a floor under every press regardless of rule. The
  per-rule cooldowns are the tuning knob; this is the safety net that makes
  "empty the belt in one second" impossible even with a mistuned threshold or a
  misreading orb.
- A rule with several keys alternates between them. Nothing here can see how
  many potions a belt column holds, so spreading presses across both
  rejuvenation columns beats emptying one and then pressing a dead key
  mid-emergency.
- _potion_due() is kept pure - no clock of its own, no globals, no key presses
  - because what it decides is "press a key into a live game", which is not
  something to validate by playing and hoping. test_potions.py covers it with
  27 assertions and needs no game.

FOUND WHILE BUILDING IT, and the reason the guard had to go first:

- The guard's meter suspension never reached a consumer. It set the raw
  readings to all-None, but Smoother converted that straight back into the last
  good value FOREVER - probed directly, 60 consecutive failed reads still
  published 0.85 - and current_game_state_age() stayed fresh the whole time,
  because it is the READING that went stale, not the publishing. A potion layer
  would have read a frozen, confident, live-looking number. Fixed generically
  in game_state.py (MAX_CARRIED_FAILURES, 15 frames) rather than as a special
  case in main.py, since the pre-existing "window not found" path had it too.
  Past the cap the meter drops its history as well, so a good frame arriving
  after a gap is not median-blended with values measured before it.
- pyautogui would have silently done nothing. It hardcodes keybd_event's
  scancode argument to 0 where the keyboard package passes the real one - read
  out of both libraries' source, then MEASURED through a raw WH_KEYBOARD_LL
  hook: press_key('f13') delivers scanCode=100, pyautogui.press('f13')
  delivers scanCode=0. A game reading the keyboard through DirectInput or Raw
  Input looks at the scancode, so pyautogui's zero arrives empty and the game
  does nothing, with no error anywhere to say why. This is the keyboard-side
  twin of the v0.004 mouse finding, and the pattern is now written down in
  actions.py: the convenient call from an input library sends something, raises
  nothing, and is silently ignored by the one program it was aimed at.

TESTING: 34 new synthetic assertions, no game required - test_potions.py (new,
27) and test_game_state.py (+7 for the Smoother cap). The guard was verified
against the real Diablo II window with 21 assertions, and confirmed working in
live play by the project owner.

NOT YET VALIDATED: every threshold in POTION_RULES is a starting point guessed
at playstyle, not a measurement. F6 snoozes potion drinking for 10s and

Version 0.011 - 2026-08-30
------------------------------------------------------------------------------
Bug fix, reported from live gameplay the same day v0.010 shipped, and exactly
the kind v0.010 made dangerous: an unreadable HUD meter reported 0% instead of
"cannot read", so "I cannot see it" arrived at the potion layer as "you are
about to die".

SYMPTOM. Health and mana both read 0% in two states where nothing is wrong:
sitting in the game lobby, where the HUD does not exist at all, and with the
in-game menu open (Options / Save and Exit), which dims the whole screen. The
menu screenshot shows Life 1131/1228 and Mana 372/372 - both effectively full -
while the pipeline reported 0% for each. 0% health is the emergency tier's
trigger, so this is a potion belt emptied at full life.

ROOT CAUSE. game_state.py's _fill_fraction() had TWO separate "return 0.0"
branches and neither was a measurement:
  - no filled rows found at all                        -> 0.0 "meter is empty"
  - filled rows found, but no coherent liquid surface  -> 0.0
Neither conclusion is available from the evidence. "No liquid visible" is
exactly what an ABSENT meter looks like through a colour mask, and exactly what
a DIMMED one looks like: the configured hsv_ranges floor is V >= 40, and
measured on the real menu screenshot the orb region's mean V was 34 (max 123),
so the mask went patchy. Per-row on that same screenshot, 74 of 147 rows still
passed ROW_FILL_RATIO - scattered rather than stacked - which cleared the first
branch and fell into the second. The lobby screenshot hit the first branch
instead (mana matched 0.00% of its region).

The second branch's own comment already said what it meant - "the same test
rejects stray colour matches floating above an empty meter... since those have
almost nothing filled beneath them" - and then returned 0.0 anyway. The code
knew the answer was "this is not the meter" and reported it as "the meter is
empty". This module's entire contract is that None and 0.0 are different
answers; this was the one place that broke its own rule, in the function every
reading passes through.

FIX. Both branches return None.

NOTHING WAS TRADED FOR IT, which is what makes this a fix rather than a
tradeoff: a MEASURED reading can never be exactly 0.0 anyway. The surface row is
at most the last row of the band, so the smallest value the measuring path can
return is 1/height - about 0.7% on a 150px orb, verified across synthetic fills
from 0.5% to 100%. Every 0.0 the system had ever produced came from one of these
two branches, never from a measurement. The only behavioural change is that an
orb below ~1% now reads "unknown" instead of "empty", and a potion is not what
saves you at 1% health. A real 5% orb still reads 5% and still triggers the
emergency tier - now an explicit test.

VERIFIED against both real screenshots: all four readings went 0% -> None, and
_potion_due() returns nothing for either state. The debug panel shows "no read"
rather than 0%. In the in-game menu the reading is now None rather than the true
~92%, which is correct - the game is paused and "do not act" is the right answer.

- 10 new assertions in test_game_state.py: an absent meter, a meter dimmed to
  50/35/20%, scattered colour with no coherent surface, and - the other
  direction - real 5%/10%/20% orbs that must still read a number, because low
  health has to stay actionable.
- Two existing assertions changed to match the corrected semantics (a 0.0-fill
  orb, and a blue detector pointed at a red orb, now both expect None).
- Error_history.txt #40.
- assets/zelScreenshots/ added to .gitignore: screenshots dropped in for session
  context are multi-megabyte and the folder only grows, so they stay out of git
  history. Anything worth keeping from one belongs in Error_history.txt as
  measured numbers, which is what happened here.

LESSON, recorded because the shape of it generalises well beyond this bug: a
sentinel that is also a legitimate value will eventually be returned from an
error path, and it will look like data. The tell here was a return statement
whose COMMENT asserted something the function could not support - "the meter is
empty" is a claim about the world, from code that had only observed an absence
of evidence. Note also the direction: the failure value happened to be the most
alarming number in the domain, so an unreadable sensor read as maximum urgency.
Where a sensor's failure has to collapse into a number at all, it must fail
toward "do nothing", never toward "act immediately".
