Hunter's Eye - Update Log
=========================

Versioning: starts at 0.001, incrementing by 0.001 for each significant update,
working toward 1.000 ("Hunter's Eye complete" - see the long-term vision in
CLAUDE.md, which is a long way off on purpose). Each version below has a
matching git tag (v0.001, v0.002, ...) pointing at the exact commit for that
state. To get back to a known-working point after something breaks, check out
that tag rather than guessing from commit history - that's what these are for.

------------------------------------------------------------------------------
Version 0.001 - 2026-08-27
------------------------------------------------------------------------------
First tagged checkpoint. Took the project from a rough Diablo II prototype to
a working, documented, cross-platform-minded detection engine:

- Docs & project setup: added CLAUDE.md (architecture + long-term product
  vision), requirements.txt, a portfolio-ready README, and a source-available
  license (PolyForm Strict) suited to a future commercial product.
- Cleanup: merged two main.py files into one, renamed version1/ -> legacy/,
  organized assets into folders, added .gitignore.
- Fixed an OpenCV 5 compatibility break (cv.groupRectangles was removed from
  OpenCV's Python bindings; replaced with NMS-based match merging) and a
  backwards result-limiting slice bug.
- Added OCR-based item-name detection (text_detection.py + assets/items.txt)
  so new items can be watched for by adding a line of text, not a new
  reference image - built to scale to hundreds of item names at no extra
  per-frame cost.
- Performance pass: profiled every stage of the pipeline, cut matchTemplate
  cost via a tuned capture scale, and moved OCR onto its own thread so it can
  no longer stall the fast detection loop. Took real-gameplay FPS from ~11 to
  ~40+.
- Replaced the debug window with a real transparent, click-through overlay
  (overlay.py) drawn directly over the game, fixing two subtle Win32 bugs
  along the way (the window rendering solid black, and clicks not passing
  through to the game) - both verified with actual on-screen testing, not
  just code review.
- Confirmed end-to-end on real gameplay: the overlay correctly boxes
  "Full Rejuvenation Potion" text over the live game, with the character
  still fully controllable through the overlay.

Version 0.002 - 2026-08-27
------------------------------------------------------------------------------
Focused entirely on making OCR item tracking usable during real, active
gameplay instead of only while standing still - a mix of visual fit and a
multi-round performance investigation, each step verified against the real
game rather than assumed:

- assets/items.txt renamed to assets/targets.txt (matches the code's own
  target_items/load_target_items naming); added FLAWLESS RUBY as a second
  watched item.
- Label boxes now padded to match the game's semi-transparent background
  panel instead of hugging just the OCR'd text glyphs.
- Fixed OCR item-tracking during movement, in three rounds once each fix
  proved insufficient on real gameplay:
  1. Widened the local re-localization search window and shortened the OCR
     refresh interval.
  2. Found the interval was now BELOW a single OCR call's own cost, making
     the throttle a no-op (confirmed via a loop-rate diagnostic); fixed the
     interval, and made tracking refresh its own reference patch every
     frame instead of comparing against an increasingly stale one.
  3. Found - via real gameplay logging - that OCR's returned position is
     already stale by the OCR call's own duration (~150-300ms at the time),
     not just "since the last loop tick"; fixed by immediately re-localizing
     against a fresh frame right after every OCR call instead of waiting for
     the next loop iteration.
- Cut real OCR latency significantly: measured actual OCR cost against real
  gameplay (~0.9s/call - far higher than earlier synthetic-benchmark
  assumptions of ~150-300ms), then cropped OCR to the gameplay viewport
  (excluding HUD margins where item labels never render anyway), cutting it
  to ~0.42s/call - over 2x - for free. This let the OCR refresh interval
  drop further, roughly halving worst-case discovery latency for brand-new
  items on top of the per-call speedup. An MSER-based smarter-sounding
  alternative was tried and measured first, then rejected when its own
  overhead turned out to eat most of its benefit - see Error_history.txt.
- Result: item discovery and tracking now hold up well during continuous
  movement and direction changes, not just while standing still - confirmed
  via real gameplay testing, not just code review.
- Found and fixed one more discovery-latency bug after user-reported real
  gameplay felt like a ~3-second delay: the OCR refresh interval was timed
  from when the previous call FINISHED, not when it started, silently
  stacking the call's own ~0.5s duration onto the intended 0.7s interval
  (~1.2s real gap instead of 0.7s). Confirmed via a live scan-to-scan-gap
  diagnostic before and after the fix. Real-gameplay hotkey behavior (Alt
  held continuously, not pressed on-demand) and a "does combat complexity
  spike OCR cost" hypothesis were both checked and ruled out as explanations
  - see Error_history.txt for both. User-confirmed after the fix: perceived
  delay dropped from "like 3 seconds" to "more like 0.5 seconds."

Version 0.003 - 2026-08-27
------------------------------------------------------------------------------
Pushed OCR speed further after user still wanted more than v0.002 delivered.
Considered and measured two alternative approaches before picking one:

- Considered switching text detection from OCR to template-matching known
  target strings (like the image-matching path already does for icons).
  Measured first: at OCR's native resolution, a single matchTemplate call
  costs ~21ms, so 20 templates/frame (~424ms) already matches OCR's old
  cost, and 80 templates/frame (~40 items with color-rarity variants) costs
  ~1.7s - over 3x slower than OCR. Rejected: OCR's cost is constant
  regardless of vocabulary size, template matching's grows linearly - the
  wrong trade for a system meant to scale to dozens/hundreds of items.
- Added tesserocr as the primary OCR backend (text_detection.py), talking to
  the Tesseract engine in-process instead of pytesseract's subprocess-per-
  call model, with automatic fallback to pytesseract if unavailable. No
  official Windows wheel exists (source build failed, needs a full C++
  toolchain - see Error_history.txt); used a well-established prebuilt-wheel
  project instead, no compiler needed. Measured ~3.5-4.5x faster against
  real gameplay (~0.1-0.26s vs ~0.42-0.6s per OCR call).
- Retuned OCR_INTERVAL_SECONDS down to 0.4 (from 0.7) now that a call costs
  far less, cutting worst-case new-item discovery latency further to ~0.6s.
- Verified live against real gameplay: zero lost-track events across a full
  test with substantial on-screen movement, FPS unaffected (~41).
- Changed the console FPS line to print once every 5 seconds (average over
  just that window) instead of every single frame, which was flooding the
  console at ~40 lines/second.

Version 0.004 - 2026-08-28
------------------------------------------------------------------------------
Added auto-collect: the first concrete use of the "action" seam described in
CLAUDE.md (move mouse / press key / click), which had only existed as a
future-plans note until now. Most of this version is a multi-round accuracy
investigation once real gameplay testing showed the first version wasn't
good enough - see Error_history.txt #16-#18 for the full root-cause detail
behind each round below.

- assets/targets.txt: a trailing "*" on an item name now marks it "to
  collect" - auto-collect moves the mouse to it and clicks until it's picked
  up or 5 seconds pass with it still on the ground, at which point it backs
  off and hands mouse control back rather than clicking forever.
- actions.py (new): a generic, game-agnostic click_until_gone() - knows
  nothing about item names or OCR, just clicks wherever a caller's position
  callback reports until that callback returns None or a timeout elapses.
  main.py's new run_auto_collect() thread is the D2R-specific glue that feeds
  it OCR-tracked positions.
- Hotkeys changed: quit moved from 'q' to 'End', and a new 'F4' snoozes
  auto-collect for 10 seconds (then re-arms itself automatically - not a
  plain on/off toggle, so it can't be accidentally left disabled). Both are
  global hotkeys via the `keyboard` package, same as before; 'q' was
  replaced because it's an ordinary letter pressed constantly during real
  gameplay.
- Fixed a false-positive bug in the fuzzy OCR matcher: short target names
  (2-3 letter Diablo II rune names like "Lo", "Um", "Ko") could match
  unrelated on-screen noise under the same fixed 0.75 similarity cutoff that
  works fine for long names - because difflib's ratio math makes short
  strings far more sensitive to a single shared letter. Now the required
  cutoff scales with target name length (effectively exact-match at length
  <= 3). This matters more than it otherwise would now that a match can
  trigger a real mouse click, not just a wrong overlay box.
- Fixed unstable detection boxes for short names: matching was done against
  Tesseract's whole recognized line, but Tesseract doesn't consistently
  decide whether e.g. a rune's name and the word "Rune" next to/below it
  belong on the same line between OCR passes - so the box (and therefore
  where auto-collect clicked) changed size depending on what else got swept
  onto the line that pass. Matching now tries every contiguous word-run
  within a line and boxes only the words that actually matched.
- Auto-collect click accuracy, fixed in stages after each proved
  insufficient on real gameplay (character moving during detection kept
  making clicks land where the item used to be, then clicks landing
  correctly but not registering, then registering but "rushed"):
  1. Replaced separate moveTo()+click() calls with one click(x, y) call,
     removing a ~0.1s gap (pyautogui's own default PAUSE) between the
     cursor arriving and the click actually firing.
  2. Slowed the actual click-retry cadence from every 0.15s to every 0.8s
     (while still polling every 0.1s for fast success detection) - D2R
     treats a click on an item as "walk over and pick it up on arrival," so
     clicking much faster than that walk takes kept re-issuing the move
     command and retargeting the character before it ever arrived.
  3. Replaced pyautogui.click() with manual mouseDown()/sleep/mouseUp():
     click() sends the press and release combined into one Windows
     mouse_event() call with zero time held, which some games' per-frame
     input polling can miss entirely even with the cursor in the right
     spot.
  4. Split the move and the press apart with their own settle delay too
     (not just press-then-release) - mouseDown(x, y) moved the cursor and
     pressed in the same call, risking the game resolving the click against
     where the cursor was a frame earlier.
- Reduced unnecessary overlay redraws (overlay.py's draw_rectangles() now
  skips repainting when the rectangles haven't changed since last frame) -
  an attempted fix for a reported mouse-cursor flicker; plausible root cause
  identified (this always-on-top layered window was being repainted every
  frame regardless of whether anything visible changed) but not separately
  re-confirmed by the user after the fact.
- Gated the OCR loop-rate/scan-gap/call-time diagnostic prints added in
  v0.002-0.003 behind a new OCR_DEBUG_TIMING flag (default off) - useful for
  re-tuning OCR_INTERVAL_SECONDS later, but too noisy to leave on by default
  once auto-collect added its own console output.
- User-confirmed after all of the above: click accuracy issue resolved.

Version 0.005 - 2026-08-28
------------------------------------------------------------------------------
Added per-item detection box colors, with a design discussion up front about
which targets.txt convention would be least error-prone before writing any
code:

- assets/targets.txt: an optional trailing "[colorname]" tag (e.g.
  "[purple]", "[darkorange]") sets an item's box color; omitted or
  misspelled falls back to the same green used before this feature existed,
  with a load-time warning on a misspelling rather than a silent wrong
  color or a crash. Considered and rejected a single-letter code (the
  user's original "[o]"/"[p]" idea) and a category-indirection scheme
  (define a color once, tag many items with a category name) in favor of
  this simpler per-item tag once the user clarified they wanted color set
  per item, not shared across a category.
- text_detection.py: new NAMED_COLORS palette (green, red, blue, yellow,
  cyan, purple, orange, darkorange, pink, gold, white) and DEFAULT_BOX_COLOR
  (green, unchanged). Deliberately excludes magenta/fuchsia - overlay.py's
  click-through mechanism depends on one exact color being invisible, and a
  box in that exact color would silently vanish.
- Colored FULL REJUVENATION POTION purple and all 15 runes dark orange in
  targets.txt, per the user's request.
- Threaded color end-to-end through the whole detection pipeline
  (find_text_matches -> shared_text_tracks -> detect_objects's rectangle
  merge -> detection_queue -> both run_overlay and the run_debug_window
  fallback) as an (r, g, b) tuple, converted to hex for Tk and reversed to
  BGR for OpenCV at each renderer's own call site - verified with a
  simulation script threading fake tracks through every stage before
  relying on live testing.
- Image-template matches (the icon-matching path, unrelated to targets.txt)
  keep using DEFAULT_BOX_COLOR - the color tag only applies to OCR matches.
- Found and fixed a documentation gap while touching CLAUDE.md for this:
  the auto-collect thread and actions.py added in v0.004 were never
  actually documented in the Architecture section (only referenced in
  passing from other sections) - added proper subsections for both.
