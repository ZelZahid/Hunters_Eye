Hunter's Eye - Error History
=============================

Log of significant bugs hit during development, their root cause, and the fix -
kept so the same mistake doesn't get repeated (or re-diagnosed from scratch,
burning time/tokens) later. Listed chronologically. See updates.txt for the
version/changelog this all landed in (v0.001).

------------------------------------------------------------------------------
1. AttributeError: module 'cv2' has no attribute 'groupRectangles'
------------------------------------------------------------------------------
Where: main.py, detect_objects()
Cause: OpenCV 5.0 removed cv.groupRectangles from its Python bindings (legacy
  API tied to the old HOG/cascade detectors). Code written against OpenCV 4.x
  assumptions broke on the OpenCV 5.x actually installed (opencv-python 5.0.0.93).
Fix: Replaced with cv.dnn.NMSBoxes (standard, actively-maintained non-max
  suppression) - collapses overlapping matches using their real match
  confidence scores instead of raw rectangle-overlap counts.
Lesson: Don't assume an OpenCV tutorial/example's API surface matches whatever
  version is actually installed - check cv2.__version__ and be ready for
  legacy functions to be gone in v5.

------------------------------------------------------------------------------
2. Result-limiting slice was backwards (silent logic bug, not a crash)
------------------------------------------------------------------------------
Where: main.py, detect_objects() (found while fixing #1)
Cause: `rectangles = rectangles[max_results:]` was written to "keep only the
  top max_results" but actually DROPS the first max_results entries and keeps
  everything after - the opposite of the intent.
Fix: Changed to `rectangles[:max_results]`.
Lesson: Slice-based truncation bugs are easy to get backwards and easy to miss
  since both versions "run fine" - only the wrong items get kept. Worth a
  second look any time a slice is used to "limit to N".

------------------------------------------------------------------------------
3. pytesseract per-region OCR calls collapsed FPS from ~15 to ~0.6
------------------------------------------------------------------------------
Where: text_detection.py (early MSER-based version)
Cause: pytesseract launches a brand-new tesseract.exe subprocess on EVERY
  call (~120-150ms fixed cost, independent of image size). Calling it once
  per candidate text region (up to 12/frame) multiplied that fixed cost into
  a 10-20x FPS hit.
Fix: Rewrote to make exactly ONE Tesseract call per frame, over the whole
  image, using pytesseract.image_to_data() and grouping its per-word output
  back into lines - instead of pre-cropping N regions and OCR'ing each.
Lesson: For any external-subprocess-backed API (OCR, CLI tools wrapped in
  Python, etc.), profile whether cost is dominated by call overhead or by
  work size BEFORE assuming "smaller inputs = faster." Batch calls when the
  overhead is the bottleneck.

------------------------------------------------------------------------------
4. OCR still stalled the fast image-matching loop even when throttled
------------------------------------------------------------------------------
Where: main.py, detect_objects() (early throttled version)
Cause: OCR ran inline in the same thread as image matching, gated to every
  Nth frame - but on the Nth frame it still blocked that thread for its full
  ~150ms cost, capping overall FPS well below what image matching alone
  could do.
Fix: Moved OCR onto its own thread (detect_text()) that only *publishes*
  results (shared_text_tracks, behind a lock) - the fast image-matching
  thread reads whatever's latest and never waits on OCR. Took the pipeline
  from ~25 FPS to ~44-46 FPS with OCR active either way.
Lesson: Throttling an expensive call's frequency doesn't fix the stall it
  causes on the frame it DOES run - if that stall is unacceptable, the call
  needs to be decoupled onto its own thread, not just made less frequent.

------------------------------------------------------------------------------
5. Unguarded Tesseract-missing / Tesseract-error paths could crash the thread
------------------------------------------------------------------------------
Where: text_detection.py
Cause: (a) If Tesseract isn't installed at all, every OCR call throws
  TesseractNotFoundError. (b) Even installed, the Windows Tesseract 5.4.0
  build intermittently throws a spurious TesseractError ("ObjectCache leak"
  warning during its own internal cleanup, unrelated to whether OCR actually
  succeeded) - confirmed happening roughly once per 15-20 calls in testing.
  Neither was originally guarded, so either would kill the detect_text thread.
Fix: (a) Check pytesseract.get_tesseract_version() once at import time; if it
  fails, print one warning and make find_text_matches() a no-op instead of
  letting every call throw. (b) Wrap each OCR call in try/except
  TesseractError - log and skip that scan, don't crash.
Lesson: Any call into an external, unversioned, non-Python-controlled binary
  should be treated as unreliable by default - check availability once, and
  wrap every individual call, not just the "is it installed" check.

------------------------------------------------------------------------------
6. Dropping CAPTURE_SCALE for speed silently broke OCR accuracy
------------------------------------------------------------------------------
Where: main.py (CAPTURE_SCALE 0.5 -> 0.3) + text_detection.py
Cause: CAPTURE_SCALE was lowered specifically to speed up cv.matchTemplate
  for icon matching. detect_text() was reading that SAME downscaled frame for
  OCR - and at 0.3x, in-game text on a 1280x800 screen shrinks to only a few
  pixels tall, well below what Tesseract can read. Result: OCR stopped
  finding anything, with no error at all (just silently no matches).
Fix: Gave detect_text() its own independent mss capture loop at a much
  higher, separate resolution (OCR_CAPTURE_SCALE = 1.0), and convert its
  match coordinates back into CAPTURE_SCALE space before publishing them.
Lesson: Different detectors can have fundamentally different resolution
  needs (template matching tolerates small/blurry input; OCR does not).
  Sharing one downscaled frame across detector types is a trap - a change
  tuned for one detector's speed can silently break another's correctness,
  with no exception to point at the cause. Worth re-checking every consumer
  of a shared frame/resolution constant before changing it.

------------------------------------------------------------------------------
7. Transparent overlay rendered as solid black
------------------------------------------------------------------------------
Where: overlay.py, Overlay.__init__
Cause: Tk's "-transparentcolor" attribute sets up the window's Win32 layered
  colorkey transparency internally. Immediately after, calling
  win32gui.SetWindowLong to add WS_EX_TRANSPARENT reset that transparency
  data, because Tk has no idea the window was modified behind its back.
  Windows' fallback for a layered window with invalid transparency data is
  to render it solid black - which blanketed the whole monitor.
Fix: Re-assert the colorkey explicitly right after the SetWindowLong call,
  via win32gui.SetLayeredWindowAttributes(hwnd, colorkey, 0, LWA_COLORKEY).
Lesson: Mixing a high-level toolkit's (Tk's) internal window-state management
  with manual low-level (Win32) style changes is fragile - any manual style
  change can silently invalidate state the toolkit set up, with no error,
  only wrong visual output. Re-verify/re-apply toolkit-managed state after
  any manual Win32 call on the same window.

------------------------------------------------------------------------------
8. Transparent overlay looked correct but clicks didn't pass through
------------------------------------------------------------------------------
Where: overlay.py, Overlay.__init__ (found immediately after fixing #7)
Cause: Two compounding issues. (a) root.winfo_id() can return an inner Tk
  drawing-surface window handle, not the actual outer OS-level frame that
  Windows uses for hit-testing/click-routing - styling the wrong (child)
  window does nothing, silently. (b) Even targeting the right HWND,
  SetWindowLong alone doesn't reliably make Windows re-evaluate hit-testing
  for a newly-added style bit.
Fix: (a) Walk up to the real frame via win32gui.GetParent(hwnd) before
  applying styles. (b) Force Windows to re-evaluate by calling
  win32gui.SetWindowPos(hwnd, ..., SWP_FRAMECHANGED) right after
  SetWindowLong.
Verification: Visual screenshot inspection could NOT have caught this - the
  overlay looks identical whether clicks pass through or not. Built an
  isolated test instead: a plain Tk window with a click-counting button, on
  a monitor away from the live game, with the overlay on top; simulated a
  real click via pyautogui at its exact screen coordinates and confirmed via
  a status file + before/after screenshot that the click reached the button
  underneath.
Lesson: For click-through / input-routing bugs specifically, visual
  correctness and input correctness are independent properties governed by
  different Win32 mechanisms - test both explicitly, don't infer one from
  the other. A real interactive test (even a scripted/simulated one) is
  sometimes the only way to actually verify a fix.

9. git commit failed: "Author identity unknown"
------------------------------------------------------------------------------
Where: local machine, first commit attempt this project
Cause: git user.name/user.email were never configured on this machine.
Fix: Had the user run `git config user.name "..."` and
  `git config user.email "..."` themselves (Claude Code is not permitted to
  modify git config directly, even on request).
Lesson: Not a code bug - an environment-setup gap. Worth checking
  `git config user.name/user.email` early on a fresh machine before
  assuming a commit will succeed.

10. winget install hung / failed on an interactive prompt
------------------------------------------------------------------------------
Where: installing the Tesseract OCR engine via winget
Cause: `winget install UB-Mannheim.TesseractOCR` triggered an interactive
  "do you agree to the msstore source terms?" Y/N prompt, which can't receive
  input through a non-interactive shell pipe - it errored out
  (0x8a150042 : Error reading input in prompt).
Fix: Re-ran with `--accept-source-agreements --accept-package-agreements`
  flags to answer the prompt non-interactively up front.
Lesson: winget commands run from a non-interactive context should default to
  including both accept flags rather than hitting the prompt and retrying.

------------------------------------------------------------------------------
11. __pycache__ almost got committed to the repo
------------------------------------------------------------------------------
Where: repo root, after running `python -m py_compile` for syntax checks
Cause: There was no .gitignore yet, so running compile checks (which create
  __pycache__/*.pyc) left artifacts that `git add -A` swept up alongside
  real changes. Caught via reviewing `git status` before committing, not
  automatically.
Fix: Added a .gitignore covering __pycache__/, *.pyc, and venv/.venv/ early,
  and made a habit of `rm -rf __pycache__` before staging after any test run.
Lesson: Always add .gitignore near the start of a project, before the first
  round of local testing - not after noticing compiled artifacts in
  `git status`.

12. OCR item-label tracking couldn't keep up with real character movement
------------------------------------------------------------------------------
Where: main.py, detect_text() / _relocalize_track()
Cause: Two compounding issues, found via a loop-rate diagnostic added to
  detect_text() rather than by guessing:
  (a) OCR_INTERVAL_SECONDS was set to 0.3, but a single Tesseract OCR call
  itself costs ~150-300ms - ABOVE that interval. So the "wait between calls"
  throttle did nothing in practice: by the time one OCR call finished, the
  interval had usually already elapsed, so OCR ran back-to-back on nearly
  every loop iteration. Measured effect: the loop dropped to ~6-9 Hz (should
  be ~20-70 Hz depending on system load), leaving almost no time for the
  cheap, fast relocalization step that's supposed to keep the box glued to a
  moving target.
  (b) Separately, _relocalize_track() always matched against the ORIGINAL
  patch captured at the last full OCR refresh, never updating it. Fine while
  standing still (nothing nearby changes), but real gameplay has dynamic
  content near labels (flickering torches, animated water/grass, other
  moving characters) - the longer a reference patch goes unrefreshed, the
  more the live scene has drifted from it, degrading match confidence.
  Together: the box worked fine standing still (matched the "only works
  when standing still" symptom exactly) and lagged/lost the target the
  moment the camera panned.
Fix: (a) Raised OCR_INTERVAL_SECONDS to 1.5 - well above a single OCR call's
  own cost, leaving real room for many fast relocalization passes between
  refreshes. (b) Changed _relocalize_track() to re-crop the patch from the
  CURRENT frame at the newly-found position after every successful match,
  so the reference is always at most one loop iteration stale, not up to
  OCR_INTERVAL_SECONDS stale.
Lesson: When throttling an expensive periodic call, always check the
  interval against the call's OWN duration, not just against "what feels
  like a reasonable number." An interval near or below the call's cost
  doesn't throttle anything - it just serializes the expensive call onto
  every loop iteration. When a "smart tracker" reuses a reference captured
  once, ask whether anything nearby is expected to change over time even
  without motion (animation, lighting, particles) - if so, refresh the
  reference, don't assume a stale snapshot stays valid. And when a fix
  doesn't work, add a cheap diagnostic (a loop-rate print, in this case)
  before guessing at a third parameter tweak - it turned "still doesn't
  work" into an exact, measurable root cause in one round trip.

Follow-up (still #12, same investigation): (a) and (b) above weren't enough -
  user report: "slightly better moving straight, even worse changing
  direction." Real-gameplay logging (TRACK LOST prints added per-track) showed
  the ACTUAL cause: relocalization was failing on almost the very FIRST
  attempt after every OCR refresh, at very low confidence (0.08-0.30 - a
  genuine miss, not a near-threshold one). Root cause: a single OCR call
  itself takes ~150-300ms, so the position it returns describes where the
  item was BEFORE that call started - by the time the first relocalization
  check runs, the real position has already moved by the OCR call's full
  duration PLUS a loop iteration, not just one iteration's worth as
  previously assumed. Fix: immediately grab one more fresh frame right after
  OCR completes and relocalize against THAT before publishing the position,
  instead of leaving the OCR-time position stale until the next loop
  iteration. Also raised TRACK_SEARCH_MARGIN 150 -> 250 for headroom on the
  steady-state (non-OCR) gap. Re-tested live: TRACK LOST events dropped from
  nearly every refresh cycle to ~3 in a full test run with heavy movement.
  Lesson (sharper version of the one above): when a periodic expensive call
  reports a result, that result describes the PAST, aged by the call's own
  duration - if anything downstream treats it as "current," measure the
  call's duration and account for it explicitly (here: one extra catch-up
  frame), don't just assume the caller's next scheduled step will catch up
  naturally.

13. Discovery latency for NEW items was assumed to be ~150-300ms; it was ~0.9s
------------------------------------------------------------------------------
Where: text_detection.py find_text_matches(), main.py OCR_INTERVAL_SECONDS
Cause: All earlier OCR timing assumptions (~150-300ms/call) came from a
  synthetic benchmark - a mostly-blank test image with two short lines of
  text. Measured directly against real, busy gameplay: a single full-frame
  (1920x1080) OCR call actually cost ~0.9s. Tesseract's sparse-text-mode
  segmentation cost scales with visual complexity, not just pixel count, so
  a cluttered real game screen is far more expensive to analyze than a quiet
  synthetic one. This meant OCR_INTERVAL_SECONDS=1.5 (tuned around the wrong,
  much lower, assumed cost) left far less headroom than it looked like, and
  capped how fast a brand-new item (one not already being tracked) could
  ever be discovered - bounded by the interval, not by anything relocalize
  could help with.
Investigation: tried (and rejected, after measuring) an MSER-based
  candidate-region pre-filter to crop OCR down to just where text-like
  content is. Measured cost of MSER itself against real gameplay: ~240ms -
  not free. Worse, the combined bounding box of all its candidates covered
  99% of the frame, because unrelated UI chrome (health/mana numbers, clock,
  inventory) is scattered at the very top and bottom edges of the screen,
  forcing the box wide regardless. Net: MSER's own cost ate most of the
  benefit of a smaller crop. Rejected in favor of something simpler.
Fix: Permanently crop OCR calls to a fixed "gameplay viewport" - excluding a
  top margin (game clock/info) and a larger bottom margin (health/mana
  orbs, inventory bar) - via VIEWPORT_TOP_MARGIN/VIEWPORT_BOTTOM_MARGIN in
  main.py. Item labels never render inside HUD chrome anyway (the world
  isn't visible there), so nothing is lost by excluding it, and it costs
  nothing extra (a slice, not a detection pass). Measured effect: ~0.9s ->
  ~0.42s per OCR call, over 2x. This let OCR_INTERVAL_SECONDS drop from 1.5
  to 0.7 safely (still well above the new call cost), roughly halving
  worst-case new-item discovery latency on top of the per-call speedup.
Lesson: Don't tune timing constants against an assumed or synthetically-
  benchmarked cost when the real workload is available to measure directly -
  a "close enough" assumption (150-300ms vs the real ~900ms) can be off by
  3-6x and quietly caps what's achievable elsewhere (here: discovery
  latency) without any error or crash to point at. Also: a smarter-sounding
  optimization (candidate pre-filtering) isn't automatically better than a
  dumber one (a fixed crop) - measure both against the real workload before
  committing to the more complex one, since its own overhead can eat the
  benefit it was supposed to provide.

14. OCR_INTERVAL_SECONDS was timed from call completion, not call start
------------------------------------------------------------------------------
Where: main.py detect_text()
Cause: `last_ocr_time = time.time()` was set AFTER the OCR call finished, not
  before it started. Since the interval check is `time.time() - last_ocr_time
  >= OCR_INTERVAL_SECONDS`, this meant the real gap between successive scans
  was actually (interval + the previous call's own duration), not just the
  interval as intended - e.g. with a 0.7s interval and a ~0.5s call, the real
  cadence was ~1.2s, not 0.7s. User report ("takes like 3 seconds") was
  higher than this bug alone explains, but a live diagnostic ("[scan-to-scan
  gap: ...]", timing actual successive scan starts) confirmed the real gap
  was ~1.2s before the fix and ~0.7s after - matching the interval exactly.
  A separate hypothesis (OCR cost spiking during actual combat/drop moments
  due to higher visual complexity) was tested and NOT confirmed - real
  combat-moment OCR calls measured 0.42-0.63s, the same range as calm-moment
  testing, not meaningfully higher.
Fix: Move the `last_ocr_time = time.time()` timestamp to the START of the
  OCR call instead of after it completes, so the interval can elapse WHILE
  the call is running - the next scan fires right after the current one
  finishes instead of waiting a full interval again on top of it.
Lesson: When a periodic action's "next run" timestamp is set after the
  action completes rather than when it starts, the action's own duration
  silently stacks onto the intended interval every cycle. This is easy to
  miss by inspection (both versions "look right" in isolation) - a live
  diagnostic that measures the actual real-world gap between occurrences
  (not just log each occurrence) is what caught it. Also worth remembering:
  a plausible-sounding hypothesis (combat complexity spiking OCR cost) can
  be wrong even when it fits the symptom - measure before treating a guess
  as the explanation.
