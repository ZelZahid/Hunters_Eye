Hunter's Eye - Error History
=============================

Log of significant bugs hit during development, their root cause, and the fix -
kept so the same mistake doesn't get repeated (or re-diagnosed from scratch,
burning time/tokens) later. Listed chronologically. See updates.txt for the
version/changelog this all landed in (v0.001).

------------------------------------------------------------------------------
1. AttributeError: module 'cv2' has no attribute 'groupRectangles'
------------------------------------------------------------------------------
Where: main.py, detect_objects()
Cause: OpenCV 5.0 removed cv.groupRectangles from its Python bindings (legacy
  API tied to the old HOG/cascade detectors). Code written against OpenCV 4.x
  assumptions broke on the OpenCV 5.x actually installed (opencv-python 5.0.0.93).
Fix: Replaced with cv.dnn.NMSBoxes (standard, actively-maintained non-max
  suppression) - collapses overlapping matches using their real match
  confidence scores instead of raw rectangle-overlap counts.
Lesson: Don't assume an OpenCV tutorial/example's API surface matches whatever
  version is actually installed - check cv2.__version__ and be ready for
  legacy functions to be gone in v5.

------------------------------------------------------------------------------
2. Result-limiting slice was backwards (silent logic bug, not a crash)
------------------------------------------------------------------------------
Where: main.py, detect_objects() (found while fixing #1)
Cause: `rectangles = rectangles[max_results:]` was written to "keep only the
  top max_results" but actually DROPS the first max_results entries and keeps
  everything after - the opposite of the intent.
Fix: Changed to `rectangles[:max_results]`.
Lesson: Slice-based truncation bugs are easy to get backwards and easy to miss
  since both versions "run fine" - only the wrong items get kept. Worth a
  second look any time a slice is used to "limit to N".

------------------------------------------------------------------------------
3. pytesseract per-region OCR calls collapsed FPS from ~15 to ~0.6
------------------------------------------------------------------------------
Where: text_detection.py (early MSER-based version)
Cause: pytesseract launches a brand-new tesseract.exe subprocess on EVERY
  call (~120-150ms fixed cost, independent of image size). Calling it once
  per candidate text region (up to 12/frame) multiplied that fixed cost into
  a 10-20x FPS hit.
Fix: Rewrote to make exactly ONE Tesseract call per frame, over the whole
  image, using pytesseract.image_to_data() and grouping its per-word output
  back into lines - instead of pre-cropping N regions and OCR'ing each.
Lesson: For any external-subprocess-backed API (OCR, CLI tools wrapped in
  Python, etc.), profile whether cost is dominated by call overhead or by
  work size BEFORE assuming "smaller inputs = faster." Batch calls when the
  overhead is the bottleneck.

------------------------------------------------------------------------------
4. OCR still stalled the fast image-matching loop even when throttled
------------------------------------------------------------------------------
Where: main.py, detect_objects() (early throttled version)
Cause: OCR ran inline in the same thread as image matching, gated to every
  Nth frame - but on the Nth frame it still blocked that thread for its full
  ~150ms cost, capping overall FPS well below what image matching alone
  could do.
Fix: Moved OCR onto its own thread (detect_text()) that only *publishes*
  results (shared_text_tracks, behind a lock) - the fast image-matching
  thread reads whatever's latest and never waits on OCR. Took the pipeline
  from ~25 FPS to ~44-46 FPS with OCR active either way.
Lesson: Throttling an expensive call's frequency doesn't fix the stall it
  causes on the frame it DOES run - if that stall is unacceptable, the call
  needs to be decoupled onto its own thread, not just made less frequent.

------------------------------------------------------------------------------
5. Unguarded Tesseract-missing / Tesseract-error paths could crash the thread
------------------------------------------------------------------------------
Where: text_detection.py
Cause: (a) If Tesseract isn't installed at all, every OCR call throws
  TesseractNotFoundError. (b) Even installed, the Windows Tesseract 5.4.0
  build intermittently throws a spurious TesseractError ("ObjectCache leak"
  warning during its own internal cleanup, unrelated to whether OCR actually
  succeeded) - confirmed happening roughly once per 15-20 calls in testing.
  Neither was originally guarded, so either would kill the detect_text thread.
Fix: (a) Check pytesseract.get_tesseract_version() once at import time; if it
  fails, print one warning and make find_text_matches() a no-op instead of
  letting every call throw. (b) Wrap each OCR call in try/except
  TesseractError - log and skip that scan, don't crash.
Lesson: Any call into an external, unversioned, non-Python-controlled binary
  should be treated as unreliable by default - check availability once, and
  wrap every individual call, not just the "is it installed" check.

------------------------------------------------------------------------------
6. Dropping CAPTURE_SCALE for speed silently broke OCR accuracy
------------------------------------------------------------------------------
Where: main.py (CAPTURE_SCALE 0.5 -> 0.3) + text_detection.py
Cause: CAPTURE_SCALE was lowered specifically to speed up cv.matchTemplate
  for icon matching. detect_text() was reading that SAME downscaled frame for
  OCR - and at 0.3x, in-game text on a 1280x800 screen shrinks to only a few
  pixels tall, well below what Tesseract can read. Result: OCR stopped
  finding anything, with no error at all (just silently no matches).
Fix: Gave detect_text() its own independent mss capture loop at a much
  higher, separate resolution (OCR_CAPTURE_SCALE = 1.0), and convert its
  match coordinates back into CAPTURE_SCALE space before publishing them.
Lesson: Different detectors can have fundamentally different resolution
  needs (template matching tolerates small/blurry input; OCR does not).
  Sharing one downscaled frame across detector types is a trap - a change
  tuned for one detector's speed can silently break another's correctness,
  with no exception to point at the cause. Worth re-checking every consumer
  of a shared frame/resolution constant before changing it.

------------------------------------------------------------------------------
7. Transparent overlay rendered as solid black
------------------------------------------------------------------------------
Where: overlay.py, Overlay.__init__
Cause: Tk's "-transparentcolor" attribute sets up the window's Win32 layered
  colorkey transparency internally. Immediately after, calling
  win32gui.SetWindowLong to add WS_EX_TRANSPARENT reset that transparency
  data, because Tk has no idea the window was modified behind its back.
  Windows' fallback for a layered window with invalid transparency data is
  to render it solid black - which blanketed the whole monitor.
Fix: Re-assert the colorkey explicitly right after the SetWindowLong call,
  via win32gui.SetLayeredWindowAttributes(hwnd, colorkey, 0, LWA_COLORKEY).
Lesson: Mixing a high-level toolkit's (Tk's) internal window-state management
  with manual low-level (Win32) style changes is fragile - any manual style
  change can silently invalidate state the toolkit set up, with no error,
  only wrong visual output. Re-verify/re-apply toolkit-managed state after
  any manual Win32 call on the same window.

------------------------------------------------------------------------------
8. Transparent overlay looked correct but clicks didn't pass through
------------------------------------------------------------------------------
Where: overlay.py, Overlay.__init__ (found immediately after fixing #7)
Cause: Two compounding issues. (a) root.winfo_id() can return an inner Tk
  drawing-surface window handle, not the actual outer OS-level frame that
  Windows uses for hit-testing/click-routing - styling the wrong (child)
  window does nothing, silently. (b) Even targeting the right HWND,
  SetWindowLong alone doesn't reliably make Windows re-evaluate hit-testing
  for a newly-added style bit.
Fix: (a) Walk up to the real frame via win32gui.GetParent(hwnd) before
  applying styles. (b) Force Windows to re-evaluate by calling
  win32gui.SetWindowPos(hwnd, ..., SWP_FRAMECHANGED) right after
  SetWindowLong.
Verification: Visual screenshot inspection could NOT have caught this - the
  overlay looks identical whether clicks pass through or not. Built an
  isolated test instead: a plain Tk window with a click-counting button, on
  a monitor away from the live game, with the overlay on top; simulated a
  real click via pyautogui at its exact screen coordinates and confirmed via
  a status file + before/after screenshot that the click reached the button
  underneath.
Lesson: For click-through / input-routing bugs specifically, visual
  correctness and input correctness are independent properties governed by
  different Win32 mechanisms - test both explicitly, don't infer one from
  the other. A real interactive test (even a scripted/simulated one) is
  sometimes the only way to actually verify a fix.

10. winget install hung / failed on an interactive prompt
------------------------------------------------------------------------------
Where: installing the Tesseract OCR engine via winget
Cause: `winget install UB-Mannheim.TesseractOCR` triggered an interactive
  "do you agree to the msstore source terms?" Y/N prompt, which can't receive
  input through a non-interactive shell pipe - it errored out
  (0x8a150042 : Error reading input in prompt).
Fix: Re-ran with `--accept-source-agreements --accept-package-agreements`
  flags to answer the prompt non-interactively up front.
Lesson: winget commands run from a non-interactive context should default to
  including both accept flags rather than hitting the prompt and retrying.

11. __pycache__ almost got committed to the repo
------------------------------------------------------------------------------
Where: repo root, after running `python -m py_compile` for syntax checks
Cause: There was no .gitignore yet, so running compile checks (which create
  __pycache__/*.pyc) left artifacts that `git add -A` swept up alongside
  real changes. Caught via reviewing `git status` before committing, not
  automatically.
Fix: Added a .gitignore covering __pycache__/, *.pyc, and venv/.venv/ early,
  and made a habit of `rm -rf __pycache__` before staging after any test run.
Lesson: Always add .gitignore near the start of a project, before the first
  round of local testing - not after noticing compiled artifacts in
  `git status`.

12. OCR item-label tracking couldn't keep up with real character movement
------------------------------------------------------------------------------
Where: main.py, detect_text() / _relocalize_track()
Cause: Two compounding issues, found via a loop-rate diagnostic added to
  detect_text() rather than by guessing:
  (a) OCR_INTERVAL_SECONDS was set to 0.3, but a single Tesseract OCR call
  itself costs ~150-300ms - ABOVE that interval. So the "wait between calls"
  throttle did nothing in practice: by the time one OCR call finished, the
  interval had usually already elapsed, so OCR ran back-to-back on nearly
  every loop iteration. Measured effect: the loop dropped to ~6-9 Hz (should
  be ~20-70 Hz depending on system load), leaving almost no time for the
  cheap, fast relocalization step that's supposed to keep the box glued to a
  moving target.
  (b) Separately, _relocalize_track() always matched against the ORIGINAL
  patch captured at the last full OCR refresh, never updating it. Fine while
  standing still (nothing nearby changes), but real gameplay has dynamic
  content near labels (flickering torches, animated water/grass, other
  moving characters) - the longer a reference patch goes unrefreshed, the
  more the live scene has drifted from it, degrading match confidence.
  Together: the box worked fine standing still (matched the "only works
  when standing still" symptom exactly) and lagged/lost the target the
  moment the camera panned.
Fix: (a) Raised OCR_INTERVAL_SECONDS to 1.5 - well above a single OCR call's
  own cost, leaving real room for many fast relocalization passes between
  refreshes. (b) Changed _relocalize_track() to re-crop the patch from the
  CURRENT frame at the newly-found position after every successful match,
  so the reference is always at most one loop iteration stale, not up to
  OCR_INTERVAL_SECONDS stale.
Lesson: When throttling an expensive periodic call, always check the
  interval against the call's OWN duration, not just against "what feels
  like a reasonable number." An interval near or below the call's cost
  doesn't throttle anything - it just serializes the expensive call onto
  every loop iteration. When a "smart tracker" reuses a reference captured
  once, ask whether anything nearby is expected to change over time even
  without motion (animation, lighting, particles) - if so, refresh the
  reference, don't assume a stale snapshot stays valid. And when a fix
  doesn't work, add a cheap diagnostic (a loop-rate print, in this case)
  before guessing at a third parameter tweak - it turned "still doesn't
  work" into an exact, measurable root cause in one round trip.

Follow-up (still #12, same investigation): (a) and (b) above weren't enough -
  user report: "slightly better moving straight, even worse changing
  direction." Real-gameplay logging (TRACK LOST prints added per-track) showed
  the ACTUAL cause: relocalization was failing on almost the very FIRST
  attempt after every OCR refresh, at very low confidence (0.08-0.30 - a
  genuine miss, not a near-threshold one). Root cause: a single OCR call
  itself takes ~150-300ms, so the position it returns describes where the
  item was BEFORE that call started - by the time the first relocalization
  check runs, the real position has already moved by the OCR call's full
  duration PLUS a loop iteration, not just one iteration's worth as
  previously assumed. Fix: immediately grab one more fresh frame right after
  OCR completes and relocalize against THAT before publishing the position,
  instead of leaving the OCR-time position stale until the next loop
  iteration. Also raised TRACK_SEARCH_MARGIN 150 -> 250 for headroom on the
  steady-state (non-OCR) gap. Re-tested live: TRACK LOST events dropped from
  nearly every refresh cycle to ~3 in a full test run with heavy movement.
  Lesson (sharper version of the one above): when a periodic expensive call
  reports a result, that result describes the PAST, aged by the call's own
  duration - if anything downstream treats it as "current," measure the
  call's duration and account for it explicitly (here: one extra catch-up
  frame), don't just assume the caller's next scheduled step will catch up
  naturally.

13. Discovery latency for NEW items was assumed to be ~150-300ms; it was ~0.9s
------------------------------------------------------------------------------
Where: text_detection.py find_text_matches(), main.py OCR_INTERVAL_SECONDS
Cause: All earlier OCR timing assumptions (~150-300ms/call) came from a
  synthetic benchmark - a mostly-blank test image with two short lines of
  text. Measured directly against real, busy gameplay: a single full-frame
  (1920x1080) OCR call actually cost ~0.9s. Tesseract's sparse-text-mode
  segmentation cost scales with visual complexity, not just pixel count, so
  a cluttered real game screen is far more expensive to analyze than a quiet
  synthetic one. This meant OCR_INTERVAL_SECONDS=1.5 (tuned around the wrong,
  much lower, assumed cost) left far less headroom than it looked like, and
  capped how fast a brand-new item (one not already being tracked) could
  ever be discovered - bounded by the interval, not by anything relocalize
  could help with.
Investigation: tried (and rejected, after measuring) an MSER-based
  candidate-region pre-filter to crop OCR down to just where text-like
  content is. Measured cost of MSER itself against real gameplay: ~240ms -
  not free. Worse, the combined bounding box of all its candidates covered
  99% of the frame, because unrelated UI chrome (health/mana numbers, clock,
  inventory) is scattered at the very top and bottom edges of the screen,
  forcing the box wide regardless. Net: MSER's own cost ate most of the
  benefit of a smaller crop. Rejected in favor of something simpler.
Fix: Permanently crop OCR calls to a fixed "gameplay viewport" - excluding a
  top margin (game clock/info) and a larger bottom margin (health/mana
  orbs, inventory bar) - via VIEWPORT_TOP_MARGIN/VIEWPORT_BOTTOM_MARGIN in
  main.py. Item labels never render inside HUD chrome anyway (the world
  isn't visible there), so nothing is lost by excluding it, and it costs
  nothing extra (a slice, not a detection pass). Measured effect: ~0.9s ->
  ~0.42s per OCR call, over 2x. This let OCR_INTERVAL_SECONDS drop from 1.5
  to 0.7 safely (still well above the new call cost), roughly halving
  worst-case new-item discovery latency on top of the per-call speedup.
Lesson: Don't tune timing constants against an assumed or synthetically-
  benchmarked cost when the real workload is available to measure directly -
  a "close enough" assumption (150-300ms vs the real ~900ms) can be off by
  3-6x and quietly caps what's achievable elsewhere (here: discovery
  latency) without any error or crash to point at. Also: a smarter-sounding
  optimization (candidate pre-filtering) isn't automatically better than a
  dumber one (a fixed crop) - measure both against the real workload before
  committing to the more complex one, since its own overhead can eat the
  benefit it was supposed to provide.

14. OCR_INTERVAL_SECONDS was timed from call completion, not call start
------------------------------------------------------------------------------
Where: main.py detect_text()
Cause: `last_ocr_time = time.time()` was set AFTER the OCR call finished, not
  before it started. Since the interval check is `time.time() - last_ocr_time
  >= OCR_INTERVAL_SECONDS`, this meant the real gap between successive scans
  was actually (interval + the previous call's own duration), not just the
  interval as intended - e.g. with a 0.7s interval and a ~0.5s call, the real
  cadence was ~1.2s, not 0.7s. User report ("takes like 3 seconds") was
  higher than this bug alone explains, but a live diagnostic ("[scan-to-scan
  gap: ...]", timing actual successive scan starts) confirmed the real gap
  was ~1.2s before the fix and ~0.7s after - matching the interval exactly.
  A separate hypothesis (OCR cost spiking during actual combat/drop moments
  due to higher visual complexity) was tested and NOT confirmed - real
  combat-moment OCR calls measured 0.42-0.63s, the same range as calm-moment
  testing, not meaningfully higher.
Fix: Move the `last_ocr_time = time.time()` timestamp to the START of the
  OCR call instead of after it completes, so the interval can elapse WHILE
  the call is running - the next scan fires right after the current one
  finishes instead of waiting a full interval again on top of it.
Lesson: When a periodic action's "next run" timestamp is set after the
  action completes rather than when it starts, the action's own duration
  silently stacks onto the intended interval every cycle. This is easy to
  miss by inspection (both versions "look right" in isolation) - a live
  diagnostic that measures the actual real-world gap between occurrences
  (not just log each occurrence) is what caught it. Also worth remembering:
  a plausible-sounding hypothesis (combat complexity spiking OCR cost) can
  be wrong even when it fits the symptom - measure before treating a guess
  as the explanation.

15. tesserocr wouldn't build from source; a prebuilt wheel fixed it
------------------------------------------------------------------------------
Where: environment setup, adding tesserocr as a faster OCR backend
Cause: `python -m pip install tesserocr` failed with `RuntimeError: Tesseract
  library not found in LIBPATH: []`. tesserocr has no PyPI wheel for Windows -
  only a source distribution, which needs Tesseract's C++ development library
  and headers (not just the `tesseract.exe` runtime binary already installed)
  plus a C++ compiler to build against them. Installing a full build toolchain
  (Visual Studio Build Tools + Tesseract dev libraries via something like
  vcpkg) just to get one package building was considered disproportionate
  effort for uncertain payoff.
Fix: Used a prebuilt wheel from a well-established third-party build instead:
  github.com/simonflueckiger/tesserocr-windows_build/releases - it bundles
  Tesseract + Leptonica as DLLs directly in the wheel, so no separate compiler
  or dev libraries are needed at all. It covers current Python versions
  including very new ones (a cp314-win_amd64 wheel already existed the same
  day Python 3.14 was current). Installed directly via
  `pip install <release-asset-url>.whl`. Still needed to separately point it
  at the existing Tesseract installation's tessdata folder (the wheel doesn't
  bundle language data) via `PyTessBaseAPI(path=...)`.
Lesson: A package failing to build from source on Windows doesn't mean it's
  unusable - check for a well-established prebuilt-wheel project before
  assuming a full compiler/dev-library toolchain install is required. This
  is common for Python packages wrapping C/C++ libraries on Windows
  specifically, since Windows has no standard system package manager most
  such libraries assume (unlike apt/brew on Linux/macOS).

16. Short target names (2-3 letter runes) false-matched unrelated OCR noise
------------------------------------------------------------------------------
Where: text_detection.py find_text_matches()
Cause: User added ~15 short Diablo II rune names (Lo, Um, Ko, ...) to
  targets.txt, all marked "*" for auto-collect. The existing fuzzy matcher
  used one fixed cutoff (0.75, via difflib.get_close_matches) for every
  target regardless of length. difflib's ratio is 2*matched/(lenA+lenB) - for
  a 25-character name like "FULL REJUVENATION POTION" one stray mismatched
  letter barely moves the ratio, so 0.75 works well; for a 2-3 letter name, a
  single shared letter with ANY unrelated short OCR misread (stray HUD text,
  chat, icons) can already clear 0.75. Confirmed via a standalone script
  testing candidate strings ("LOL", "SOL", "GOLD", "HUM", etc.) against the
  cutoff logic before and after the fix. Because these items were all
  auto-collect targets, a false match didn't just draw a wrong box - it moved
  the mouse and clicked.
Fix: Added _required_cutoff(item_length, base_cutoff), scaling the required
  cutoff up as the target name gets shorter - effectively exact-match at
  length <= 3, 0.9 at length <= 6, the base cutoff above that. Not
  difflib.get_close_matches() any more since it only accepts one cutoff for
  every candidate; matching is now a manual per-target-name loop instead.
Lesson: A similarity threshold tuned against long strings can be far too
  loose for short ones, since the same ratio formula behaves very
  differently at different string lengths - check short edge cases
  separately rather than assuming one cutoff generalizes. This matters more
  than usual whenever a fuzzy match result drives a real-world action
  (here: a mouse click) rather than just a label.

17. OCR detection box (and auto-collect's click point) changed size between
    passes for the same physical item
------------------------------------------------------------------------------
Where: text_detection.py, _group_words_into_lines() (now _group_words_by_line
  + _padded_box)
Cause: Matching (and the returned bounding box) was based on Tesseract's
  WHOLE recognized line, joining every word Tesseract grouped into that
  line/paragraph. Tesseract's own line-grouping isn't consistent between OCR
  passes for the same on-screen content - e.g. a rune's name and the word
  "Rune" rendered next to/below it sometimes landed on the same line,
  sometimes on separate lines. This compounded with #16's fix: a line OCR'd
  as "GUL RUNE" would never exact-match target "GUL" at all (ratio ~0.545,
  well under the required 1.0), so detection only worked on the passes where
  Tesseract happened to isolate the rune name by itself - and even then, the
  box's width/height (hence its center, hence where auto-collect clicked)
  varied depending on what else got swept onto that line that particular
  pass. User-reported symptom: "the size of the boxes constantly changing."
Fix: Rewrote matching to try every contiguous word-run within a line (single
  word, first two words, etc.) against every target name, and box only the
  words in the best-scoring run - not the whole line. Verified with a
  standalone script simulating both groupings ("Gul"+"Rune" merged onto one
  line vs. split across two): match result and box came out byte-identical
  either way, confirming the box no longer depends on Tesseract's
  inconsistent line assignment.
Lesson: When an OCR/text pipeline groups recognized words into larger units
  (lines, paragraphs) before matching, don't assume that grouping is stable
  frame-to-frame just because it usually looks reasonable - test whether the
  match (and any geometry derived from it) survives the grouping coming out
  differently for the same physical content. This one also compounded with
  an unrelated recent fix (#16) in a way that wasn't obvious until traced
  through by hand: the exact-match rule that fixed false positives on short
  names also depended on this grouping being minimal.

18. Auto-collect clicks didn't reliably land on / pick up the item
------------------------------------------------------------------------------
Where: actions.py click_until_gone(), main.py run_auto_collect()
Cause: Four compounding issues, found in sequence as each fix proved
  insufficient against real gameplay - each confirmed by reading pyautogui's
  actual source rather than guessing at its behavior:
  (a) click_until_gone() called pyautogui.moveTo() then pyautogui.click() as
  two separate calls. Both are decorated to sleep pyautogui's own PAUSE
  (default 0.1s) after they run, before returning - so moveTo() didn't
  return, and click() didn't fire, until ~0.1s after the cursor arrived.
  During that gap, if the character/camera was moving, the item's on-screen
  position had already drifted out from under the now-stationary cursor.
  User-reported symptom: "very inaccurate... character is moving while the
  detection is happening."
  (b) After (a), clicks landed accurately but items still weren't reliably
  picked up. D2R (like many games) treats a click on an item as "walk over
  and pick it up on arrival," not an instant action - but clicks were being
  re-issued every 0.15s, far faster than a walk-to-item takes, so each new
  click kept re-issuing the move command and retargeting the character
  before it ever completed the walk to the previous click.
  (c) After (b), user reported clicks now looked accurate (cursor visibly
  on the item) but still weren't registering as a pickup at all. Read
  pyautogui's Windows backend (_pyautogui_win.py) directly: click() sends
  MOUSEEVENTF_LEFTCLICK, which IS MOUSEEVENTF_LEFTDOWN | MOUSEEVENTF_LEFTUP
  combined into one single mouse_event() call - button down and up in the
  same instant, zero time held. A game polling input state once per frame
  can miss a press/release pair that lands within the same instant entirely.
  (d) After (c) (manual mouseDown(x,y)+sleep+mouseUp()), user reported the
  click still "seemed rushed... not waiting for the mouse to get to the
  location, then click." mouseDown(x, y) repositions the cursor AND presses
  the button in the same call with nothing separating them - the game could
  receive "cursor moved" and "button down" in the same input instant and
  resolve the click against where the cursor was a frame earlier.
Fix: (a) One click(x, y) call instead of moveTo()+click() (later superseded
  by (d)). (b) Separated "how often to check if the item is gone" (fast
  poll, stayed at ~0.1s) from "how often to actually click" (slowed to
  0.8s) in click_until_gone(). (c) Replaced click() with manual
  mouseDown()/time.sleep(CLICK_HOLD_SECONDS)/mouseUp(), holding the button
  down for a real, deliberate duration (0.05s) instead of an instantaneous
  combined event. (d) Split the move and the press into two separate steps
  with their own settle delay (MOVE_SETTLE_SECONDS, 0.05s) between them,
  instead of moving and pressing in the same call. All pyautogui calls pass
  _pause=False explicitly so the only delays present are the two
  intentional ones, not an incidental side effect of pyautogui's own
  default post-call pause.
Lesson: A physical input action (mouse click, key press) synthesized via an
  automation library can fail for reasons that have nothing to do with
  screen-space accuracy - timing gaps between move/press/release, and
  whether an event is held long enough for the target application's own
  input polling to observe it, are separate failure modes from "did the
  cursor end up in the right place." When an automation call behaves
  unexpectedly, read the library's actual platform-specific implementation
  (here: _pyautogui_win.py's use of a combined MOUSEEVENTF_LEFTCLICK flag)
  rather than assuming its high-level API name ("click") maps onto what a
  real human physical click does at the OS event level. Also worth noting
  generally: user-reported symptoms arrived one layer at a time (position
  accuracy, then registration, then timing) precisely because each fix
  removed the dominant error source and exposed the next smaller one
  underneath it - a "still broken" report after a real fix often means a
  different, smaller bug, not that the fix didn't work.

19. Meter fill percentage read badly wrong when a highlight crossed the liquid
------------------------------------------------------------------------------
Where: game_state.py, _fill_fraction() (caught by synthetic testing during
  development, before this ever ran against the real game)
Cause: The first implementation found the liquid surface by walking up from the
  bottom of the orb and stopping at the first run of non-matching rows, with a
  small tolerance (MAX_SURFACE_GAP_ROWS = 3) for the rippling surface. Games
  draw a bright specular highlight streak across a globe, and where that streak
  crosses the liquid it blanks out a run of rows wider than the tolerance. The
  walk stopped dead at the streak and reported the STREAK's height as the fill
  level: a 65%-full orb read as 25%. Widening the tolerance only moves the
  failure, because the streak's thickness in rows is not a fixed number - it
  depends on resolution, the streak's angle, and where it crosses the globe.
Fix: Replaced the local walk with a global consistency test - the surface is the
  highest row that is itself filled AND has at least SURFACE_CONSISTENCY (0.7)
  of the rows below it filled as well. A blocked run of rows in the middle of
  the liquid barely moves that ratio, so the streak stops mattering. Requiring
  the surface row itself to be filled keeps the answer pinned to a real row of
  liquid rather than drifting up into the empty space above it, and the same
  test independently fixed a second failure mode that was in the original
  design's comments as a known weakness: a stray patch of the meter's own color
  floating above an empty meter (a spell effect, or a badly-tuned hsv_range
  catching nearby UI art) used to inflate the reading, and now fails the
  ratio test because almost nothing is filled beneath it.
Lesson: Two lessons, one specific and one general. Specific: a local scan that
  stops at the first anomaly is fragile against rendering artifacts drawn OVER
  the thing being measured; a global test that weighs all the evidence below a
  candidate is both simpler and far more robust, and it cost nothing in speed
  (it is two numpy cumulative sums). General: this was found only because the
  synthetic test deliberately included an adversarial case - noise plus a gloss
  streak - rather than only clean, ideal inputs. A test that just renders a
  perfect orb passes against both the broken and the fixed implementation. Also
  worth noting the direction of the error: it under-reported health, which
  would have triggered emergency behaviour at full health, and the mirror-image
  case (a streak above the liquid) would have MISSED a real emergency. Any
  reading that will drive an automatic action deserves an adversarial test
  before it drives anything.

20. A pixel-count fill measurement is exactly right at 50% and wrong everywhere
    else (design trap, avoided rather than hit)
------------------------------------------------------------------------------
Where: game_state.py, _fill_fraction() - recorded because the obvious
  implementation is the wrong one and someone will reach for it again later
Cause: The natural way to measure "how full is this orb" is to count matching
  pixels and divide by the orb's total pixels. That measures AREA, but a game
  fills a globe by HEIGHT, and for a circle the two are only equal at 0%, 50%
  and 100%. A circle filled to 25% of its height is 19.5% full by area - the
  bottom of a circle is narrow, so those rows hold fewer pixels than average.
Fix: Measure the height of the liquid surface directly via a row scan and never
  convert through area at all (this is why game_state.py scans rows instead of
  doing the much shorter mask.sum() / total.sum()). Verified numerically: the
  synthetic test measures 19.7% by pixel count against the analytic 19.5%,
  confirming the row scan's 24.6% is the correct answer and the pixel count is
  the wrong one.
Lesson: A wrong measurement that happens to be exactly right at the midpoint is
  a genuinely nasty bug, because casual testing at "about half health" confirms
  it works. The error grows precisely as the value approaches its extremes -
  which for a health orb means it is least accurate exactly when the reading
  matters most. When measuring a fill level, check what shape the container is
  and what the game is actually varying (height, angle, area), and test at the
  extremes, not just in the middle.

21. Auto-collect clicked on unlisted runes: any "<X> Rune" matched every other
    "<Y> Rune" in targets.txt
------------------------------------------------------------------------------
Where: text_detection.py, find_text_matches() / _required_cutoff()
Symptom: A "Ral Rune" (not in targets.txt at all) dropped, and the program boxed
  it and auto-collected it - reported once as "Jah Rune" and once as "Lem Rune".
  It looked like "the program matches anything containing the word Rune", and
  that reading was essentially correct.
Cause: Matching used one whole-string difflib ratio against a 0.75 cutoff.
  difflib's ratio is 2*matched/(lenA+lenB), so a word shared by many target
  names counts toward every one of them. Measured: "RAL RUNE" scores exactly
  0.75 against "JAH RUNE", "LEM RUNE" and "GUL RUNE" - the shared " RUNE" is 5
  of the 8 characters and clears the cutoff by itself, regardless of the other
  word. The same flaw had targets in the list cross-matching each other:
  "KO RUNE" vs "LO RUNE" = 0.857, "OHM RUNE" vs "LO RUNE" = 0.80.
  _required_cutoff() was written to prevent exactly this and did nothing here,
  because it scaled off len(name) and every name in targets.txt is "Lo Rune"
  (7 chars), not "Lo" (2). The generic suffix pushed every rune out of the
  strict short-name bracket and into the loose one. Note this made the guard
  useless precisely BECAUSE the names were written the way the game shows them,
  which is what targets.txt tells the user to do.
Fix: Match word by word (new _match_ratio()) instead of over the whole string;
  every word of the target name must clear its own length-scaled cutoff, so the
  3-letter word that actually identifies the item can no longer ride in on the
  generic one. _required_cutoff() now takes a word rather than a whole name, so
  its existing ladder (exact at <= 3, 0.9 at <= 6, base above) finally applies
  to the part that carries the identity. Differing word counts fall back to a
  space-stripped whole-string compare at the strictest of the name's per-word
  cutoffs, so Tesseract merging or splitting a word ("JAHRUNE") doesn't lose a
  real detection. Verified: all eight low runes now match nothing, every listed
  target still matches, and the pass is 5.9ms vs 6.4ms before - slightly FASTER,
  because a failed 3-letter word compare short-circuits before the full-string
  SequenceMatcher is ever built.
Lesson: Two lessons. Specific: a whole-string similarity score is the wrong tool
  when the candidates share a common word - the score is dominated by the part
  that carries no information, and no cutoff can recover what the metric threw
  away ("RAL RUNE" and "JAH RUNE" really are 75% identical; the fact that the
  DIFFERING word is the identifying one is only visible word by word). Compare
  at the granularity where the meaning lives. General: a guard that is written
  against the right threat can still be wired to the wrong input and silently
  never fire. _required_cutoff()'s docstring named "Lo", "Um", "Ko" exactly -
  the threat model was right, but it was fed len("LO RUNE") instead of len("LO")
  and so returned the loose cutoff every single time. When a defensive check
  never seems to trigger, check what it is actually measuring before trusting
  that the case just hasn't come up.

22. Overlay panel text rendered pink instead of grey (color-key transparency +
    subpixel font antialiasing)
------------------------------------------------------------------------------
Where: overlay.py, draw_panel() / _panel_text() - found during development of
  the game-state debug panel, before it ever shipped
Symptom: Panel labels asked for a neutral grey (220,220,220) and rendered as
  saturated pink/magenta on screen. The colored value text (green/amber/red)
  looked roughly right, which made it look like a color-constant typo in the
  greys specifically.
Cause: Not a wrong constant - measuring the actual rendered pixels showed the
  glyph CORES were exactly (220,220,220) and (170,170,170) as requested, but
  the mean lit pixel was (204,140,201). The overlay's transparency is a color
  KEY, not real alpha: every pixel is either exactly TRANSPARENT_COLOR
  (#ff00ff) and fully invisible, or fully opaque. Windows' subpixel font
  smoothing therefore antialiased the text against MAGENTA, and on thin 11px
  bold glyphs the fringe pixels outnumber the core pixels, so the fringe color
  is what the eye actually sees. The brighter/more saturated value text
  survived better only because its core color is further from magenta.
Fix: Draw a solid dark backing plate behind the panel first (Tk canvas draws in
  insertion order), so the text antialiases against dark instead of magenta. A
  black 1px text shadow was tried first and was not enough - it outlines the
  glyph but does not change what the glyph itself blends into. Accepted the
  tradeoff that the plate is opaque over the game, since the panel is a debug
  surface with an 'F5' toggle. Detection boxes deliberately keep no backing:
  a 2px rectangle outline does not antialias the same way, and covering the
  game exactly where an item is lying would defeat their purpose.
  Because the plate is the first fully opaque thing this overlay has ever
  drawn, click-through was re-verified specifically over it (button-under-the-
  overlay harness, clicked via pyautogui): WS_EX_TRANSPARENT applies to the
  whole window regardless of pixel opacity - confirmed, not assumed.
Lesson: Two lessons. Specific: on a color-key layered window, ANY antialiased
  content blends toward the key color, so text needs something opaque behind it
  or it picks up the key's hue - a trap that will recur for any future text on
  this overlay. General: "the color constant must be wrong" was the obvious
  diagnosis and it was wrong. Measuring the rendered pixels (core color vs mean
  color) took one command and pointed straight at antialiasing instead, because
  the two hypotheses predict different things: a bad constant makes the cores
  wrong, while a blending problem leaves the cores exactly right. When a color
  renders wrong, check whether the CORE is wrong before assuming the value is.

23. Per-word exact matching killed nearly all item detection against the real
    game font (regression introduced by the fix for #21)
------------------------------------------------------------------------------
Where: text_detection.py, _required_cutoff() / _match_ratio()
Symptom: After fixing #21, runes and Full Rejuvenation Potions stopped being
  detected almost entirely. Two rounds of loosening the cutoff didn't fix it,
  which was itself the clue: the problem was not the cutoff VALUE.
Cause: #21's fix required every word of a target name to clear its own cutoff,
  with words of 3 or fewer characters needing an EXACT match. That reasoning was
  sound but rested on an unexamined assumption: that Tesseract reads the text
  correctly, so an exact match is achievable. It isn't. Diablo II renders item
  labels in a stylized Exocet-derived display face, and Tesseract is trained on
  conventional print fonts, so a systematic one-character misread is the NORMAL
  case: "GUL"->"GU1", "BER"->"8ER", "VEX"->"V3X". The old whole-string cutoff
  had been absorbing all of this invisibly, because the shared " RUNE" suffix
  contributed 5 of 8 characters and carried a misread name over 0.75 - the very
  same property that caused bug #21. So #21 and #23 are the same mechanism seen
  from opposite sides: the suffix was simultaneously hiding real misreads (good)
  and admitting wrong items (bad). Removing it fixed one and broke the other.
  The project owner suggested the font as the cause, which was correct and was
  what turned this from threshold-guessing into a diagnosis.
Fix: Two mechanisms that only work as a pair. (a) Tolerance: a 3-letter word may
  now differ by one character (0.65); 2-letter and shorter must still be exact.
  (b) Completeness: targets.txt gained a leading "-" ("ignore") marker - matched
  normally, then discarded - and all 16 unlisted low runes were added with it.
  A correctly-read "Ral Rune" now scores 1.000 against its own entry, beating
  the 0.875 it scores against "Mal Rune", and is then dropped. Tolerance alone
  would re-admit #21; completeness alone would still miss every misread rune.
  Verified across four groups: 10 font-style misreads of collectibles now
  detected, all 16 low runes still not clicked, misread LOW runes still resolve
  to a low rune rather than stealing a collectible, and unrelated screen text
  ("Antidote Potion", "Scroll of Town Portal", "Healing Potion") still matches
  nothing. Also added diagnose_ocr.py, because this took three attempts purely
  from not knowing what Tesseract actually read off a real frame.
Lesson: Three. (1) When two successive threshold adjustments both fail to fix a
  detection problem, stop adjusting the threshold - the model of the input is
  wrong, not the number. (2) Synthetic test strings encode the same assumption
  the code does. Every test string used to validate #21 was spelled correctly,
  so the tests agreed with the bug; only the real font disproved it. Test data
  for a recognition system must come from the recognizer, not from the author.
  (3) A fuzzy matcher always returns the closest LISTED name, so an incomplete
  vocabulary silently misattributes rather than reporting nothing - which means
  completeness of the target list is a correctness property, not a convenience.

24. The real cause of "it stopped detecting": Tesseract was never reading the
    labels at all (raw game frames are not OCR-able input)
------------------------------------------------------------------------------
Where: text_detection.py, find_text_matches() - no preprocessing before the
  OCR call. This had been true since the module was written; entries #21 and
  #23 were both chasing symptoms of it.
Symptom: Items plainly visible on screen were not detected. Two successive
  matching-cutoff changes (#21's fix, then #23's) failed to fix it. That double
  failure was the real clue and it was not acted on soon enough.
Cause: Tesseract expects a scanned page - dark text on a light background, no
  texture. A game frame is the opposite: thin bright glyphs over dark, noisy,
  high-detail art. Ground truth came from diagnose_ocr.py, which saves the
  actual captured viewport: a frame containing FIVE plainly legible rune labels
  (Amn, Sol, Fal, Ko, Gul) produced ZERO of them from Tesseract, along with 57
  junk "words" scraped off the terrain texture. Every matching-cutoff theory
  was therefore operating on lines that never existed. No cutoff can rescue a
  line that was never read.
Fix: Binarize before the OCR call - threshold at BRIGHT_TEXT_THRESHOLD (150),
  then invert so it looks like dark-on-light. Same frame: 4 of the 5 labels now
  read. It is also much FASTER, which is not the usual direction for an accuracy
  fix - Tesseract's cost scales with how much candidate text it believes it can
  see, and thresholding deletes the texture that was generating all the false
  candidates: 362ms -> 51ms, 83 words -> 7; a full find_text_matches() call
  374ms -> 67ms. Kept general rather than hardcoded, per the detector-
  independence rule: three modes with PREPROCESS_AUTO choosing per frame from
  its median brightness, verified on a white document, a light-grey document, a
  dark terminal and a black game screen - auto picks correctly on all four.
  Never rescales, so box coordinates need no translation.
  A second frame (two potions on the ground) then exposed a follow-on: with OCR
  suddenly working, the small "Rejuvenation Potion" was read correctly for the
  first time and scored 0.900 against "Full Rejuvenation Potion", so it got
  auto-collected. Fixed with a look-alike entry, the same mechanism as #23.
Lesson: Four. (1) When two successive threshold adjustments both fail, the
  model of the INPUT is wrong, not the number - stop tuning and go look at the
  input. (2) Verify the pipeline stage-by-stage from the front. Everything from
  #21 onward assumed OCR output existed and only the matching of it was in
  question; one look at what Tesseract actually returned would have ended it
  immediately. (3) Save the real intermediate artifact. The whole thing turned
  on diagnose_ocr.py writing the captured viewport to disk, which made "five
  labels, zero read" visible in seconds after days of inference. (4) Fixing a
  recognition stage makes DOWNSTREAM matching stricter-needing, not looser -
  better OCR surfaced a false positive that bad OCR had been accidentally
  hiding, so recheck the next stage after improving the previous one.

25. difflib's ratio is the wrong similarity metric for short OCR words - it
    counts matching characters without regard to WHERE they are
------------------------------------------------------------------------------
Where: text_detection.py, _word_ratio() (new) - found immediately after #24,
  once preprocessing made Tesseract actually read the labels
Symptom: With OCR finally working, a frame containing six readable labels still
  lost one: "Ko Rune" was read by Tesseract as "Ke RUNE" and reported nothing.
Cause: difflib.SequenceMatcher's ratio is 2*M/(lenA+lenB) where M counts
  characters in common as an order-preserving subsequence. On a 2-letter word
  that is almost no information: "KE" scores 0.5 against "KO" (a real
  one-character misread, sharing the K in position 0) AND 0.5 against "EL"
  (sharing only an E, in a different position, and otherwise unrelated). The
  two tie, so the newly-added ambiguity check - correctly refusing to guess
  between equally-scoring targets - discarded the line. Note the ambiguity
  check was not the bug; it was doing exactly its job on a metric that was
  feeding it a false tie.
Fix: _word_ratio() compares equal-length words of <= 3 characters position by
  position instead ("KO" 0.5, "EL" 0.0), and keeps difflib for everything
  longer. Verified on the real frame: all four collectibles (Ko, Fal, Gul, Full
  Rejuvenation Potion) now detected, both look-alikes (small Rejuvenation
  Potion, Hel Rune) still suppressed.
Lesson: Match the similarity metric to the error process that actually
  generates the differences. OCR SUBSTITUTES a glyph in place; it does not
  transpose or shift characters. difflib's subsequence matching is designed for
  edits that move text around (diffs, patches), so applied to a misread glyph
  it discards position - the single most informative thing about a substitution
  - and on a 2-3 character word position is nearly all the information there
  is. The generic string-similarity function being right there in the standard
  library is not evidence that it models your errors. Longer words are a
  different regime and legitimately keep difflib, because a dropped or doubled
  letter really does shift everything after it.

26. calibrate_meters.py appeared to do nothing - its window opened behind the
    game and was never visible
------------------------------------------------------------------------------
Where: calibrate_meters.py, calibrate() and preview()
Symptom: "I don't see a box or anything when I run calibrate_meters.py."
  Reported alongside a reasonable but wrong guess that main.py had to be running
  first - the tool is standalone, and running both together would in fact be
  harmful, since main.py's always-on-top overlay would be captured INTO the
  screenshot being calibrated against.
Cause: The tool's flow is "switch to the game, wait out a countdown, then
  interact with a window". By the time cv.selectROI() creates its window, the
  GAME is the foreground application, so a normally-created OpenCV window opens
  behind it. Nothing errors; the program just sits there blocking on input for
  a window the user cannot see.
Fix: _show_window() creates each window with cv.namedWindow() and immediately
  sets cv.WND_PROP_TOPMOST, plus one waitKey(1) so it actually paints before
  selectROI blocks. Verified by screenshotting the desktop with the window up
  and counting its distinctive background pixels (82k visible = rendering in
  front), not by assuming the property took effect. Also print, before the
  countdown, that a window will open on top afterwards and that exclusive-
  fullscreen has to be switched to Windowed/Borderless since nothing can draw
  over it.
Lesson: Any tool that deliberately sends the user to another application and
  then wants attention back has this problem, and it presents as "the program
  does nothing" rather than as an error. Worth remembering for diagnose_ocr.py
  and anything else countdown-driven added later. More generally: a blocking
  call waiting on an invisible window is indistinguishable from a hang.

27. Calibrator and pipeline captured DIFFERENT screen regions, so every meter
    region would have pointed at the wrong part of the screen
------------------------------------------------------------------------------
Where: calibrate_meters.py grab_screen() vs main.py monitor_area
Symptom: Noticed by the project owner as a usability complaint - "the window
  used to select the orb captured all 3 monitors" - and asked whether it even
  mattered. It mattered a great deal; the cosmetic symptom was hiding a
  correctness bug that had not been hit yet only because no config had ever
  been written.
Cause: grab_screen() used sct.monitors[0], which in mss means the whole VIRTUAL
  desktop across every monitor (here left=-1920, width=5760). main.py's
  monitor_area is built from pyautogui.size() and covers only the PRIMARY
  monitor (left=0, width=1920). A meter's region is stored as FRACTIONS of the
  captured frame specifically so it survives any capture scale - but that only
  holds if both sides agree what frame the fractions are OF. An orb at x=500 on
  the primary screen sits at pixel 2420 within the virtual-desktop capture
  (because that capture starts at -1920), giving fraction 0.420; main.py would
  then apply 0.420 to a 1920-wide frame and measure at x=806 - a completely
  different part of the screen. Nothing raises: game_state returns a
  plausible-but-wrong percentage or None. The comment on that very line claimed
  "the whole virtual screen, matching main.py's monitor_area", so the code
  documented the invariant it was breaking.
Fix: calibrate_meters.py now imports main.monitor_area and captures exactly
  that, so the two cannot drift. Verified: calibrator now reports 1920x1080,
  identical to main.py. Side benefit - the selection window no longer squeezes
  5760px into a 1500px-wide display, so the orb is drawn at 0.78 scale instead
  of 0.26 and is roughly 3x easier to box accurately.
Lesson: This is Error_history #6 again (shared capture-resolution constants
  drifting) in a new place, which is itself the lesson: when correctness
  depends on two components agreeing about a value, they must SHARE it, not
  each derive it. Note the contrast with --fast-scale in this same tool, which
  is deliberately a duplicated argument rather than an import - that is correct
  precisely because correctness does NOT depend on it (it only affects a
  displayed validation number). "Import it" and "pass it explicitly" are both
  right answers; which one applies depends on whether a mismatch can produce a
  wrong ANSWER or merely a wrong DISPLAY. Also: a stale comment asserting an
  invariant is worse than no comment, because it stops the next reader looking.

28. Health orb read 87% at full and 0% after the slightest damage - the

------------------------------------------------------------------------------
Where: calibrate_meters.py - the hand-drawn selection box, used as-is
Symptom: Reported as "mana seems somewhat accurate, but health is inaccurate -

Cause: NOT the damage, and not game_state's measurement. The box drawn around

  scene is visible behind. That artwork is ANIMATED (torchlight, the statues,

  inside the health ellipse was H 0-179, S 0-255 - i.e. every colour on the

  inaccurate while health was pure noise.

  synthetically from 100% down to 10% in software. The user's region returned
  0.0% at EVERY level including 100%; a region tightened to the orb returned
  100.0 / 99.3 / 96.7 / 91.4 / 76.2 / 51.0 / 25.8 / 10.6%. Two captures minutes
  apart of the same full orb read 87% and then 0%, with nothing but the
  background art having changed.

  can", since the fit depends on it. Verified on synthetic orbs: full orb fits
  within 3-5px of truth, 40%-full orb fits short AND fires the warning, no orb
  returns None.
Lesson: Three. (1) When a measurement is noisy rather than merely offset, ask

  simulating the failure on real captured pixels (draining the orb in
  software), which took one script and settled in seconds a question that
  eyeballing percentages could not - the reading being wrong at 100% fill was
  the tell that it was never tracking health at all.

29. A single word off an unlisted item matched a listed one - "Flawless" from
    "Flawless Diamond" was reported as "Flawless Ruby"
------------------------------------------------------------------------------
Where: text_detection.py, _match_ratio()'s differing-word-count fallback
Symptom: A Flawless Diamond on the ground produced a detection box around just
  the word "Flawless", reported as the listed Flawless Ruby. Note "FLAWLESS
  DIAMOND" as a whole correctly did NOT match - the per-word path rejected it
  ("DIAMOND" vs "RUBY" scores 0.0). The match came from somewhere else.
Cause: find_text_matches() tries every contiguous RUN of words on a line, so
  the one-word window ["FLAWLESS"] is tested on its own. Against the two-word
  "FLAWLESS RUBY" the word counts differ, which routes it to the space-stripped
  fallback: "FLAWLESS" vs "FLAWLESSRUBY" = 0.8, clearing the 0.75 floor. That
  fallback exists for OCR merges and splits ("JAHRUNE", "REJUVEN ATION"), where
  every character is still present and only the spacing moved. A strict prefix
  is a different thing entirely - an entire word is missing - and was being
  forgiven as though it were a spacing artifact.
Fix: MERGED_WORD_CUTOFF = 0.9 as a floor on that path, making it STRICTER than
  the per-word path rather than looser. A genuine merge/split scores near 1.0
  so nothing legitimate is lost: verified JAHRUNE, GULRUNE, KORUNE,
  FLAWLESSRUBY and FULLREJUVENATIONPOTION all still match, while FLAWLESS,
  FLAWLESS DIAMOND/EMERALD/SAPPHIRE/SKULL, and the bare words FULL, POTION,
  RUNE, GUL and JAH all now match nothing.
Lesson: A fallback path taken when the primary check cannot be applied should
  be stricter than the primary, not more permissive. This one was reached
  precisely BECAUSE the structure needed to verify a match was absent, and it
  responded by asking for less evidence rather than more. Worth checking the
  same instinct anywhere else a "we can't do the careful check here" branch
  exists. Related to #21: same root shape - a shared word carrying a match it
  had not earned - surfacing in the one code path that #21's fix did not cover.

31. Red glow around every word on the overlay panel - and a measurement that

32. Better OCR made detection WORSE: a perfectly-read "Full Rejuvenation
    Potion" was suppressed while a misread one worked
------------------------------------------------------------------------------
Where: text_detection.py, find_text_matches() candidate ranking
Symptom: Reported as "I changed the targets.txt text from all caps to 'Full
  Rejuvenation Potion' and now it has a tougher time finding the item". The
  edit was a red herring - load_target_items() uppercases every name and
  _clean_text() uppercases the OCR text, so the loaded key was byte-identical
  before and after. Worth confirming that first rather than debugging the
  change the user happened to notice.
Cause: find_text_matches() tries every contiguous RUN of words on a line, and
  ranked candidates by ratio alone. "Rejuvenation Potion" exists as a look-alike
  entry (added in #24 so the small potion isn't collected as the large one), and
  it is a strict tail of "Full Rejuvenation Potion". So on a clean read BOTH
  scored exactly 1.000 - the 3-word span against the real target and the 2-word
  span against the look-alike - the ambiguity check (added in #25) saw two
  different targets tied, and correctly-by-its-own-rules suppressed everything.
  The same fault has a second form: misread as "Fvll Rejuvenation Potion" the
  full span drops to 0.958 while the tail still scores 1.000, so the look-alike
  wins outright and the item is reported as the ignored small potion.
  This is why the OCR preprocessing fix (#24) appeared to cause it: before that,
  labels were read imperfectly enough that the two spans rarely scored the same,
  so the tie never happened. Improving recognition quality surfaced it.
Fix: Rank by (words matched, ratio) instead of (ratio, words matched) - longest
  match wins, ratio only breaks ties among equal-length spans. A shorter span is
  not better evidence just because it scores higher on the little it covers, and
  a long sloppy span cannot win by accident because every span must already
  clear each per-word cutoff and MERGED_WORD_CUTOFF to be eligible at all.
  Verified through the real window loop (not whole-string comparisons, which was
  how this was missed): all 19 collectibles match cleanly, the potion matches
  clean / mangled / embedded in a longer line, and all 17 look-alikes plus the
  bare word "Rune" stay suppressed. "LVM RUNE" is still suppressed and that is
  correct - it is one substitution from both LUM and LEM, so there is no honest
  answer.
Lesson: Three. (1) A bug that gets WORSE as an upstream stage gets BETTER is
  almost always a tie-break or ranking problem, because improving quality is
  what makes scores collide. Ranking rules only get exercised at the top of
  their range. (2) Test through the real code path: the earlier regression suite
  compared whole strings against each target and never built the sub-spans, so
  it passed on every case that was actually broken. A helper that "does what the
  function does" is not the function. (3) When a user reports a regression right
  after a change they made, check whether their change can possibly matter
  before investigating it - here two minutes confirming the loaded key was
  identical redirected the whole search.

33. Meters read 0% at full health once the game was windowed - regions were
    anchored to the screen, not to the game window
------------------------------------------------------------------------------
Where: assets/meters.json region semantics; fixed via new window_region.py
Symptom: Switching Diablo II from fullscreen-borderless to windowed 1280x800
  made health and mana both read 0% at full, and put the debug panel outside
  the game window. Item detection and auto-collect were unaffected.
Cause: Meter regions are stored as fractions, which was designed to survive a
  change of CAPTURE_SCALE - but fractions OF THE SCREEN. The game window was at
  (525,150) sized 1280x800 inside a 1920x1080 capture, so the stored fractions
  pointed at bare desktop. That detection kept working is the useful contrast
  and explains the split: a detection box is found BY LOOKING AT PIXELS and is
  therefore screen-absolute and position-independent, whereas a meter region is
  a statement about a window's layout and is meaningless without knowing where
  that window is. Two kinds of coordinate that look alike in the config file.
Fix: window_region.py resolves a window's CLIENT rect (not window rect - the
  title bar is a 33px offset here, enough to miss an orb) and converts
  window-relative fractions into frame-relative ones. calibrate_meters.py
  attributes each hand-drawn selection to the smallest window containing it and
  records that as "_anchor", so the user never types a title; it snapshots the
  window list BEFORE drawing its own UI, or its own always-on-top selection
  window is what the point lands in. main.py re-resolves at most once a second
  and, when the anchor window is missing, reads no meters so every value becomes
  None rather than 0.0. Configs with no "_anchor" behave exactly as before.
  Two bugs caught while building it, both worth remembering:
  (a) Ranking candidate windows by SIZE picked a browser tab titled "d2r.guide
  - Diablo II: Resurrected Cheat Sheet - Google Chrome" (1920x1080) over the
  game itself (1280x800). Fixed by preferring an exact title match first.
  (b) The refresh cache seeded _anchor_rect with None and compared new results
  against it - but None is a MEANINGFUL result here ("window not on screen"),
  so the first lookup of a missing window compared equal to the initial state,
  skipped the update, and returned the un-rewritten screen-relative meters:
  reading the wrong pixels at precisely the moment it meant to report "cannot
  read". Fixed with a distinct _UNRESOLVED sentinel.
Lesson: Three. (1) "Store it as a fraction so it survives rescaling" solves
  only one of the two ways a coordinate can move; it says nothing about the
  origin. Ask what a stored coordinate is measured FROM, not just in what
  units. (2) When disambiguating by a heuristic like "the biggest one", check
  what else on a real desktop could satisfy the filter - a title substring
  match is satisfied by every browser tab, chat window and editor tab that
  mentions the game. (3) A cache whose "empty" marker is also a valid answer
  will silently serve a stale value for that answer; give it its own sentinel.

34. Health read 0% while poisoned - the game recolours the orb, and the colour
    range only knew about red
------------------------------------------------------------------------------
Where: assets/meters.json hsv_ranges for health; preset in calibrate_meters.py
Symptom: "When I am poisoned in-game my health circle turns green, and Game
  State thinks I died - reading 0% when I was really at 90% and ticking down."
Cause: Diablo II turns the health globe green while poison is active. The
  configured ranges covered red and red-wrapped-around-H=0 only, so once the
  liquid turned green NOTHING inside the region matched, every row failed
  ROW_FILL_RATIO, and _fill_fraction correctly returned 0.0 for "no liquid
  anywhere". The measurement was right; the description of what liquid LOOKS
  like was incomplete. Note the timing: this is worst exactly when it matters
  most - poison means health is actively draining, so a potion-drinking or
  retreat layer would have been fed "you are dead" during a real emergency.
  It is also silent: 0.0 is a legitimate value, not an error, so nothing warns.
Fix: Add green as a third range. hsv_ranges was already a LIST OR-ed together,
  so no code change was needed - the data model already supported "this meter
  can be several colours", it just had not been filled in. Verified on
  synthetic orbs at 100/90/50/25% fill: red-only reads 0.0% at every level for
  a green orb (reproducing the report exactly), red+green reads
  94.9/87.2/50.3/27.2% for BOTH a red and a green orb - so the healthy reading
  is unchanged. The chosen green band (H 35-85, same S/V floors as red) is
  generous rather than measured from a real poisoned frame; confirm it by
  getting poisoned with the panel open.
Lesson: A colour-keyed measurement encodes an assumption that the thing being
  measured has ONE appearance, and games routinely break that to convey state -
  poisoned, cursed, shielded, overhealed, low-battery. Enumerate the states a
  meter can be in when calibrating it, not just the state it happens to be in
  at that moment. More generally: when a reading collapses to a clean 0 rather
  than becoming noisy, the input probably stopped matching the filter entirely,
  which points at the filter's definition rather than at its geometry or
  thresholds - the opposite conclusion from #28, where the reading was noisy
  and the region was at fault.

35. Three-channel template matching cost 5x for zero extra discrimination
------------------------------------------------------------------------------
Where: main.py, detect_objects() and _relocalize_track()
Symptom: Average FPS drifted to ~34. matchTemplate measured 17.5ms/frame at
  CAPTURE_SCALE 0.3, and relocalization 27-33ms PER TRACKED ITEM - the single
  largest costs in the pipeline.
Cause: Both ran on BGR frames, on the reasonable-sounding assumption that
  matching in colour is stricter than matching in grey. It is not, for this
  metric. TM_CCOEFF_NORMED subtracts the mean and normalises across the entire
  patch, and on a multi-channel image it does that over all channels together -
  which makes it very nearly invariant to exactly the transforms colour is
  supposed to catch. Measured against the real needle: a FULLY DESATURATED copy
  scored 1.000, and copies hue-rotated by 30, 60, 90 and 120 degrees all scored
  1.000. The matcher had been colour-blind the whole time; the extra two
  channels were pure cost.
Fix: Convert frame and template to grey once and match on one channel. 17.5ms ->
  3.2ms for detection, 27-33ms -> 5.7ms per track. Verified rather than assumed:
  false-positive headroom on real screen content is unchanged (best non-match
  0.365 grey vs 0.353 colour, both far under the 0.60 threshold); an end-to-end
  test boxes all three planted needles at the exact expected pixel and fires
  zero boxes on a needle-free frame; and over 20 perturbed relocalizations
  (drift, dimming, added noise) grey localised correctly 20/20 against colour's
  18/20, at equal or higher confidence every time.
Lesson: "More channels must mean stricter matching" is an assumption about the
  METRIC, not about the data, and it is worth actually testing - build the
  adversarial input (a desaturated and a hue-rotated copy) and see whether the
  score moves at all. If it does not, the channels are costing you nothing but
  time. Where a detector genuinely must key on colour, that belongs in an
  explicit HSV pre-mask (see legacy/vision.py), which can express it; normalised
  cross-correlation cannot.

36. The OCR thread captured a full-resolution frame it then threw away, ~45x/sec
------------------------------------------------------------------------------
Where: main.py, detect_text()
Symptom: An apparently idle OCR thread held a CPU core at 100% with nothing on
  screen to detect, and overall pipeline FPS was well below what the capture and
  matching threads could sustain on their own.
Cause: The loop grabbed a frame unconditionally at the top of every iteration,
  before deciding what to do with it. When there were no tracks to relocalize
  and no scan yet due - the normal case, since most of the time nothing is lying
  on the ground - every branch below was a no-op and the frame was discarded
  untouched. That "nothing happened" iteration still cost a full 1920x1080 grab
  plus conversion (~21ms) and ran about 45 times a second, so the thread spent a
  whole core and roughly 400MB/s of memory bandwidth in direct competition with
  the two threads that actually determine FPS. It looked free because the
  wasted work was in the part of the loop that did nothing.
  Compounding it: cv.resize at fx=1.0 is NOT a no-op. It is a full-resolution
  copy, and it ran on every one of those captures for ~3.7ms to produce an
  array identical to its input.
Fix: Work out whether the iteration has anything to do BEFORE capturing, and
  sleep instead when it does not. Skip the resize entirely when the scale is 1.0.
  Grab straight to one channel (BGRA->GRAY) when only relocalization needs the
  frame, instead of building a 3-channel full-resolution intermediate first.
  Idle pipeline throughput went 35.6 -> 51.8 FPS.
Lesson: Fetching input at the top of a loop "so it is ready" hides its cost in
  the branch that does nothing, which is the branch nobody profiles. Acquire
  expensive input only once you know it will be used. And treat any resize,
  convert or copy with identity parameters as real work until measured -
  libraries very rarely short-circuit them.

37. np.array() on an mss capture duplicated 8MB per frame, per capture thread
------------------------------------------------------------------------------
Where: main.py, get_screenshot() and detect_text()'s frame grab
Symptom: Screen capture measured ~21ms/frame against a ~17ms floor for the grab
  itself, on two separate threads.
Cause: np.array(screenshot) goes through mss's array interface and copies the
  entire 1920x1080x4 buffer (~8MB) into a fresh allocation every frame. The
  pixels were then immediately downscaled, so the copy existed only to be read
  once and freed.
Fix: np.frombuffer(img.raw, ...).reshape(...) wraps mss's existing buffer with
  no copy. Verified byte-identical to np.array(img) on the same capture. ~4ms
  per frame on each of the two capture threads. Because it is a VIEW over a
  buffer the library may reuse, it must be consumed before the next grab() -
  here the immediately-following resize/convert copies the pixels out, and
  nothing keeps a reference past that.
  Separately: downscaling now happens BEFORE the alpha channel is stripped
  rather than after. The output is bit-for-bit identical (max difference 0 over
  a full frame) because INTER_LINEAR mixes each channel independently and alpha
  is discarded either way - but the colour conversion then runs over 576x324
  pixels instead of 1920x1080.
Lesson: In a per-frame path, know which of your calls copy. Two that look like
  free reinterpretations (np.array over a buffer protocol; a channel conversion)
  are full-frame copies, and at 50 FPS an 8MB copy is 400MB/s of memory
  bandwidth that every other thread then has to share. Relatedly, when two cheap
  operations commute, do the one that SHRINKS the data first - the ordering is
  free and the saving is proportional.

38. A pure FPS optimisation silently made cursor flicker worse
------------------------------------------------------------------------------
Where: overlay.py, draw_rectangles() / draw_panel(); main.py, run_overlay()
Symptom: Reported right after the v0.008 performance pass - extra flicker on the
  mouse cursor, and clicking/right-clicking on items feeling slightly delayed.
  Nothing in the overlay had been touched.
Cause: run_overlay() redraws the overlay once per detection frame, so the
  overlay's repaint rate is bolted to detection throughput. Raising FPS from ~34
  to ~51 therefore raised box repaints from 34/s to 51/s without anyone asking
  for it. This is a fullscreen, always-on-top, WS_EX_LAYERED window - the single
  most expensive kind to repaint, because each repaint makes the desktop
  compositor redo the whole screen - and that cost is paid by the GAME
  underneath, not by us, so it never showed up in our own FPS number. The debug
  panel made it worse than the boxes did: 1.17ms per panel repaint against
  0.35ms for boxes, because every label is drawn nine times over to ring it in
  black, and it redraws on every 1% change in health or mana.
Fix: Cap each layer's repaint rate independently in overlay.py (BOX_REDRAW_HZ
  30, PANEL_REDRAW_HZ 10), decoupled from how often the caller asks. These are
  display-only rates - nothing reads the screen to make a decision, since
  auto-collect reads shared_text_tracks directly - so detection, tracking and
  actions are untouched. Worst case measured 73.3 -> 34.3 ms/s of repaint work.
  Two things had to be got right: a skipped repaint must NOT record its content
  as drawn (otherwise a box that stops moving right after a skipped frame is
  stranded at a stale position forever - tested explicitly), and a cap can only
  land on caller_rate/N, so 30Hz against a 51Hz caller really means ~25Hz.
Also measured, and NOT the cause: the overlay does not delay clicks. End-to-end
  (click issued -> a window underneath actually handling it, with the overlay
  repainting concurrently) it costs ~0.1ms, which is noise - no overlay 0.7ms
  median, repainting at 51Hz 0.8ms, both mouse buttons. Worth recording so the
  next person does not go hunting there.
Lesson: An optimisation's effects are not confined to the thing it optimised.
  Anything downstream that runs "once per iteration" silently speeds up too, and
  if that downstream thing costs someone ELSE resources - a compositor, a GPU, a
  disk, a rate-limited API - the new cost is invisible in your own numbers by
  construction. After changing a loop's rate, list what else is keyed to that
  loop and decide deliberately whether each one should follow. Display rates in
  particular should be pinned to what a human can perceive, never to how fast
  the machine happens to be able to go.

39. A second DXGI capture source is silently the FIRST one, and steals its frames
------------------------------------------------------------------------------
Where: frame_source.py; would have hit main.py's detect_text() thread.
Symptom: Found while designing the DXGI frame source, before it could ship - the
  obvious next step after speeding up the fast path's capture was to give the
  OCR thread the same treatment, since it does its own independent full-
  resolution grab. That would have broken OCR completely, silently.
Root cause: bettercam.create() is a per-output SINGLETON. Asking for a camera on
  an output that already has one does not raise and does not create a second
  one - it prints a note to stdout and hands back the SAME object. Two threads
  then share one DXGI duplicator. Verified directly: with camera A and camera B
  (the same object) in one process, A.grab() returned a full (1080,1920,4)
  frame and B.grab() returned None on the very next line, because DXGI hands
  over a frame only when the desktop CHANGED since the last acquire, and A had
  just consumed it. In the pipeline that means whichever thread polls faster
  starves the other, intermittently and at random - the OCR thread would appear
  to just stop finding items sometimes.
Fix: frame_source.py takes an explicit backend argument, the DXGI path is
  documented as single-consumer, and detect_text() deliberately keeps its own
  independent mss capture. mss and DXGI coexist fine - they are different APIs
  against different parts of the stack.
Also found in the same file, and avoided rather than debugged: bettercam's
  video_mode / get_latest_frame() path waits on a threading.Event with NO
  timeout, so if its internal capture thread dies the caller blocks forever with
  no way to time it out from outside - a silent hang, which is exactly what this
  project's first design priority rules out. It also np.array()-copies every
  frame out of a ring buffer, the same per-frame 8MB copy removed in v0.008.
  The polled grab() path avoids both and measured cheaper anyway (3.4 vs 5.6
  CPU-ms per frame at a matched 90 FPS), so nothing was traded to avoid it.
Lesson: A factory function that returns an EXISTING object instead of a new one
  breaks the assumption every caller makes about ownership, and it does it
  without an exception, a None, or a distinct type - the only signal here was a
  line printed to stdout, which nothing reads. Before giving a second consumer
  its own handle to a scarce OS resource (a capture device, a duplicator, an
  exclusive-mode audio endpoint), verify you actually GOT a second one, by
  checking identity - not by checking that the call succeeded.

40. An unreadable HUD meter reported 0%, so "I cannot see it" read as "you are
    about to die" - and the potion layer acted on it
------------------------------------------------------------------------------
Where: game_state.py, _fill_fraction(). Reported by the project owner against
  live gameplay, with two screenshots (assets/zelScreenshots/).
Symptom: Health and mana both read 0% in two states where nothing is wrong -
  sitting in the game lobby (where the HUD does not exist at all), and with the
  in-game menu open (Options / Save and Exit), which dims the whole screen. The
  screenshot of the menu case shows Life 1131/1228 and Mana 372/372, i.e. both
  effectively full, while the pipeline reported 0% for each. With v0.010's
  potion drinking attached, 0% health is the emergency tier's trigger, so this
  is a belt being emptied at full health.
Root cause: _fill_fraction() had TWO separate "return 0.0" branches, and both
  were failure paths mislabelled as measurements:
    - no filled rows found at all -> return 0.0  ("the meter is empty")
    - filled rows found but no coherent liquid surface -> return 0.0
  Neither is a measurement. "No liquid visible" is exactly what an ABSENT meter
  looks like through a colour mask, and exactly what a DIMMED one looks like:
  the configured hsv_ranges floor is V >= 40, and measured on the real menu
  screenshot the orb region's mean V was 34 (max 123), so the mask went patchy.
  Measured per-row on that screenshot: 74 of 147 rows still passed
  ROW_FILL_RATIO, scattered rather than stacked, so it cleared the first branch
  and fell into the second. The lobby screenshot hit the first branch instead
  (mana matched 0.00% of its region).
  The second branch's own comment already said what it meant - "the same test
  rejects stray colour matches floating above an empty meter... since those have
  almost nothing filled beneath them" - and then returned 0.0 anyway. The code
  knew the answer was "this is not the meter" and reported it as "the meter is
  empty".
Fix: both branches return None. This module's whole contract is that None
  ("cannot read") and 0.0 ("empty") are different answers that consumers must
  not conflate - it says so in three docstrings - and this was the one place
  that broke its own rule, in the function every reading passes through.
Why this cost nothing: a MEASURED reading can never be exactly 0.0 anyway. The
  surface row is at most the last row of the band, so the smallest value the
  measuring path can return is 1/height - about 0.7% on a 150px orb, verified
  across synthetic fills from 0.5% to 100%. Every 0.0 the system had ever
  produced came from one of these two branches, never from a measurement, so
  nothing genuinely measured changed behaviour. The only difference is that an
  orb below ~1% now reads "unknown" instead of "empty", and a potion is not
  what saves you at 1% health. Confirmed the fix against both real screenshots:
  all four readings went 0% -> None, and _potion_due() returns nothing for both.
Lesson: A sentinel that is also a legitimate value will eventually be returned
  from an error path, and it will look like data. The tell is a return statement
  whose COMMENT states an interpretation the function cannot actually support -
  "the meter is empty" was an inference about the world, from a function that
  had only observed the absence of evidence. When a measurement fails, say it
  failed; do not pick the plausible-looking value at the bottom of the range.
  Note also which direction the mistake ran: the failure value happened to be
  the most alarming one in the domain, so every consumer treated an unreadable
  sensor as a maximum-urgency reading. Where a sensor's failure mode has to
  collapse into a number at all, it must fail toward "do nothing", never toward
  "act immediately".
