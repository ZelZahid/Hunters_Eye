# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Hunter's Eye is a real-time on-screen object detection tool: it grabs the screen, runs template matching to find a target image ("needle") on it, and draws bounding boxes around matches. It's a personal portfolio project (Python + OpenCV), currently a prototype/proof-of-concept rather than a packaged application.

**This is intentionally more than a Diablo II tool.** The end goal is a cross-platform (Windows + macOS), purely pixels-in computer-vision engine: point it at a screen or camera feed, tell it what to look for (a reference image, or a piece of on-screen text), and it reports every match as a bounding box plus the match's center point (so a caller can e.g. move a mouse there or aim a servo there). It never reads a game's memory, process internals, or network traffic — detection is strictly "look at pixels," which is exactly what keeps it usable against any game (or any camera) instead of being tied to one title.

Diablo II: Resurrected is the current test bed for validating detection accuracy and driving simple mouse/keyboard automation — it is not the product. Two other consumers are already planned and should shape design decisions now, even though neither is built yet:
- A future GUI product where a non-technical end user supplies a reference image or text string plus an action (move mouse here / press this key), with this repo's detection engine as the backend.
- A robotics project (a patrolling security robot) that reuses the same detection engine against a live camera feed to spot people instead of game sprites.

Treat anything Diablo-II-specific (item/potion reference images, cascade classifiers, `pindle.py`-style scripted click sequences) as example/integration code, not something to design the core engine's abstractions around.

## Design priorities

In order, because they can conflict and the tradeoff should always be made deliberately, not by accident:

1. **Stability** — no crashes, no silent hangs. This is meant to run unattended alongside a game (or eventually on a robot with no one watching the console), so it can't be flaky.
2. **Performance (FPS)** — this must never noticeably slow down whatever it's watching, and must run acceptably on modest, non-"beefy" hardware. This is the top practical constraint the project owner cares about — a correct detector that tanks game FPS is a failed detector. If a change trades accuracy for speed (or vice versa), call that tradeoff out explicitly rather than making it silently.
3. **Portability** — Windows and macOS both need to work from the same codebase. OS-specific code (e.g. `pywin32`/`win32gui` window capture) must stay isolated behind something that can degrade gracefully on platforms that don't have it, not be sprinkled through core logic.
4. **Flexibility for future targets** — nothing in the core detection path should assume "this is Diablo II," because the same code needs to make sense pointed at a webcam later. Expect these seams to matter even before they're formally built out:
   - **frame source** — full-screen grab (`mss`, current), a specific window (`win32gui`, `legacy`), or eventually a camera (`cv.VideoCapture`).
   - **detector** — template matching (current); OCR for on-screen text is an explicitly planned near-term addition; a trained model (Haar cascade, or a small object/person detector) for the robotics use case later.
   - **match result** — bounding box + center point. Keep this contract stable; both future automation and the future GUI depend on it.
   - **action** — move mouse / press key / click. Not built in the current root pipeline yet; `legacy/pindle.py` is a rough, hardcoded preview of what this becomes.

   None of this needs formal plugin interfaces today, but avoid choices that would be painful to walk back later — e.g. don't assume `win32gui` is always importable, and don't hardcode game-specific window titles, item images, or key bindings into files outside of an obviously example/integration area.

### Detector independence — a hard rule, not a preference

Every detector (template matching, OCR, HUD meter reading, and any future one — a trained model, color/HSV blob detection, motion detection) is a **separate, self-contained way of finding things, and they must stay that way.** They exist because each is the right tool in a different situation, and the project needs all of them available at once, permanently. Concretely:

- **Detector modules must not import each other.** `text_detection.py` and `game_state.py` know nothing about one another today. Keep it that way. If two detectors need something in common, that shared thing belongs in a neutral module both can import, never in one detector reaching into another.
- **Never delete, gut, or let rot a detector because it isn't the current focus.** A stretch of work concentrating on template matching must leave OCR exactly as capable as it was — OCR is not "the item-name feature," it is *the ability to read text on a screen*, which will be needed again for menus, dialogue, timers, counters, subtitles, license plates, signage. The same holds in reverse, and for meter reading. If a refactor would make an out-of-focus detector worse, it is the wrong refactor.
- **Removing or rewriting one detector must not require touching any other.** If it does, they've become entangled and that coupling is the bug — fix the coupling, don't work around it.
- **Every detector must work on non-game input.** A browser window, a desktop, a document, a webcam frame. A detector is handed a BGR frame and returns matches; it must never assume the frame came from a game, or from a screen at all.
- **Diablo II specifics never live inside a detector.** Item names live in `assets/targets.txt`, meter positions in `assets/meters.json`, click sequences in integration code. `text_detection.py` doesn't know what a rune is; it matches strings from a file. `game_state.py` doesn't know what a health orb is; it measures a colored region. Preserve that split when adding anything new.

**The litmus test for any change:** *could this still work pointed at a security camera, or at a browser window, with only a different config file?* If the answer is no, the game-specific part is in the wrong place. This applies to new detectors as much as existing ones — a monster detector should be a general object detector that happens to be loaded with monster classes, not a Diablo-shaped thing.

## Versioning

`docs/updates.txt` is the changelog and the source of truth for version numbers — read it before assuming what "the current version" means. Versioning starts at `0.001` and increments by `0.001` per significant update, working toward `1.000` ("Hunter's Eye complete," which is intentionally far off). Each version has a matching git tag (`v0.001`, `v0.002`, ...) on the exact commit for that state — **when asked to roll back to a known-working version, check out that tag; don't guess from raw commit history.** When cutting a new version: append an entry to `docs/updates.txt` (and a one-line summary to its AT A GLANCE index at the top) (date + a short description of what changed, in the same style as existing entries), commit, then create an annotated tag (`git tag -a v0.XXX -m "..."`) on that commit.

`docs/todolist.md` is the project's working memory — what to do next and why, plus ideas, open questions, known limitations, and decisions already made. **Read it at the start of a session and check it before proposing what to work on**, rather than inferring priorities from the code. Keep it current as work happens: move the finished item to DONE, promote the next thing into NOW (which holds exactly one item), and add anything raised in conversation that isn't being acted on immediately — a parked idea belongs in PARKING LOT, not lost in a transcript. It also records decisions that are already settled, so they don't get re-litigated months later.

`docs/Error_history.txt` logs significant bugs hit during development with root cause + fix + a one-line lesson each — **check it before debugging something that feels familiar** (e.g. anything touching `overlay.py`'s Win32 layered-window code, OCR/Tesseract error handling, or shared capture-resolution constants); it may already be documented there with the fix ready to reapply. Append a new entry there (same format as existing ones) any time a bug takes real effort to track down, not just quick typo fixes.

## Running

No build step (no `setup.py`/`pyproject.toml`). Dependencies are listed in `requirements.txt`; install with:

```
python -m pip install -r requirements.txt
```

`pywin32` is Windows-only and gated behind a `sys_platform == "win32"` marker in `requirements.txt`, so the same file installs cleanly on macOS/Linux too (the `legacy/Window_Capture.py` module that needs it just won't import there). **When you add a new import to any script in this repo, add the matching package to `requirements.txt` in the same change.**

Run the current (root-level) version:

```
python main.py
```

Press `End` to quit the overlay (or `q` in the fallback debug window); final average FPS is printed on exit.

Global hotkeys while running (all via the `keyboard` package, because the overlay is click-through and can never hold keyboard focus): `End` quits, `F3` starts the next game (quit → read the lobby's game name → increment → create), `F4` snoozes auto-collect for 10s, `F6` snoozes potion drinking for 10s, `F5` toggles the game-state debug panel. `F5` only changes what gets *drawn*, so toggling it cannot disturb detection, the boxes, or auto-collect.

`user_config.txt` at the repo root holds the settings a *user* changes rather than a developer — potion thresholds, belt key bindings, cooldowns. It is read once at import; edit and restart to apply. It sits at the root rather than in `assets/` deliberately: `assets/` holds *data* (a word list, calibration output produced by a tool), while this is the one file a person is expected to open and hand-edit, so it belongs where they will find it.

One-time setup for HUD meter reading (health/mana), needed before `game_state.py` reports anything:

```
python tools/calibrate_meters.py
```

This is a setup/validation tool, not a second pipeline — the rule that there's exactly one `main.py` still holds, and this is the "distinctly-named new file" case that rule allows for. Re-run it after any resolution or UI-scale change, since the meter regions are tied to where the orbs appear on screen.

There is no linter config or CI in this repo. There are eight test files in `tests/` — `test_game_state.py`, `test_next_game.py`, `test_overlay.py`, `test_potions.py`, `test_presence.py`, `test_quit_game.py`, `test_targets.py` and `test_user_config.py` (run each with `python tests/<file>`). `test_game_state.py` — synthetic, no game required, covering `game_state.py`'s fill measurement. It exists because that measurement drives automatic actions and fails silently with a plausible-but-wrong number rather than an error; its adversarial cases caught two real bugs (`Error_history.txt` #19, #20). Other modules have no tests.

## Architecture

### Root `main.py` — current version, producer/consumer pipeline

Four background daemon threads plus a main-thread output loop, connected by two bounded `queue.Queue`s (maxsize 3, drop-oldest-when-full) plus a lock-protected shared variable:

1. `get_screenshot()` — grabs the full screen via `frame_source.FrameSource` (DXGI where available, `mss` otherwise — see `frame_source.py` below), downscales by `CAPTURE_SCALE`, converts BGRA→BGR, pushes to `screenshot_queue`, then **sleeps out the rest of the frame to hold `TARGET_FPS` (60)**. The pacing is the point, not an afterthought: capture used to *be* the throttle at ~58 FPS, and DXGI can produce ~177, which costs 3.56 CPU cores against 0.42 paced. Higher FPS is not the goal — the same work for less CPU is, per design priority #2. Nothing downstream can use more than 60 anyway (the overlay caps itself at 30Hz, auto-collect reads `shared_text_tracks` not this path, `game_state` medians over 5 frames).
2. `detect_objects()` — the fast path. Pulls from `screenshot_queue`, runs `cv.matchTemplate` against a single hardcoded needle image (`assets/image1.png`), collapses overlapping matches via `cv.dnn.NMSBoxes` (**not** `cv.groupRectangles` — OpenCV 5 removed that from its Python bindings), reads whatever `detect_text()` last published from `shared_text_tracks` (behind `text_tracks_lock`, never blocks waiting on it), merges both rectangle sets, and pushes `(frame, rectangles)` to `detection_queue`. This thread's speed is governed only by capture + `matchTemplate` cost — OCR never touches it. Matching runs on a **grayscale** copy of the frame, converted *after* `game_state` has read it (meter reading is an HSV threshold and genuinely needs the colour; matching measurably does not — see "Measured performance facts"). Every rectangle now carries its own `(r, g, b)` draw color (image-template matches always use `text_detection.DEFAULT_BOX_COLOR`; OCR matches carry whatever `detect_text()` resolved for that item — see below). It also reads the HUD meters (`game_state.read_all()`) off this same frame and publishes them to `shared_game_state` — that piggybacks here rather than getting its own thread because it costs ~0.15ms/frame while a dedicated thread would need its own ~17-20ms capture; see `game_state.py` below.
3. `detect_text()` — the slow path, fully decoupled from thread 2 on purpose (see "Why OCR has its own thread" below). **It only captures a frame when that frame will actually be used** — with no tracks to relocalize and no scan yet due (the normal case, since most of the time nothing is on the ground) it sleeps instead. It previously grabbed unconditionally at the top of every iteration and discarded the result untouched ~45 times a second, which cost a whole CPU core and ~400MB/s of memory bandwidth against the two threads that actually set the FPS (`Error_history.txt` #36). Runs its **own independent `mss` capture loop** at `OCR_CAPTURE_SCALE` (not `CAPTURE_SCALE` — see "Why OCR needs its own capture resolution" below), runs a full OCR pass via `text_detection.find_text_matches()` at most every `OCR_INTERVAL_SECONDS`, and in between re-localizes each already-found match every loop iteration via `_relocalize_track()` (a small local **grayscale** `cv.matchTemplate` search around the item's last position) so the box tracks the item smoothly instead of jumping only when OCR refreshes. That search is the most expensive thing this thread does per track — at `OCR_CAPTURE_SCALE` 1.0 the search window is ~700x530 native pixels — which is why it runs on one channel. Converts match coordinates from `OCR_CAPTURE_SCALE` space to `CAPTURE_SCALE` space before publishing to `shared_text_tracks` (consumers only ever deal in `CAPTURE_SCALE` coordinates). New matches are logged to the console (`Found '<name>' at center (x, y)`).
4. `run_auto_collect()` — the first concrete use of the "action" seam (move mouse / press key / click) described in Design Priorities above; see `actions.py` below for the generic click-driving code it calls into. Polls `shared_text_tracks` (same never-block-on-OCR read as thread 2) for any track whose item was marked `to_collect` in `assets/targets.txt`, and drives `actions.click_until_gone()` to click the nearest-to-cursor one until it's picked up or `COLLECT_TIMEOUT_SECONDS` (5s) passes with it still on the ground. It is gated on `actions_allowed()` both before starting an attempt and, via `click_until_gone`'s `is_paused`, throughout one — an attempt clicks repeatedly for up to 5s, so alt-tabbing one click in would otherwise let the rest land somewhere else. `'F4'` is a global hotkey (same `keyboard`-package mechanism as the overlay's quit hotkey) that snoozes this thread for `SNOOZE_SECONDS` (10s) rather than toggling it off outright — a snooze re-arms itself automatically, so it can't be accidentally left disabled for an entire session the way a plain toggle could.
5. `run_potion_drinking()` — the second consumer of the action seam, and **the first thing in the project that acts on a measured NUMBER rather than a found position**. Polls `current_game_state()` and presses a belt key when a meter reads low. Gated on `actions_allowed()`. See "Potion drinking" below.
6. `run_overlay()` — **runs on the main thread, not a spawned one** (Tk's event loop must own whichever thread created its window). Pulls from `detection_queue`, rescales rectangles from `CAPTURE_SCALE` coordinates back to real screen pixels (`SCALE_TO_NATIVE = 1 / CAPTURE_SCALE`), and draws them via `overlay.Overlay` — see below. `main()` calls this and falls back to `run_debug_window()` (the old plain OpenCV window, kept for platforms the overlay doesn't support) if `Overlay` raises `NotImplementedError`. It also draws the game-state debug panel every iteration via `overlay.draw_panel(*_debug_panel())` — placed *before* the queue read so the panel keeps updating (and keeps reporting staleness) even when no detection frames are arriving. The panel is **not** mirrored into `run_debug_window()`; that fallback path still shows boxes only.

The needle image, monitor geometry, target item list, and queues/shared state are module-level globals set up at import time — there's no class/config object here yet.

**`assets/targets.txt`'s per-line syntax**: one item name per line; a **leading `-`** marks it `ignore` (matched, then discarded — see the look-alike discussion under `text_detection.py`; this is load-bearing, not decoration); a trailing `*` marks it `to_collect` (drives thread 4 above); an optional trailing `[colorname]` tag (checked against `text_detection.NAMED_COLORS`, e.g. `[purple]`, `[darkorange]`) sets that item's detection box color, falling back to `text_detection.DEFAULT_BOX_COLOR` (green) if omitted or unrecognized (with a load-time warning for the latter, not a crash or silent misparse). Both are parsed and stripped in `text_detection.load_target_items()` before the name is used for matching. Named colors are spelled out in full (`darkorange`, not a single letter like `o`) deliberately — a single-letter code is ambiguous (`o` for orange or olive?) and a typo in one letter silently picks a different valid color, whereas a misspelled word just fails the dict lookup and falls back to green with a warning. The palette deliberately excludes magenta/fuchsia: `overlay.py`'s click-through mechanism relies on one exact color (`TRANSPARENT_COLOR`, `#ff00ff`) being invisible, and a box drawn in that exact color would silently vanish.

### `frame_source.py` — where pixels come from

The **frame source** seam from Design Priorities, made concrete. A frame source is handed a screen region and hands back BGRA pixels; it knows nothing about what looks at them. `cv.VideoCapture` for a camera is the next backend to slot in here, and nothing above this line should have to change when it does.

Two backends today. **DXGI Desktop Duplication** (`bettercam`, Windows-only, optional) reads the composited desktop back from the GPU that already holds it, instead of asking GDI to re-blit it — measured, that replaces essentially all of the ~12.7ms `BitBlt` that was setting the pipeline's frame rate, taking the capture thread from 15.3 to 7.0 CPU-ms per frame and raising the pipeline's own ceiling from ~58 to ~177 FPS. **`mss`** is the portable backend and what this project used exclusively before; it is chosen automatically when `bettercam` is absent, on non-Windows platforms, **and as a runtime fallback if DXGI fails mid-session** (`DXGI_ERROR_ACCESS_LOST` fires on a resolution change, a UAC prompt, a driver reset, a fullscreen transition). All three of those paths are tested explicitly, because stability outranks performance: a machine without `bettercam` measured 52.4 FPS / 0.79 cores, exactly the pre-change baseline.

**A DXGI source is a per-output SINGLETON, so exactly one consumer in the process can have one — and asking for a second silently hands you the first.** `bettercam.create()` on an output that already has a camera does not raise and does not give you a new camera; it prints a note to stdout and returns the same object. Two threads then share one duplicator and steal frames from each other — verified directly, the second caller's `grab()` returned `None` because the first had just consumed the only pending frame. This is why `detect_text()` keeps its own independent `mss` capture rather than taking a DXGI source of its own, and why any second consumer must pass `backend=MSS` explicitly. See `Error_history.txt` #39.

**Use the polled `grab()`, never `bettercam`'s `video_mode`/`get_latest_frame()`.** That path waits on a `threading.Event` with **no timeout**, so a dead capture thread hangs the caller forever with no way to time it out from outside — the one failure mode design priority #1 rules out. It also `np.array()`-copies every frame out of a ring buffer, the same per-frame 8MB copy v0.008 removed from the `mss` path. Polling measured *cheaper* anyway (3.4 vs 5.6 CPU-ms/frame at a matched 90 FPS), so avoiding the hang cost nothing.

**`grab()` returns a VIEW valid only until the next `grab()` on that source**, preserved rather than papered over with a copy — copying an 8MB BGRA frame every frame is exactly the waste v0.008 removed. Consume it (resize, convert, slice) before grabbing again. And DXGI hands over a frame only when the desktop actually **changed**, so `None` is the normal answer on a static screen, not an error; the source re-serves the previous frame so the pipeline's cadence stays steady.

**Still on the table, and measured**: capturing only the game window instead of the whole screen is 3.4 CPU-ms/frame against 7.0 — the single biggest remaining win. It is not done yet because it changes the coordinate space every consumer assumes (`CAPTURE_RECT`, `SCALE_TO_NATIVE`, `window_region.to_frame_fractions`).

### `actions.py` — generic mouse-click action layer

The "action" seam from Design Priorities, made concrete for the first time. Deliberately knows nothing about item names, OCR, or Diablo II — `click_until_gone(get_position, timeout, click_interval, poll_interval, is_paused)` just clicks wherever a caller's `get_position()` callback reports until that callback returns `None` (target gone) or `timeout` elapses with it still present. `main.py`'s `run_auto_collect()` is the D2R-specific glue that feeds it OCR-tracked positions and item semantics.

Checking "is it gone yet" (`poll_interval`) and actually issuing a new click (`click_interval`) are deliberately different cadences — many games (D2R included) treat a click on an item as "walk over there and pick it up on arrival," not an instant action, so re-clicking faster than that walk takes kept re-issuing the move command and retargeting the character before it ever arrived (see `updates.txt` v0.004 / `Error_history.txt` #18 for the full multi-round investigation that led here). Each actual click is three separate steps, not one combined call: move, wait `MOVE_SETTLE_SECONDS`, press, wait `CLICK_HOLD_SECONDS`, release — both delays exist because pyautogui's own convenience functions (`moveTo()`+`click()`, or `click(x, y)`) either introduce an unwanted extra ~0.1s gap (pyautogui's own `PAUSE`) or collapse press+release into a single zero-duration Windows `mouse_event()` call that some games' per-frame input polling can miss entirely — confirmed by reading pyautogui's actual `_pyautogui_win.py`, not assumed. All pyautogui calls pass `_pause=False` so the only delays present are the two intentional ones.

`press_key(key, hold)` is the keyboard half. **It uses the `keyboard` package rather than pyautogui, and the two are not interchangeable here.** Both reach Windows' `keybd_event`, but pyautogui hardcodes the scancode argument to `0` while `keyboard` passes the real one — read out of each library's source, then **measured** through a raw `WH_KEYBOARD_LL` hook: `press_key('f13')` delivers `scanCode=100`, `pyautogui.press('f13')` delivers `scanCode=0`. A game reading the keyboard through DirectInput or Raw Input looks at the *scancode*, so pyautogui's zero arrives empty and the game does nothing, with no error anywhere. This is the keyboard-side twin of the mouse finding above — **the pattern to expect from any input library is that the convenient call sends something, raises nothing, and is silently ignored by the one program it was aimed at.** `hold` exists for the same reason `CLICK_HOLD_SECONDS` does. (`keyboard` raises `ValueError` on an unrecognised key name rather than no-opping, so a typo'd binding fails loudly — checked.)

**Potion drinking** (`main.py`'s `POTION_RULES` / `_potion_due()` / `run_potion_drinking()`) is the D2R glue on top, and **the rules come from `user_config.txt` at runtime, not from code** — `main.py`'s `DEFAULT_POTION_RULES` is only the fallback for a missing or unusable file, so behaviour is identical to before that file existed rather than silently doing nothing. `user_config.py` is the loader and is as generic as the rest of the engine: it parses "when this named meter drops below this level, press these keys, then wait this long", which describes a potion belt, a drone returning to base on low battery, and a pump switching on when a tank runs low, equally well. **Every value is validated and every bad one falls back with a named warning, because a config file must never be able to stop a program that runs unattended** — nor let it run with a setting nobody intended, which is worse because nothing looks wrong. Two specifics worth keeping: `configparser` needs `interpolation=None` or a perfectly reasonable `below = 20%` raises `InterpolationSyntaxError` **on access rather than on read**, landing outside any file-level `try`; and a rule naming a meter that does not exist is **dropped, never repointed**, since a rule that can never fire is as bad as one that fires wrongly and much harder to notice. A `PotionRule` is `(meter, at_or_below, keys, cooldown, label)`, evaluated **in order, first match wins**, so more urgent tiers come first. Four properties, each guarding a distinct failure:
- **A reading of `None` fires nothing, ever.** `None` means "could not read", not "critically low" — treating them alike dumps the whole belt the instant you alt-tab. This is the consumer `game_state.py`'s `None`/`0.0` split exists for, and `0.0` *is* acted on.
- **Each rule cools down on its own clock.** Taking a big hit one second after an ordinary heal is precisely when the emergency tier is needed, and a single shared cooldown would swallow it.
- **`POTION_MIN_GAP_SECONDS` is a floor under every press regardless of rule.** The per-rule cooldowns are the tuning knob; this is the safety net that makes "empty the belt in one second" impossible even with a mistuned threshold or a misreading orb.
- **A reading below `ignore_below` (3%) is treated as unreadable, not as critical.** At `CAPTURE_SCALE` 0.3 an orb is only ~43 rows tall, so one row is 2.3% and the smallest possible non-zero reading is indistinguishable from a stray patch of the right colour where the meter should be. This costs nothing real because **a meter does not teleport**: health falls *through* 20%, 15% and 10% on its way down at ~50 samples a second, so the emergency tier has already fired long before a reading gets that low.
- **A rule with several keys alternates between them.** Nothing can see how many potions a belt column holds (belt counting is not built), so spreading presses across both rejuvenation columns beats emptying one and then pressing a dead key mid-emergency.

`_potion_due()` is kept **pure** — no clock of its own, no globals, no key presses — because what it decides is "press a key into a live game", which is not something to validate by playing and hoping. `test_potions.py` covers it (27 assertions, no game required).

`click_when_seen(find_position, ...)` is the counterpart to `click_until_gone`: that one clicks something already on screen until it goes away, this one waits for something to appear and clicks it **once**. Together they cover "act on what is here" and "act when this shows up". Once, not repeatedly, because a menu button is not a walk-over-and-pick-it-up — clicking it again lands on whatever replaced it. `wait_until(condition, ...)` is the third piece: waiting for an *effect*, so a step can check that it worked.

**A paused attempt is bounded, and the reason is a hang that shipped for two versions.** Both click functions treat a pause as "suspend, do not fail" — paused iterations deliberately do not consume the timeout. That is safe only while every `is_paused` callback eventually goes false, which was true when the only one was a snooze hotkey (a snooze always expires). **v0.010's foreground guard made it reachable** by widening auto-collect's callback to "snoozed OR not safe to act": the second half stays true for as long as the game is not focused, so alt-tabbing mid-pickup meant `click_until_gone` never returned and auto-collect silently stopped for the session — no spin, no error, no log line. `PAUSE_BUDGET_SECONDS` (30s) now bounds paused time separately from active time. **"This wait does not count against the timeout" is the same statement as "this wait is unbounded"**, and the second phrasing is the one that shows the bug. See `Error_history.txt` #41.

**`quit_game()` (`main.py`) is the first scripted sequence, and the shape later ones should follow.** Press Esc → wait for the "Save and Exit" button to appear → click it → **confirm we actually left** by waiting for `in_play()` to go false. Every step waits on detection, never on a clock; and it returns True only if the game was actually exited, because `next_game()` is built on it and a `next_game` that believes it quit when it did not would press Create-Game buttons into a live game world. It is not bound to a hotkey of its own — `next_game()` is what `F3` runs, and quitting is its first step. It runs on its own thread (via `run_next_game()`, which also refuses to start a second one while the first is still going) — the `keyboard` package runs a hotkey callback on its listener thread, and blocking that for seconds would stall every other hotkey including `End`.

**`next_game()` (`main.py`) is the full loop, and `F3` runs it**: quit → read the name Diablo II pre-filled into the lobby's Game Name box → increment it → type it in → set or clear the password → Enter → confirm a game actually loaded. Every step verifies its own effect before the next runs, because the failures compound — one that believes it quit types a game name into a live world, and one that believes it created a game leaves you in a lobby thinking you are farming. On "a game already exists with that name" it bumps the number and tries once more, then stops and stays in the lobby rather than hammering the server.

**The name is read from the LOBBY, not from the in-game map overlay, and that was forced by measurement.** The map's "Game: z25pin41" text is ~11px in a stylised font and could not be read exactly by any combination of threshold, scale and segmentation mode tried — upscaling made it *worse*, because interpolation blurs thin glyphs before they are thresholded. Diablo II pre-fills the lobby box with the last game name, which reads exactly: same information, one fewer step. Two things that cost real time there and generalise: **Tesseract clips a glyph touching the crop border**, so a crop needs a quiet margin around the text (this alone took `z25pin41` from `Z25pindt` to correct at every threshold from 110 to 140); and a single threshold that works on one screenshot is a setting tuned to that screenshot, so the read votes across four. **OCR cannot determine CASE here and that is not fixable** — `z` and `Z` are the same glyph at different sizes and a text box gives no x-height to judge against, so the program remembers the case it typed and `user_config.txt`'s `game_name` seeds the first one.

**The shared Tesseract engine is not thread-safe, and a second caller took the whole process down with no traceback.** `read_line()` also switches the page-segmentation mode mid-call. Two threads in a C++ library's mutable state does not raise — the *absence* of a traceback was the clue, since a Python exception in a daemon thread prints and leaves everything else running. Every use is now behind a lock. See `Error_history.txt` #42.

**The button template is the TEXT, not the button, and this is the counter-intuitive part.** All five menu buttons share identical frame art, so chrome is nearly all of the correlation and the words are a rounding error. Measured on a real menu at 0.3x: a whole-button template scored **0.900 on the right button and 0.888 on a wrong one** — a margin of 0.013, a coin flip that would report success while clicking the wrong thing. Text-only took the margin to 0.331. **A bigger template is not a stronger match when the things you are telling apart share most of their pixels.**

**It takes its own full-resolution capture rather than using the pipeline's 0.3x frame**, which is the same lesson already recorded for OCR one level deeper: resolution needs come from what a detector has to *tell apart*. Measured through the real code path — right button vs best wrong button: `0.3x → 0.793 vs 0.671` (0.029 of headroom over any threshold between them), `full → 0.891 vs 0.529`. Affordable precisely because this is rare and user-initiated, ~24ms per poll for a few seconds once per game; it never touches the fast path's budget.

**Why OCR has its own thread**: it used to run inline inside `detect_objects()`, throttled to every Nth frame. That still periodically stalled the fast image-matching path for the OCR call's full ~120-150ms cost (pytesseract launches a new `tesseract.exe` subprocess per call — see `text_detection.py`'s docstring), capping overall FPS well below what image matching alone could do. Moving it to its own thread that merely *publishes* results asynchronously means `detect_objects()`'s throughput is no longer coupled to OCR timing at all — measured on dev hardware, this took the pipeline from ~25 FPS to ~44-46 FPS with OCR active either way.

**A single real OCR call against actual gameplay costs far more than a synthetic benchmark suggests — measure against the real thing before tuning around it.** Earlier profiling (against a mostly-blank synthetic test image) suggested ~150-300ms per Tesseract call; measured against actual busy gameplay it was **~0.9s**. Tesseract's sparse-text segmentation cost scales with visual complexity, not just pixel count, so a cluttered real game screen is far more expensive than a quiet test image. `VIEWPORT_TOP_MARGIN`/`VIEWPORT_BOTTOM_MARGIN` in `main.py` crop OCR calls to the gameplay viewport, excluding the HUD (health/mana, inventory, minimap, clock) at the top/bottom edges — item labels never render there, and that chrome is disproportionately expensive per pixel (small icons/numbers) for zero benefit. Measured effect: ~0.9s → ~0.42s per call, over 2x, for the cost of a slice (no extra processing). This is a general HUD-vs-viewport assumption applicable beyond Diablo II, not a hardcoded game-specific hack — but it IS an assumption: an item rendering very close to the top/bottom edge could go undetected; narrow the margins if that happens. A cheaper-input pre-filter (MSER, tried first) was measured and rejected: it cost ~240ms on its own against real gameplay, and the combined bounding box of all its candidates covered 99% of the frame (unrelated UI text scattered at the top and bottom forced it wide) — not worth its own overhead once measured, which is why the simpler fixed-margin crop is what shipped instead.

**`OCR_INTERVAL_SECONDS` must be well above a single OCR call's own cost, not near or below it.** Set too low (0.3s was tried and measured, back when a call cost ~0.9s pre-viewport-crop), the "wait between calls" throttle does nothing in practice — by the time one OCR call finishes, the interval has usually already elapsed, so OCR ends up running back-to-back on nearly every loop iteration. That starves `_relocalize_track()` (the cheap, fast tracking step that's supposed to keep the box glued to a moving/panning target) of any chance to run — confirmed via a loop-rate diagnostic print in `detect_text()` (`[detect_text loop rate: ...]`), which dropped to ~6-9 Hz at 0.3s vs ~19-21 Hz at `1.5`. Symptom when this is wrong: the box tracks fine while standing still (position isn't changing anyway) but loses or lags badly behind the target the moment the camera pans. Current value (`0.7`) is tuned against the post-viewport-crop call cost (~0.42-0.6s) — if the crop margins or OCR call cost change again, re-check this against the new real cost, don't just leave it.

**Time a periodic action's "next run" from when it *starts*, not when it *finishes*.** `last_ocr_time` used to be stamped after the OCR call completed — since the interval check is `elapsed_since(last_ocr_time) >= OCR_INTERVAL_SECONDS`, this meant the real gap between successive scans was `interval + the call's own duration` (~1.2s with `interval=0.7` and a ~0.5s call), not just the interval as intended, silently doubling worst-case discovery latency. Both versions look correct on casual inspection. Caught with a live diagnostic that measures the actual real-world gap between occurrences (`[scan-to-scan gap: ...]` in `detect_text()`), not just logging each occurrence — confirmed ~1.2s before the fix, ~0.7s (matching the interval exactly) after. Fixed by stamping `last_ocr_time` at the start of the call, so the interval can elapse *while* the call runs.

**`_relocalize_track()` must refresh its own reference patch on every successful match, not keep reusing the original OCR-time snapshot.** An earlier version always matched against the patch captured at the last full OCR refresh, however long ago that was. That's fine while nothing nearby changes, but real gameplay isn't static (flickering torches, animated water/grass, other moving characters) — the longer a reference patch goes unrefreshed, the more the live scene has drifted from it, degrading match confidence. Now each successful relocalization re-crops the patch from the *current* frame at the newly-found position, so the reference is always at most one loop iteration (a few ms) stale instead of up to `OCR_INTERVAL_SECONDS` stale.

**The position OCR returns is already stale by the time you get it — by the OCR call's own duration, not just "since the last loop tick."** The two fixes above weren't enough on their own; live logging (per-track `TRACK LOST` prints) showed relocalization failing almost immediately after nearly every OCR refresh, at very low confidence (0.08-0.30 — a genuine miss, not a near-threshold one). Cause: a single OCR call takes ~150-300ms, so the coordinates it returns describe where the item was *before* that call started — the first relocalization attempt has to bridge that entire call duration on top of a normal loop iteration, which is a much bigger gap than "one iteration's worth of movement." Fix in `detect_text()`: immediately grab one more frame right after OCR completes and relocalize against *that* before publishing, instead of leaving the OCR-time position to go stale until the next loop iteration. Also raised `TRACK_SEARCH_MARGIN` to `250` for headroom on the remaining steady-state gap. Re-verified with real gameplay logging: lost-track events dropped from nearly every refresh cycle to a small handful across a full test with heavy movement and direction changes. General lesson: any time a slow periodic call's result gets used as if it were "current," account for the call's own duration explicitly — don't assume the next scheduled step naturally catches up.

**Why OCR needs its own capture resolution**: `CAPTURE_SCALE` was dropped to 0.3 purely to speed up `matchTemplate` for icon matching. `detect_text()` briefly shared that same downscaled frame for OCR too — and broke text recognition entirely, because shrinking a 1280x800 screen to 0.3x leaves in-game text only a few pixels tall, well below what Tesseract can read. Template matching and OCR have fundamentally different resolution needs; sharing one frame between different-shaped detectors is a trap worth remembering when adding a third one later. Since OCR only runs a couple of times a second (`OCR_INTERVAL_SECONDS`), it can affordably run its own separate, much higher-resolution capture (`OCR_CAPTURE_SCALE`, currently `1.0`) without touching the fast path at all.

**Measured performance facts** (profiled on dev hardware — treat as directional, re-profile on real target hardware before trusting exact numbers):
- **Everything on a per-frame path runs on ONE channel, not three, and that is a free 5x — not a trade.** `TM_CCOEFF_NORMED` subtracts the mean and normalises across the whole patch, which on a multi-channel image makes it very nearly colour-blind already: measured against the real needle, a *fully desaturated* copy and copies hue-rotated by 30/60/90/120 degrees **all still scored 1.000 in colour**. Detection went 17.5ms → 3.2ms/frame and track relocalization 27-33ms → 5.7ms *per tracked item*, with false-positive headroom unchanged (best non-match 0.365 grey vs 0.353 colour, against a 0.60 threshold) and relocalization accuracy measurably *better* (20/20 vs 18/20 over perturbed cases). **If a detector ever genuinely needs colour to tell two things apart, that is a job for an explicit HSV pre-mask (see `legacy/vision.py`), which can express it — normalised cross-correlation cannot, so paying for three channels does not buy it.**
- `cv.matchTemplate` cost scales with frame area, not template size: in colour, ~43ms/call at 0.5x downscale (960x540), ~22ms at 0.35x, ~12ms at 0.25x. It is no longer the dominant cost now that it runs on one channel (~3.2ms at 0.3x); **capture is.**
- **Screen capture, not detection, is what sets the frame rate — and with `mss` it is GDI's blit, which no tuning reaches.** `sct.grab` alone is ~13.6ms/frame at 1920x1080, of which a raw GDI `BitBlt` is ~12.7ms; the whole capture thread is 16.0ms against detection's 3.2ms. It is **not** vsync — this dev display runs at 239Hz, so the "suspiciously close to one refresh" reading recorded earlier was a coincidence. `CAPTURE_SCALE` does not touch it (the grab is full-resolution regardless; the resize is 0.3ms), and downscaling GDI-side with `StretchBlt` measured 12.3ms — i.e. all of the cost is the blit and none of it the readback. The way past it is a different frame source, which is what `frame_source.py` exists for. **Wrap `mss`'s buffer with `np.frombuffer(img.raw, ...)`, never `np.array(img)`** — the latter copies the whole ~8MB BGRA frame through the array interface every frame (~4ms, and 400MB/s of memory bandwidth every other thread then shares). It is a *view* over a buffer the library may reuse, so consume it before the next `grab()`. Going below this floor would mean capturing a smaller region or an OS-specific backend — not worth the portability cost without a concrete reason.
- **When two cheap operations commute, do the one that SHRINKS the data first.** Downscaling before stripping alpha rather than after is bit-for-bit identical output (verified: max difference 0 over a full frame) and runs the colour conversion over 576x324 pixels instead of 1920x1080.
- **A resize or convert with identity parameters is real work.** `cv.resize` at `fx=1.0` is a full-resolution copy, not a no-op — it cost ~3.7ms on every OCR-thread capture to produce an identical array.
- Measured and **rejected**, so it does not get re-tried: grabbing small sub-regions around each track instead of the whole screen (one 700x530 grab is 6.3ms vs 17.3ms full-screen, but *three* cost 22ms — per-call overhead dominates, so it only pays at one track); and capping OpenCV's thread count to leave CPU for the game (`matchTemplate` barely parallelises here — 3.12ms at 16 threads vs 3.26ms at 1).
- `CAPTURE_SCALE` (currently `0.3`) is the tuning knob for the image-matching accuracy/speed trade-off — lower is faster but shrinks small on-screen items toward unrecognizable.

### `overlay.py` — transparent, click-through output layer (Windows-only for now)

Replaces showing a separate mirrored debug window: `Overlay` is a borderless, always-on-top Tk window using two Windows-specific tricks layered together — Tk's `-transparentcolor` attribute (a real Windows Tk feature: makes one chosen color both invisible and click-through) for the background, plus a Win32 `WS_EX_TRANSPARENT` style bit (set via `pywin32` after the window exists) so that even the drawn green box outlines never intercept a click — input always reaches the game underneath. Neither trick exists on macOS; `Overlay.__init__` raises `NotImplementedError` there, and `main()` catches that to fall back to `run_debug_window()`. A real macOS overlay would need a different implementation (e.g. an `NSWindow` via `pyobjc` with `ignoresMouseEvents` and a clear background) — nobody should try to make the Tk approach itself cross-platform, the mechanism is inherently OS-specific.

This mechanism has bitten twice already; both fixes are live in `Overlay.__init__` now, but re-verify both properties (see-through **and** click-through) if this code is touched again — testing only one can pass while the other silently regresses, since they're governed by different pieces of Win32 state:
- **Renders solid black instead of see-through**: calling `win32gui.SetWindowLong` to add `WS_EX_TRANSPARENT` after Tk has already set up `-transparentcolor` resets the layered window's transparency data, because Tk has no idea the window was touched behind its back. Fix: immediately re-assert it via `win32gui.SetLayeredWindowAttributes(hwnd, colorkey, 0, win32con.LWA_COLORKEY)` right after the `SetWindowLong` call.
- **Looks transparent but doesn't click through** (mouse input hits the overlay instead of the game/window underneath): two compounding causes. (1) `winfo_id()` can return an inner Tk drawing window rather than the actual outer OS-level frame that governs hit-testing — styling the wrong (child) window silently does nothing, so walk up via `win32gui.GetParent()` first. (2) Even on the right HWND, `SetWindowLong` alone doesn't reliably make Windows re-evaluate hit-testing for the new style — force it with `win32gui.SetWindowPos(hwnd, None, 0, 0, 0, 0, SWP_NOMOVE | SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE | SWP_FRAMECHANGED)` right after. Verified with an isolated test harness (a plain Tk window with a click-counting button, overlaid and clicked via `pyautogui` at a known screen coordinate on a monitor away from any real game window) — visual screenshot inspection alone can't catch this class of bug, since the overlay looks identical whether clicks pass through or not.

**The overlay's repaint rate is capped independently of detection FPS (`BOX_REDRAW_HZ` 30, `PANEL_REDRAW_HZ` 10), and that decoupling is the point.** `run_overlay()` redraws once per detection frame, so making detection faster silently made this window repaint more often — measured, box repaints went 34/s → 51/s purely as a side effect of an FPS optimisation. This is a fullscreen always-on-top **layered** window, the most expensive kind to repaint, and each repaint makes the compositor redo the whole screen — a cost paid by *the game underneath*, not by us, so it never appears in our own FPS number. It surfaced as cursor flicker (`Error_history.txt` #38). These are **display-only** rates: nothing reads the screen to make a decision (auto-collect reads `shared_text_tracks` directly), so detection, tracking and actions are untouched. Two non-obvious details: a skipped repaint must **not** record its content as drawn, or a box that stops moving right after a skipped frame is stranded at a stale position forever; and a cap can only land on `caller_rate/N`, so 30Hz against a 51Hz caller really means ~25Hz. The panel gets the lower cap because it is much the more expensive layer — 1.17ms per repaint against 0.35ms for boxes, since every label is drawn nine times to ring it in black.

**Measured, and *not* a problem: the overlay does not delay clicks.** End-to-end (a real click issued → the handler of a window underneath actually running, with the overlay repainting concurrently), `WS_EX_TRANSPARENT` routing costs ~0.1ms — no overlay 0.7ms median, overlay repainting at 51Hz 0.8ms, both mouse buttons. Recorded so nobody hunts there again. If clicking ever *does* feel delayed, suspect compositor load (above) or `run_auto_collect()` physically taking the mouse — 17 items in `targets.txt` are marked `*`, and while one is on the ground it moves the cursor and clicks every 0.8s for up to 5s (`F4` snoozes it).

**The panel plate is sized to its measured content, not to a constant.** `PANEL_WIDTH` (300) is a **minimum**; `draw_panel` measures the title and every row with the real Tk font metrics and grows the plate to fit. It was a fixed width, which was fine while every value was a percentage — but a row's value column starts at `PANEL_VALUE_OFFSET` (232px), so anything past about seven characters hung off the right-hand edge and rendered **in colour, over the game, outside the plate**. Reported for `not on screen (0.30)` (needs 392px); measuring also revealed `NOT CALIBRATED` (384px) and `window not found` (336px) had been spilling unnoticed. A bigger constant would only move the problem, so the fix is to measure. It stays a *minimum* because a plate sized purely to content would visibly jitter as an ordinary reading went `9%` → `100%` — verified, normal and stale states both land at exactly 300px. `test_overlay.py` checks every panel state main.py can produce.

`Overlay.draw_panel(title, rows)` draws an optional read-out panel (labels + bars + numbers) on the left of the same window, as a **separate canvas layer** — boxes are tagged `"boxes"` and the panel `"panel"`, and each is deleted and redrawn on its own, so the two never erase each other and each keeps its own skip-if-unchanged check. `main.py`'s `_debug_panel()` is what fills it (HUD meter readings; `'F5'` toggles it), but `draw_panel` itself knows nothing about game state — only labels, fractions and colors — so it can display anything later.

Note that the overlay is part of the composited screen, so `mss` captures it and **the panel's own text passes through OCR on every scan**. Checked: none of `GAME STATE`/`health`/`mana`/`no read`/`run calibrate_meters.py` matches any target, so it can't cause a false positive — but re-check that if panel wording changes, and keep in mind the plate does occlude whatever is behind it, so an item label under it won't be seen (`PANEL_TOP_FRACTION` moves it).

**`TRANSPARENT_COLOR` is near-black (`#010203`), not the traditional magenta, and that is a correctness choice.** The key colour is what antialiasing smears around every piece of text on the overlay, because it is what sits beneath the glyphs wherever the plate is stippled. With magenta that produced a visible red glow around every word. Blacking out the ring with an outline only moved the glow one pixel outward — the outline's own edges then blended into the magenta. A visually-black key makes the smear read as an ordinary drop shadow, fixing it everywhere at once instead of per-element. Measured over a neutral backdrop: mean red-and-blue over green went from **+36.8 to +0.5**. It is `#010203` rather than `#000000` so that genuinely black drawings (the text outline) stay visible — only the exact value disappears. **The constraint is inverted from what it used to be**: magenta is now a perfectly usable box colour, and near-blacks are the ones that would silently vanish. `NAMED_COLORS` in `text_detection.py` is annotated accordingly.

**The panel plate is stippled to ~50% (`PANEL_BG_STIPPLE`). Its text used to be ringed in black as well (`PANEL_TEXT_OUTLINE_OFFSETS`); that ring is now OFF, and the reason it was ever needed is the reason it no longer is.** There is no alpha to set here: the window's transparency is a colour *key*, so a pixel is either fully invisible or fully opaque. A `gray50` stipple paints every other pixel and leaves the rest as the key colour, which is how translucency has always been done on colour-keyed surfaces; measured 47% see-through. But it punches magenta holes directly behind every glyph, which brings back the pink-text problem below in a subtler form — measured, a grey `(220,220,220)` label averaged `(208,159,207)`. Painting the eight neighbouring offsets in black first fills exactly the ring of pixels the antialiasing samples, dropping magenta fringing from 20% of lit pixels to 2.8%. **That reasoning was all written while `TRANSPARENT_COLOR` was magenta, and it stopped applying when the key moved to near-black (`#010203`) — the smear behind every glyph is now already dark, so the ring was painting black next to black.** Re-measured on real renders over both a dark and a bright backdrop: 8 offsets vs 4 vs none gave glyph contrast 183.7 / 183.6 / 183.4 and 181.3 / 181.0 / 180.4 respectively, with an identical count of lit pixels — no benefit left to keep. It was not free, either: drawing every label nine times made the panel 1.66ms per repaint against 0.605ms without, and the panel is the overlay's most expensive layer. **`PANEL_TEXT_OUTLINE_OFFSETS` is empty now; if `TRANSPARENT_COLOR` is ever moved back to a saturated colour, put the eight neighbours back with it — the two settings are coupled, and only one of them is obvious from the symptom.** If you make the plate solid the ring is unnecessary regardless; if you make it more transparent it only matters again for a saturated key.

**Boxes are not repainted for jitter (`BOX_MOVE_DEADBAND_PX`, 4px).** Detection runs at `CAPTURE_SCALE` 0.3, so coordinates are scaled back up 3.33x on the way to the overlay — one pixel of `matchTemplate` jitter on a *completely stationary* item becomes a 3-4px jump on screen, which fails an equality check and forces a fullscreen layered-window repaint every frame, forever. Measured, a stationary-but-jittering item went from ~25 repaints/s to 0.3. The comparison is against the last **drawn** position, so genuine slow drift accumulates and is never ignored indefinitely (verified: a box creeping 2px/frame stays within 4px of truth rather than falling behind). The trade: the box does *not* snap to its exact position when movement stops — it settles up to 4px out. That is display-only; auto-collect clicks coordinates from `shared_text_tracks`, never from the drawn box.

**The panel has a dark backing plate, and it needs one — don't "clean that up".** The window's transparency is a color *key*, not real alpha: a pixel is either exactly `TRANSPARENT_COLOR` and fully invisible, or fully opaque. Text drawn directly onto that background gets antialiased by Windows' subpixel font rendering **against magenta**, and on thin 11px glyphs the magenta fringe dominates the stroke — measured on a real render, the glyph cores were exactly the requested `(220, 220, 220)` but the mean lit pixel came out `(204, 140, 201)`, i.e. visibly pink. A black 1px text shadow was tried first and wasn't enough. The dark plate gives the text something sane to blend into. Detection boxes don't need this (a 2px rectangle outline isn't antialiased the same way, and covering the game where an item lies would defeat the point). Because the plate is the first fully opaque thing this overlay has ever drawn, click-through was re-verified specifically over it — `WS_EX_TRANSPARENT` covers the whole window regardless of pixel opacity, confirmed with the button-under-the-overlay harness, not assumed.

Because the overlay is click-through by design, it can never hold keyboard focus — a normal Tk key-binding for quitting silently wouldn't fire. Quitting instead uses a **global hotkey** via the `keyboard` package (`main.py`'s `run_overlay()`, bound to `'End'`), the same pattern `legacy/pindle.py` already used for its own hotkey. `'End'` (not `'q'`) was chosen deliberately since ordinary letter keys get pressed constantly during real gameplay — a global hotkey on one would quit the program by accident.

### `text_detection.py` — OCR-based detector

This is the first concrete instance of the "detector" seam called out in Design Priorities above — a second way to find things on screen, independent of and unknown to the image-matching code. It exists because image templates don't scale to "watch for hundreds of item names": each new template needs its own `matchTemplate` pass, so cost grows **linearly** with vocabulary size, while OCR's cost is **constant** regardless of vocabulary size (read the text once, compare the result against a list — nearly free). This was measured directly, not assumed: a single `matchTemplate` call at OCR's native-resolution viewport costs ~21ms, so 20 templates/frame (~424ms) already roughly equals OCR's cost, and 80 templates/frame (realistic for ~40 items with a couple of color-rarity variants each) costs ~1.7s — over 3x slower than OCR. **Template matching only wins below roughly 15-20 total templates; above that, and especially at "hundreds of items" scale, OCR is the correct architecture** — this is why OCR call *speed* (below) was worth investing in rather than switching detectors when more raw speed was needed.

**The frame is binarized before it reaches Tesseract, and this matters more than every cutoff in this module put together.** Tesseract expects a scanned page — dark text, light background, no texture. A game frame is the opposite: thin bright glyphs over dark, noisy, high-detail art. Measured on a real Diablo II frame containing five plainly legible rune labels, Tesseract read **zero** of them and returned 57 junk fragments scraped off the terrain instead; binarizing first read four of the five. This was the actual cause of a long "it stopped detecting" hunt that was initially misdiagnosed twice as a matching-cutoff problem — **no cutoff can rescue a line that was never read.**

It is also *faster*, which is not the usual direction for an accuracy fix: Tesseract's cost scales with how much candidate text it thinks it can see, and thresholding deletes the texture generating all those false candidates. Same frame, measured: **362ms → 51ms, 83 words → 7**. A full `find_text_matches()` call went 374ms → 67ms.

`_preprocess()` has three modes and defaults to `PREPROCESS_AUTO`, which picks per frame from its median brightness (subsampled every 8th pixel — it only has to be roughly right to choose a branch). This is what keeps the rule from being a Diablo II hack: "light text on dark" equally describes subtitles, HUDs, dark-themed apps and night-time signage, while a document or light-themed window is the exact opposite and must **not** be inverted. Verified on all four (white page/black text, light grey/dark text, dark terminal/light text, black game screen/bright text) — auto chooses correctly and all four still match. It never rescales, so Tesseract's box coordinates still refer to the caller's original pixel grid and need no translation.

`BRIGHT_TEXT_THRESHOLD` (150) is the knob. Tuned on real gameplay: 130–160 all worked, below 120 let terrain back in, above 170 dropped the fainter labels. If a label is legible in `ocr_diagnostic_N.png` but gone in `ocr_diagnostic_N_prepared.png`, that is the number to lower.

`find_text_matches()` makes **exactly one** OCR call per invocation, over the whole frame, using the same word/line-grouping approach regardless of backend (`_group_words_by_line()`) — deliberately not one call per candidate region. An earlier version cropped candidate regions (found via OpenCV's MSER detector) and OCR'd each separately; since each OCR call pays a fixed overhead regardless of image size, calling it per-region (up to a dozen times a frame) multiplied that overhead into a 10-20x FPS hit. Recognized text is cleaned and fuzzy-matched against `assets/targets.txt` (one item name per line — this is the file to edit when adding new items to watch for, no code changes needed).

**Matching happens against contiguous word-runs within a line, not the whole line** — for each Tesseract-grouped line, every contiguous span of words (single word, first two words, etc.) is tried against every target name, and the returned box covers only the words in the best-scoring span, not the whole line. This isn't just for detection accuracy: games often render something else on the same line Tesseract perceives right next to/below an item's name (e.g. D2R's "Rune" suffix under a rune name), and Tesseract's line/paragraph grouping doesn't consistently include or exclude it between OCR passes. Matching (and boxing) the whole line made both correctness and the resulting box unstable — a short name like "Gul" could fail to match a line OCR'd as "GUL RUNE" outright (see the cutoff discussion below), and on passes where it did match, the box size (and therefore where auto-collect's mouse click lands) would jump around depending on whatever else got swept onto that line that pass. Matching is not done via `difflib.get_close_matches()`, since it only accepts one cutoff for every candidate — see `_match_ratio()` just below for why that isn't good enough here.

**A target name is matched word by word, never as one whole string — a word shared between many target names otherwise drags a completely wrong one over the cutoff.** difflib's ratio is `2*matched / (lenA+lenB)`, so for names that share a generic word, that word can be most of the string: `"RAL RUNE"` scores exactly **0.75** against `"JAH RUNE"`, `"LEM RUNE"` and `"GUL RUNE"` — the shared `" RUNE"` is 5 of the 8 characters and clears a 0.75 whole-string cutoff on its own, whatever the other word says. Names already in the list cross-matched each other the same way (`"KO RUNE"` vs `"LO RUNE"` = 0.857). **No whole-string cutoff can fix this** — `"RAL RUNE"` and `"JAH RUNE"` genuinely *are* 75% identical as strings; the information that separates them is *which* word differs, which is only visible word by word. So `_match_ratio()` requires every word of the name to clear its own length-scaled cutoff (`_required_cutoff()`: exact at length ≤ 3, the base cutoff above that), and only then returns the whole-string ratio for ranking. Differing word counts fall back to a space-stripped compare that must clear `MERGED_WORD_CUTOFF` (0.9) — deliberately **stricter** than the per-word path, because it has no structure left to verify. A genuine merge or split preserves every character and scores near 1.0; what the floor keeps out is a candidate that is merely a *prefix* of the name. Since every contiguous run of words on a line is tried, the single word `"FLAWLESS"` off a **Flawless Diamond** was scoring 0.8 against `"FLAWLESSRUBY"` and being reported as a Flawless Ruby, with the box drawn round just the word "Flawless". A whole missing word is not a transcription artifact and must not be forgiven like one. (Original note: Tesseract sometimes merges or splits words — `"JAHRUNE"`, `"REJUVEN ATION"`) fall back to a space-stripped whole-string compare at the strictest of the name's per-word cutoffs, so a merge isn't itself counted as a difference.

**A duplicate name in `targets.txt` warns, because silently letting the last one win hid a real bug for a version.** `Rejuvenation Potion` was listed twice — once as a normal target near the top of the file and once as a `-` look-alike far below — so the look-alike overwrote the target and the item was matched and then discarded on every frame. **From outside that is indistinguishable from "OCR cannot read this"**, which is a completely different problem to go hunting for, and it silently dropped the `[purple]` colour too. The file is hand-edited, long, and its two halves are far enough apart that nobody sees them at once — precisely where a plain dict assignment quietly discards what someone wrote. Last-one-wins is kept (predictable, and the warning names both line numbers) rather than guessing which line was meant. **That look-alike entry was also obsolete**: it predated span ranking becoming `(words matched, ratio)`, which already makes a three-word `Full Rejuvenation Potion` line outrank its own two-word tail — verified, both lines resolve at 1.000 with no tie, so the small potion is now a normal target. **When a look-alike entry stops being necessary, delete it** — an `ignore` entry for a name you actually want reported is invisible from the outside.

**Fuzzy matching always returns the CLOSEST LISTED name, so anything on screen that resembles a target but isn't listed gets attributed to whichever target it happens to resemble most.** This is the single most important property of this module to understand, and it is the root cause of the `"Ral Rune"` → reported-as-`"Jah Rune"`-and-clicked bug. A short distinguishing part plus a shared suffix makes it acute: `"RAL"` and `"MAL"` are one substitution apart, so no cutoff can tell a *misread* `"MAL"` from a *correctly read* `"RAL"`. The fix is not a cutoff — it is to make the vocabulary complete. `assets/targets.txt` supports a **leading `-`** meaning "match this, then throw it away": the look-alike now wins its own match at 1.000, outscoring the 0.875 it would have scored against a real target, and is then dropped. All 16 low runes are listed that way. **Deleting those lines brings the false positives straight back**, which is why they carry a comment saying so. This generalises to any vocabulary with a shared suffix and a short distinguishing part — product codes, license plates, station names.

**Cutoffs assume a stylized game font, because that is what real input looks like.** Diablo II's is Exocet-derived and Tesseract was trained on conventional print faces, so a systematic one-character misread is the *normal* case, not bad luck — `"GUL"`→`"GU1"`, `"BER"`→`"8ER"`, `"VEX"`→`"V3X"`. `_required_cutoff()` therefore allows exactly one bad character in a 3-letter word (0.65), requires 2-letter and shorter to be exact, and gives everything longer the plain base cutoff. That tolerance is only safe **because** the look-alikes are listed — the two mechanisms are a pair, and loosening the cutoff without a complete vocabulary (or vice versa) breaks in one direction or the other.

Two calibration mistakes already made here, both worth not repeating. First: a stricter tier (0.9 up to length 6) was carried over unchanged from when this ladder applied to whole *names* rather than single *words*. Per word it meant `"RUNE"`, `"FULL"` and `"POTION"` had to be read perfectly, which killed detection in live play. **When a threshold is repurposed from a whole string to each of its parts, its value has to be re-derived, not carried across.** Second: requiring 3-letter words to match exactly — correct in isolation, but it assumed clean OCR, and against the real font almost every rune stopped being detected. **Neither mistake was visible from synthetic test strings; both needed the real font to show up.**

**Short words are compared by character POSITION, not by difflib.** `_word_ratio()` uses positional agreement for equal-length words of ≤ 3 characters and difflib for everything else. difflib's ratio counts *how many* characters two strings share, not *where* they are, which on a 2-letter word throws away the only information present. Measured on a real frame: Tesseract read `"Ko Rune"` as `"Ke RUNE"`, and difflib scored `"KE"` **0.5 against both** `"KO"` (a genuine one-character misread) and `"EL"` (nothing alike, it just also contains an E) — they tied, the match was discarded as ambiguous, and a Ko Rune went uncollected. Positionally, `"KO"` scores 0.5 and `"EL"` scores 0.0. **This is the better model of what OCR does**: it substitutes a character in place, it does not transpose or shift. difflib's order-preserving subsequence matching is built for edits that move text around — the wrong tool for a misread glyph. Longer words keep difflib, where a dropped or doubled letter (which really does shift the rest) is common enough to matter.

**Candidate spans are ranked LONGEST-MATCH-FIRST, with the similarity ratio only breaking ties** — the sort key is `(words matched, ratio)`, in that order. Ratio-first is wrong whenever one target's name contains another's, which the look-alike mechanism makes routine: a cleanly read `"Full Rejuvenation Potion"` scores 1.000, and so does its own tail `"Rejuvenation Potion"` against the look-alike entry, so ratio-first tied them and suppressed the item; read as `"Fvll Rejuvenation Potion"` the full span drops to 0.958 while the tail still scores 1.000, so ratio-first picked the look-alike and reported nothing. A shorter span is not better evidence just because it scores higher on the little it covers. A long sloppy span can't win by accident either, since every span must already clear each per-word cutoff (and `MERGED_WORD_CUTOFF`) to be eligible. **Watch the shape of this bug**: a slightly misread label kept working while a perfectly read one failed, so better OCR made detection worse — which is exactly backwards from where anyone would look.

**A tie between two different targets is reported as nothing, never as a guess.** `find_text_matches()` tracks every target tied at the best score and suppresses the line if more than one is left standing. This is what makes the very loose short-word cutoffs (0.5 at two characters, 0.65 at three) safe: they permit roughly one bad character per word, and anything that stays genuinely undecidable afterwards is dropped rather than guessed. It earns its keep on real input — a bare `"RUNE"` ties across `EL`/`IO`/`KO`/`LO`/`UM` and is suppressed instead of being assigned to whichever happened to be first in the dict.

**Two diagnostics, for two different questions.** `python tools/diagnose_ocr.py` is the first thing to reach for when something on screen isn't detected: it captures through the exact path `detect_text()` uses (same monitor, same `OCR_CAPTURE_SCALE`, same viewport crop), prints every line Tesseract read and why each did or didn't match, and saves the viewport PNG. It exists because "it isn't detecting" has three causes that look identical from outside — Tesseract never saw the text (a capture/contrast problem, no cutoff will fix it), Tesseract misread characters (a font problem), or the text was read fine but nothing matched (a cutoff problem). Guessing between them wastes a lot of time. `MATCH_DEBUG = True` in `text_detection.py` is the same breakdown printed live during a normal run; off by default, far too noisy to leave on during play.

Even with all this, a short name can still get a genuine false-positive OCR read (Tesseract literally outputting the 3-letter string by misreading unrelated pixels) that no cutoff tuning can catch, since it isn't a fuzzy-match problem at that point — Tesseract's own per-word confidence score (currently read but discarded in `_get_words_tesserocr`/`_get_words_pytesseract`) is the next lever if that becomes frequent.

**Two OCR backends, tried in order at import time**, both producing the same normalized `(text, left, top, width, height, block_num, par_num, line_num)` word list before a shared `_group_words_by_line()`:
1. **`tesserocr`** (fast path) — talks to the Tesseract engine in-process via compiled bindings, reusing one long-lived `PyTessBaseAPI` instance (`_tesserocr_api`, module-level) across every call. Measured **~3.5-4.5x faster** against real gameplay (~0.1-0.26s vs ~0.42-0.6s per call) — this isn't just subprocess-launch overhead disappearing, it's also skipping the temp-file I/O round-trip pytesseract's subprocess model requires and, most importantly, not re-initializing the whole Tesseract engine from scratch on every single call the way a fresh subprocess would. `GetTSVText(0)` returns the exact same column layout as `pytesseract.image_to_data`'s DICT output (level/block/par/line/word numbers, left, top, width, height, confidence, text) — level `5` rows are actual words; other levels are page/block/paragraph/line placeholder rows with no text.
2. **`pytesseract`** (portable fallback) — used if `tesserocr` isn't installed (no matching prebuilt wheel for the current Python version/platform — see `requirements.txt`) or its `PyTessBaseAPI` init fails for any reason. Slower, but works anywhere the Tesseract binary itself is installed, regardless of platform or Python version.

`tesserocr` needs a **prebuilt wheel matching the exact Python version and platform** — there's no PyPI wheel for Windows (only a source distribution requiring a full C++ build toolchain + Tesseract dev libraries, which failed here — see `Error_history.txt` #15). The prebuilt wheels at `github.com/simonflueckiger/tesserocr-windows_build` cover current Python versions including very new ones (this project used the Python 3.14 wheel the same day 3.14 was current). It also needs `_find_tessdata_dir()` to locate the `tessdata` folder (currently only auto-detects the default Windows Tesseract install path) — separate from `pytesseract.pytesseract.tesseract_cmd`, which points at the `.exe`, not the data folder.

`_padded_box()` pads a matched word-run's bounding box by `LABEL_PAD_X`/`LABEL_PAD_Y` before returning it — Tesseract's word boxes cover only the text glyphs, but D2R (and most games) render a semi-transparent background panel behind item labels that's visibly larger than the text itself, so an unpadded box looks noticeably too small next to it. This is a fixed pixel margin, not automatic panel-edge detection (e.g. via color/contour analysis around the text) — deliberately, since D2R's panel is often similar in darkness to the surrounding terrain (dungeons, caves), making "find the edge of the dark rectangle" unreliable across different scenes. Values are estimates from visual testing against real gameplay; re-tune if the box still doesn't match the panel.

Tesseract itself is a separate program, not a pip package (see `requirements.txt` for per-OS install instructions) — `pytesseract` just shells out to it. Two layers of defense against that external dependency being unreliable: `text_detection.py` checks once at import time whether Tesseract is installed at all and disables text matching (one-time warning) rather than crashing; and each individual OCR call is wrapped in a `try/except TesseractError`, because the installed Windows build has been observed to intermittently throw a spurious `TesseractError` (an "ObjectCache leak" warning during its own internal cleanup, unrelated to whether OCR actually succeeded) — that's treated as "skip this scan," not a fatal error.

Call-site throttling (how often `find_text_matches()` gets called at all) is `main.py`'s job via `OCR_INTERVAL_SECONDS`, not this module's — see `detect_text()` above.

### `game_state.py` — HUD meter reading (health/mana orbs)

The third instance of the "detector" seam, but a **different shape of answer** from the other two. Template matching and OCR both answer *"where is this thing?"* (box + center point). This answers *"how full is this thing?"* — a single `0.0`–`1.0` reading. That's the input a decision layer actually acts on (drink a potion below 40%, disengage below 25%), and nothing in the project could read a number off the screen before this.

Deliberately game-agnostic: a `Meter` is a screen region + a color + a fill direction, which describes a health orb, a mana bar, a stamina strip, or a robot's battery gauge equally well. All the game-specific knowledge (where the orbs are, what color they are) lives in `assets/meters.json`, generated by `calibrate_meters.py` — same "edit data, not code" philosophy as `targets.txt`. `region` is stored as **fractions of the screen, not pixels**, specifically so one config stays correct at any capture scale — that's what keeps this from becoming another shared-resolution-constant trap (`Error_history.txt` #6).

**It reads off the frame `detect_objects()` already captured, and does not get its own thread.** This is the opposite call from OCR, and for a concrete measured reason: reading two orb meters costs **0.15ms/frame** (about 0.7% of the frame budget at 45 FPS), whereas a dedicated thread would have to spend ~17-20ms on its own `mss` capture to perform a ~0.3ms measurement. OCR earned its own thread because a single call costs ~100-260ms; this doesn't come close to that bar. Results are published to `shared_game_state` behind a lock and read via `current_game_state()`.

The debug panel (`'F5'`) is the live read-out of this while the game is running — one row per meter in `meters.json`, no code change needed to show a newly calibrated one. It preserves the `None`/`0.0` distinction visually: a failed read shows `no read` with **no bar at all**, an empty meter shows `0%` with a bar at zero. It also reports staleness (`STALE 4s`), since a frozen number looks exactly like a correct one.

**A meter can change COLOUR to signal a status, and that is not cosmetic.** Diablo II turns the health globe **green** while poisoned. With only the red ranges configured, the orb read **0% at every real fill level** the moment poison landed — so a decision layer would see "you are dead" at 90% health, during the one situation where the number matters most and while it is actively ticking down. This is why `hsv_ranges` is a *list*: a meter needs one range per colour it can legitimately be, OR-ed together. The health preset now carries red, red-wrapped, and green. Verified on synthetic orbs — with green added, a green orb reads the same 94.9/87.2/50.3/27.2% at 100/90/50/25% fill as a red one, so it costs the healthy reading nothing. Generic, not a Diablo detail: any game that recolours a bar (poisoned, cursed, shielded, overhealed) has this, as does a battery gauge that turns red when low. **When a meter reads 0% but you can see it is not empty, suspect a colour change before suspecting the geometry.**

**Calibration is stored as one profile per window shape** (`game_state.Profile`, `select_profile`, `upsert_profile`). A game re-lays out its HUD at a different resolution or aspect ratio, so one set of regions cannot serve every mode. Calibrating at a new size **adds** a profile; calibrating at a size already present **replaces** it, so re-running to fix a badly drawn box does the expected thing rather than accumulating stale duplicates. Selection is exact-size first, then any profile with the same aspect ratio within `ASPECT_TOLERANCE` (so one 1280x800 profile also serves 1600x1000, and a 1920x1080 one serves 3840x2160). A window shape with no matching profile selects **nothing** rather than the nearest — the panel shows `NOT CALIBRATED` with the sizes that do exist. `load_profiles()` also reads the older single-profile file shape, so existing configs keep working.

**The surface test is vacuous at the bottom of the band, and one stray row read as a real value.** `SURFACE_CONSISTENCY` asks "are the rows below this one filled too?" — which a row at the very bottom passes trivially, because there are none. `MIN_SURFACE_SUPPORT_ROWS` (1) requires enough rows beneath a candidate surface for that test to have meant anything. Seen live: the Diablo II **lobby**, where red character names sit where the health orb would be, read **2% health** and fired an emergency potion — 2% being exactly one row at 0.3 scale. **The value is measured, not picked**: at 1 the full-resolution reading is completely unchanged (a real 2% orb still reads 2%) while the artifact is gone; at 2 a real 7% orb at 0.3 scale starts reading `None` for no extra protection against a single row, which is the wrong trade — a missed low-health reading kills a character, while a spurious one in a lobby presses a key that does nothing. At `CAPTURE_SCALE` 0.3 the floor lands at ~7% of real fill, which is the honest cost and the reason `main.py` reading meters from a higher-resolution frame is worth doing later. Watch for `consistent[-0:]`, which is the *whole* array — a support of 0 would silently make every meter unreadable.

**`None` and `0.0` are different answers, and the module broke its own rule in the one function every reading passes through.** `_fill_fraction()` had two `return 0.0` branches — "no filled rows found" and "filled rows found but no coherent surface" — and neither was a measurement. Both are what an **absent** meter looks like through a colour mask (the Diablo II lobby has no orbs at all) and what a **dimmed** one looks like (the in-game menu darkens the screen; measured on a real screenshot, the orb region's mean V was 34 against the configured `V >= 40` floor, so the mask went patchy while the orb was visibly full at 1131/1228 life). Both now return `None`. **This cost nothing, which is why it is a fix and not a trade: a measured reading can never be exactly `0.0` anyway** — the surface row is at most the last row of the band, so the smallest measurable value is `1/height`, about 0.7% on a 150px orb, verified across synthetic fills from 0.5% to 100%. Every `0.0` the system ever produced came from a failure branch. The only behavioural change is that an orb below ~1% reads "unknown" instead of "empty". See `Error_history.txt` #40 — and note the direction the old bug ran: the failure value happened to be the most alarming number in the domain, so an unreadable sensor read as maximum urgency and drove the potion layer. **A sensor that must fail into a number has to fail toward "do nothing".**

**`None` and `0.0` are different answers and must stay different.** `None` means "couldn't read the region"; `0.0` means "the orb is empty." A consumer that conflates them will treat a failed read as "you are about to die" and act on it. The `Smoother` preserves this too — a failed read never enters the median history, it reports the last good value instead.

**A failed read carries the last good value, but not forever, and the cap is what makes the guard real.** Two very different things arrive at `Smoother` as `None`: one frame failed (torn capture, a tooltip over the orb), where carrying is right because a consumer that stops on every dropped frame is useless; or we are not looking at the thing at all (alt-tabbed, window closed, camera unplugged), where carrying produces a frozen number that *looks* live and gets acted on with full confidence. Nothing in a single reading tells them apart — only how long it persists. So the carry is capped at `MAX_CARRIED_FAILURES` (15, about a third of a second at 50 FPS), after which the meter reports `None` and drops its history, so a good frame arriving after a gap is not median-blended with values from before it. **A staleness timestamp does not cover this**: a caller publishing every frame keeps the timestamp fresh, because it is the *reading* that went stale, not the publishing. This was found by probing what the foreground guard actually delivered to a consumer — the guard set `raw` to all-`None` and the Smoother turned it straight back into the last good value, indefinitely.

Readings are **median**-smoothed over 5 frames, not averaged: the failure mode is one frame being wildly wrong (a tooltip drawn over the orb on hover, a spell effect flashing the same color across the HUD), and a median discards such a sample outright while an average absorbs part of it into the result.

Two traps in the measurement itself, both caught by synthetic testing before this ever ran live, both documented at length in `Error_history.txt` #19 and #20 — **read those before touching `_fill_fraction()`**, because both are the kind of bug that looks correct under casual testing:
- **Measure fill by HEIGHT, never by pixel count.** A pixel count measures *area*, and for a circle area equals height only at 0%, 50% and 100%. A 25%-full circle is 19.5% full by area. The error is therefore largest exactly when a health reading matters most, and zero at the midpoint where you'd casually test it.
- **Find the liquid surface with a global consistency test, not a local walk up from the bottom.** Games draw a specular highlight streak across a globe; where it crosses the liquid it blanks out a run of rows, and a local walk stops dead there and reports the streak's height (a 65% orb read as 25%). The surface is instead the highest row that is itself filled *and* has ≥ `SURFACE_CONSISTENCY` of the rows below it filled.

### `presence.py` — "is this reference art on screen?", and why colour could not answer it

The fourth instance of the "detector" seam, and a **third shape of answer**. Template matching says *where* (box + centre), `game_state.py` says *how full* (a 0–1 number), and this says **whether the thing is there at all** (a boolean). That third answer is what a consumer needs before it can trust either of the other two.

**It exists because a colour test provably cannot do this job.** The health meter matches red. The Diablo II lobby renders other players' names and red armour *exactly where the health orb belongs* — measured, **7.3% red pixels in that region** — and periodically enough of them line up to read as a real 2–4% health. That fired an emergency potion; and because a lobby has a text field focused, the keypresses were **typed into the game name** (observed: `z25pin232321213`). Red text and red liquid are the same colour, so no threshold, floor or consistency test separates them. **The only way out is evidence of a different kind**, which is what matching fixed HUD art provides. Measured separation on real frames:

| frame | score |
|---|---|
| actual gameplay | 0.841 |
| ESC menu (HUD still drawn — correctly still "in play") | 0.886 |
| lobby A | 0.269 |
| lobby B | 0.325 |

Threshold `0.6`, margin **0.516**. `test_presence.py` asserts that margin, so a change that erodes the guard shows up as a failure rather than as a potion typed into a text box.

**TWO references, on opposite corners, and either one is enough.** One was fragile to anything covering it: hovering an item draws a tooltip over the right-hand orb, the score fell to **0.48**, and the pipeline decided it was not in a game and paused everything — while the left orb sat in plain view. Occlusion during play is normal and **local** (tooltips, panels, spell effects), so the answer is a second piece of evidence somewhere else, not a looser threshold — a looser threshold trades away the very thing that stops a lobby matching. Measured on the frame that failed: right orb `0.48`, left orb `0.91`; on two lobby frames neither matches (`0.27`/`0.33` and `0.37`/`0.37`). `assets/in_play.json` takes a `references` list; a single reference may still be written flat at the top level, which is the right shape when there is only one thing to find (`save_and_exit.json`). Because each reference has its own search region, `main.py` passes a `resolve_region` **callback** rather than one region — forcing one region on all of them would search the right-hand corner for the left-hand orb.

**The negative is debounced; the positive is not.** Seeing the HUD is proof; *not* seeing it might only mean something is briefly covering it. So a hit publishes immediately and a miss must persist for `IN_PLAY_MISS_GRACE_SECONDS` (0.3s) first. Kept short deliberately: believing we are in a game for too long means a keypress landing where it should not, and at 0.3s against `POTION_MIN_GAP_SECONDS` of 0.6 that is at most one. This covers *flicker*; sustained occlusion is what the second reference is for.

**Restricted to a search region, and that is a 15x difference, not a tidiness preference:** a full-frame `matchTemplate` at `CAPTURE_SCALE` costs **3.0ms** — as much as the needle match, i.e. it would roughly double the detection thread's cost — against **0.198ms** restricted to the bottom-right. That is cheap enough to run **every frame**, which matters: a stale "yes" is exactly the window in which the wrong keys get typed.

**The search region and the template scale both route through the window anchor**, the same way HUD meters do — the art is at a fixed place in the *window*, not on the screen, so a windowed or moved game would otherwise search the wrong pixels, and a different resolution would compare against a wrongly-sized reference. `assets/in_play.json` holds the template path, the size it was cut at, the search region and the threshold; **nothing Diablo-II-specific is in the module.** Pointed at a security camera the same code answers "is the door frame still in view?" — a sanity check that the camera has not been knocked askew before trusting anything else measured from that frame.

`main.py` publishes the result and `actions_allowed()` now requires **both** guards to not say no. They fail differently, which is why both exist: **focus** catches "these keys are going to another program", **in-play** catches "these keys are going to THIS program, which is showing a lobby with a text field focused". As always, `None` means "cannot tell" and is not `False` — no config, no template, or an unjudgeable frame all leave the pipeline behaving exactly as it did before the check existed.

**`cv.resize` raises when a scale rounds a dimension to zero** (`!dsize.empty()`), so the size must be computed and checked *before* resizing — checking the result's shape afterwards never runs. Caught by a test rather than by the detection thread dying in a live session.

### `window_region.py` — anchoring a region to a window instead of the screen

**The distinction this module exists for: a detection box is screen-absolute, a HUD meter is not.** A box is found by looking at pixels, so it works identically fullscreen, windowed, or moved — nothing about it needs to know where the game is. "The health orb is 21% across and 84% down" is only meaningful relative to *the window drawing it*. Storing that as a fraction of the screen breaks the moment the game is not fullscreen, which is exactly what happened: meters calibrated fullscreen read **0% at full health** once the game was switched to windowed 1280x800, because the stored fractions then pointed at bare desktop. Anchoring to the window makes one config survive the window being **moved or resized**. It does **not** survive the game changing its own resolution or aspect ratio — the game re-lays out its HUD. Measured: 1920x1080 → 1280x800 held the orbs' vertical position and height to within 0.001 of the same window-fraction, but moved them horizontally by 0.033, which is **42px against a 104px-wide orb**. The calibrator records the client size, and when the live aspect no longer matches, `main.py` warns on the console **and the panel replaces its readings with `RECALIBRATE / was 1280x800 / now 1920x1080 / readings not trustworthy`**. The panel matters more than the console does here: a console warning about a silently wrong number is a warning nobody receives, because the person who needs it is looking at the game, not the terminal. This was observed exactly that way — the console warning fired and went unseen while the readings looked confidently wrong on screen. **Re-calibrate in whichever mode you actually play in.**

`find_client_rect(title_substring)` returns the **client** area, not the window rect — the window rect includes the title bar and borders the game does not draw into (measured: window rect `(515,117)`, client `(525,150)`, a 33px vertical offset, comfortably enough to miss an orb). **An exact title match beats a substring one, and only then does size break the tie.** Size alone was measured getting it wrong: searching `"Diablo II"` matched both the game (client 1280x800) and a browser tab titled *"d2r.guide — Diablo II: Resurrected Cheat Sheet — Google Chrome"* (client 1920x1080), and the browser won on size. Any editor tab, chat window or web page mentioning the game is a candidate.

The user never types a window title: `calibrate_meters.py` snapshots the visible windows **before drawing any UI of its own** (otherwise its own always-on-top selection window is what the point lands in), then attributes each hand-drawn selection to the smallest window containing it and records that as `"_anchor"` in `meters.json`. `game_state.py` stores the anchor via `load_anchor()`/`save_meters()` but **never interprets it** — resolving it needs OS-specific window lookup, which is a caller's business, not a detector's.

**Acting on the screen requires knowing the screen is still the game's — `is_foreground()` is that check, and it has THREE answers, not two.** Nothing used to verify this: alt-tab away and the meters measure whatever is now in front (typically 0%, i.e. "you are about to die"), while `run_auto_collect()` keeps clicking at screen coordinates that now belong to a browser. `find_window()` returns an **opaque handle** alongside the rect purely so this check can be a raw `GetForegroundWindow()` comparison — measured **0.3µs**, callable per frame, against 0.151ms for the `EnumWindows` sweep that finds the window in the first place (~500x). `True`/`False` are the guard; **`None` means "cannot tell" and must never be collapsed into `False`** — it is returned without `pywin32`, without an `_anchor` in `meters.json`, and when the window is not currently found, and on all three of those the pipeline has to behave exactly as it did before the guard existed. So meters suspend and actions stop only on a positive `False` (`main.actions_allowed()` is `anchor_focused() is not False`); an unguarded setup is never disabled by a check it cannot perform.

**It is a hard stop for actions and a suspension for readings, and focus is deliberately the wrong question.** A windowed game that is visible but unfocused is perfectly readable, so this will say `False` in cases that would have worked. That direction is the safe one — a false `False` costs a paused pickup, a false `True` costs a potion drunk against a browser's pixels, or a click into it. Occlusion is the question you actually want and there is no cheap correct answer to it on Windows (walking the z-order and intersecting rects is both expensive and wrong under transparency). The state is surfaced **on the panel** (`GAME STATE  NOT FOCUSED`, readings `suspended`, actions `paused`), not just the console, for the reason the `RECALIBRATE` banner exists: the person who needs to know why nothing is happening is looking at the game. Detection and OCR are deliberately **not** gated — boxes are display-only and a detector must work against any frame, so stopping them would be a performance decision, not a safety one.

**The anchor's handle is refreshed on every lookup, even when the rect is unchanged.** `_refresh_anchor()` short-circuits when the window's rect matches the cached one, but a game closed and relaunched at the same size and position is a *different* window with an *identical* rect — keeping the old handle would leave the focus check comparing against a window that no longer exists, i.e. permanently `False`, i.e. the guard stuck on with no way to clear it. Same family of bug as the `_UNRESOLVED` sentinel just above: a cache whose key can't distinguish two different states.

`main.py` re-locates the anchor at most once a second (`ANCHOR_REFRESH_SECONDS`; `EnumWindows` is far too expensive at 45 FPS) and rewrites each meter's region against the captured frame. **When the anchor is configured but its window can't be found, it reads NO meters, so every value becomes `None` — never `0.0`.** Reporting a full health orb as empty because the window moved is exactly the confusion `game_state.py` exists to prevent, and it would drive a potion or a retreat. The debug panel says `window not found` rather than showing every meter as unreadable and leaving the cause to be guessed at.

Everything degrades to `None` without `pywin32`, and every caller treats that as "no anchor, use the full frame" — the pipeline stays fully functional, just screen-anchored as before. A config with no `_anchor` (fullscreen calibration) behaves exactly as it always did.

### `calibrate_meters.py` — one-time setup + live validation tool

`python tools/calibrate_meters.py` — waits out a countdown so you can switch to the game, grabs a screenshot, lets you drag a box around each orb, and writes `assets/meters.json`. `--preview` skips straight to the preview against the saved config; `--delay` changes the countdown.

**Its windows must be created topmost (`_show_window()`), or they never appear.** The flow is "switch to the game, wait out a countdown, then interact with a window" — so by the time the window opens the *game* is the foreground app, and a normally-created OpenCV window opens behind it and is silently never seen. The symptom is "I run it and nothing happens". Any future interactive tool with a countdown has the same problem. If the game is in exclusive-fullscreen mode nothing can draw over it at all and it has to be switched to Windowed/Borderless — the tool now says so up front.

The **live preview matters more than the box-dragging does**, and is why this is an interactive tool rather than a set of constants. A mistuned color range fails by returning a plausible-but-wrong percentage rather than by raising an error, so it has to be validated by eye: the preview shows the raw region with the detected liquid surface drawn across it, the exact pixels being counted, and the live percentage. It also reports the measured hue/saturation/value of the pixels you selected and warns when they don't match the preset's expected range, which is the signal to widen `hsv_ranges` in the JSON.

**It captures `main.py`'s `monitor_area`, imported, not its own idea of "the screen".** Regions are stored as fractions of the captured frame, so the calibrator and the pipeline must agree what frame those fractions are *of*. They once didn't — this grabbed `sct.monitors[0]` (the whole multi-monitor virtual desktop) while `main.py` grabs only the primary display, which would have put every meter at the wrong screen position with no error raised (`Error_history.txt` #27). Contrast `--fast-scale` just below, which is deliberately a duplicated argument rather than an import: that one is correct *because* correctness doesn't depend on it. A mismatch that changes the ANSWER must be shared; a mismatch that only changes a DISPLAY can be passed.

It shows each meter at **both** full resolution and the fast path's downscale (`--fast-scale`, default `0.3` to match `main.py`'s `CAPTURE_SCALE`). Those two should agree within a couple of percent; if they don't, the meter is too small to measure reliably at that downscale and `main.py` should read it from a higher-resolution frame instead. `--fast-scale` is an explicit argument rather than an imported constant on purpose — correctness doesn't depend on it (regions are stored as fractions), it's purely a validation readout, so there's no second copy of a resolution constant that can silently drift out of sync.

### `legacy/` — earlier, more modular prototype (kept for reference, not run by default)

This is a different, incompatible architecture built for automating a specific game (Diablo II: Resurrected) rather than generic screen detection:

- `Window_Capture.py` — `WindowCapture` class: finds a game window by title via `win32gui`, computes crop offsets for borders/titlebar, and captures that window specifically (via `PrintWindow`) instead of the whole screen. Also maps in-window coordinates back to screen coordinates for mouse actions.
- `vision.py` — `Vision` class: reusable template-matching wrapper (load a needle image, `find()` matches/groups rectangles, `get_click_points()`, `draw_rectangles()`/`draw_crosshairs()`), plus an interactive HSV-trackbar GUI (`init_control_gui`/`apply_hsv_filter`) for tuning color-based masks.
- `hsvwindow.py` — plain data holder (`HsvWindow`) for the HSV min/max + add/sub trackbar values used by `Vision`'s HSV filter.
- `pindle.py` — game-specific automation script (`pindle_script`, `nihlathak_portal_search`) that uses `WindowCapture` + `Vision` + `pyautogui` to click through a sequence of screen positions.
- `oldmain.py` — the integration point tying the above together (loads a Haar cascade classifier and several `Vision` instances for health/mana potions, binds `F9` via the `keyboard` module to trigger `pindle_script`, runs a single-threaded detect/draw/act loop keyed on a `health` variable).

`legacy` code references assets that aren't in this repo (`cascade_classifier/cascade/cascade.xml`, `items/potions/*.jpg`, `items/misc/NithalakPortal.jpg`) and won't run as-is — treat it as prior-art/reference when porting ideas (e.g. the `Vision` class abstraction, HSV tooling, or window-specific capture) into the current `main.py` pipeline, not as runnable code. `legacy/assets/` holds a few leftover test images (`img_1.jpg`, `zombie_1.jpg`, `zombie_1_processed.jpg`) — none of them are loaded by any script; they're just artifacts from earlier testing.

**Why the layout is shaped this way, and where a new file goes.** The split is the architecture, not filing: `core/` is the engine and `main.py` is the Diablo II integration, and **the import direction enforces it** — `main.py` imports `core`, and `core` imports nothing back. If something in `core/` ever needs to import `main`, that is the design going wrong, not an import problem to solve.

- A new **detector** (a trained model, motion detection, colour blobs) is a new module in `core/`. Note that core's modules do not import *each other* either — see "Detector independence" above. That was what made moving them into a package a safe change rather than a risky one.
- A new **game-specific sequence** (a Pindle run, a chest route) does not go in `core/`. Today `main.py` holds them; when there is more than one, a `routes/` package beside `core/` is the place, importing `core` the same way `main.py` does.
- **Tools and tests are run directly** (`python tests/test_x.py`), so each begins with a two-line `sys.path` bootstrap to put the repo root on the path — `sys.path[0]` is the script's own folder, not the root.
- **A test never reads `assets/zelScreenshots/`.** That is the owner's scratch space for sharing screenshots during a session, it is gitignored, and it gets cleared whenever it suits them. A test pointed at it does not fail when a file disappears - it *skips*, which is indistinguishable from passing. **That has already happened twice**: `test_presence.py`'s entire real-screenshot section silently stopped running, and `test_quit_game.py`'s button checks are still off because the Esc-menu screenshot they used is gone. Real frames a test needs go in `tests/fixtures/`, committed, with an entry in its README.
- **Fixtures are masked, not shrunk**: everything outside the regions the tests search is blacked out at the **same frame dimensions**, so every fraction and coordinate is unchanged while the files roughly halve. The rule when adding one is *preserve the numbers a test asserts on, not just the answers* - the first attempt masked the orb corners out of the lobby frames, every True/False still matched, and the in-play score fell from 0.272 to 0.038, which would have left the margin test measuring black pixels.
- `user_config.txt` stays at the **root**, not in `assets/`, because it is the one file a person is expected to open and hand-edit. `assets/` holds data the tools write or the engine reads.

There is exactly one `main.py`, at the repo root. `legacy/` used to be `version1/` and also had its own `main.py`; that duplicate was deleted since it was a strict subset of the root pipeline's screen-capture thread with no detection logic of its own. If a second entry point becomes genuinely necessary later (e.g. a GUI mode, a camera-input mode), prefer a flag/mode on the existing `main.py` or a distinctly-named new file — avoid ending up with two files named `main.py` again.

## Key things to watch for when editing

- Anything reading frames must handle BGR (not RGB) — OpenCV convention throughout.
- The root pipeline's threads are infinite loops with no clean shutdown signal besides the `q` keypress in `draw_and_output`; if you add new threads, follow the same daemon-thread + bounded-queue pattern so the app still exits on `q`.
- Match threshold (`0.60` in root `main.py`) and `max_results` are tuned by hand — changing the needle image or resize factor generally requires re-tuning both.
- Don't add game-specific logic (Diablo II window titles, item images, key bindings) into the core capture/detect/draw pipeline — keep it in clearly-separated example/integration code so the engine stays reusable for other games and, eventually, non-game camera input.
- Watch for anything that would silently hurt FPS or add per-frame overhead (unnecessary `.copy()`s, growing data structures, blocking I/O in a hot loop) — profile or reason through the cost before merging, per the performance priority above.
